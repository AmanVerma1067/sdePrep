Section 1

System Overview & the 66 API Endpoint Matrix

How a modular SaaS packaging-spec platform handles multi-tenancy, dynamic workflows, and granular specification data on a document-native store instead of a normalized relational schema.

Why document-native for this domain

Packspec's core object — a packaging specification — is inherently a variable-shape tree: a spec has an arbitrary number of groups, each group an arbitrary number of fields, each field a different type and validation rule depending on the product category and client configuration. In a relational schema this is the textbook trigger for an EAV (Entity-Attribute-Value) table or a wall of nullable columns — both of which degrade badly under query load and schema evolution. MongoDB's document model lets a specification, its groups, and its fields live as one nested document, read and written in a single round trip, versioned as a whole unit — which maps directly onto how the product actually needs to read and write that data: "give me the whole spec" and "give me the whole spec as of revision N," not "join 4 tables and reconstruct the tree in application code."

The trade-off this buys, and its cost, is covered in full in Pillar C and Pillar D below — embedding isn't free, and where Packspec deliberately chose references over embedding (e.g. component_id → product_id) matters as much as where it chose to embed.

Pillar A — Multi-Tenant Data Isolation

Database-per-tenant vs Collection-per-tenant vs Shared-Collection

Database-per-TenantCollection-per-TenantShared-Collection + Discriminator
Isolation strengthStrongest — physically separateStrong — logically separate namespaceLogical only — enforced at query layer
Atlas connection/resource costHigh — each DB carries its own connection pool overhead and metadataModerate — collection sprawl still fragments indexes and metadata cacheLow — one pool, one index set, shared cache
Cross-tenant aggregate queriesVery hard — requires fan-out across DBsHard — fan-out across collectionsTrivial — one $match stage
Onboarding a new tenantProvisioning overhead — new DB, new indexesProvisioning overhead — new collection, new indexesZero — insert documents with a new tenant_id
Blast radius of a bugContained to one DBContained to one collectionWhole cluster if the discriminator filter is missed

Packspec used the Shared-Collection model with a uniform tenant_id discriminator field. With a Module Governance layer (Module 5) and Client Module Mapping (Module 6) that both need cross-tenant visibility for platform-level administration — and with the tenant count expected to grow continuously via self-serve-style onboarding (Module 4) — database-per-tenant would have meant provisioning and index-managing a growing number of independent databases on the same Atlas cluster, fragmenting the working set across separate connection pools instead of letting Atlas serve one hot, well-indexed collection out of RAM. The trade Packspec explicitly accepted: isolation is enforced in application code, not by the storage engine — which is why Pillar A's second half exists.

PHP Implementation: Tenant Scoping Middleware

// TenantScopeMiddleware.php
// Runs before every route handler in Modules 1, 3, 6, 7, 8, 9 —
// anywhere a query could otherwise cross tenant boundaries.
class TenantScopeMiddleware {

    public function handle(Request $request, callable $next) {
        $token = $this->extractBearerToken($request);

        try {
            $decoded = JWT::decode($token, $this->secretKey, ['HS256']);
        } catch (ExpiredException | SignatureInvalidException $e) {
            return Response::json(['error' => 'Invalid or expired token'], 401);
        }

        $tenantId = $decoded->tenant_id ?? null;
        if (!$tenantId) {
            return Response::json(['error' => 'Token missing tenant scope'], 403);
        }

        // Attach to a request-scoped context object — every downstream
        // repository call reads tenant_id from HERE, never from a
        // client-supplied field in the request body or query string.
        $request->setContext('tenant_id', $tenantId);
        $request->setContext('user_id',   $decoded->user_id);
        $request->setContext('role',     $decoded->role);

        return $next($request);
    }
}

// TenantScopedRepository.php
// The actual leak-prevention mechanism: a thin wrapper every
// Module 1/3/6/7/8/9 repository extends. Handlers can no longer
// call the raw MongoDB\Collection directly — only through this.
abstract class TenantScopedRepository {

    protected \MongoDB\Collection $collection;
    protected string $tenantId;

    public function __construct(\MongoDB\Collection $collection, string $tenantId) {
        $this->collection = $collection;
        $this->tenantId   = $tenantId;
    }

    public function find(array $filter = []): array {
        // tenant_id is force-merged LAST so it can never be overridden
        // by a caller-supplied filter key of the same name.
        $scoped = array_merge($filter, ['tenant_id' => $this->tenantId]);
        return $this->collection->find($scoped)->toArray();
    }

    public function updateOne(array $filter, array $update, array $options = []) {
        $scoped = array_merge($filter, ['tenant_id' => $this->tenantId]);
        return $this->collection->updateOne($scoped, $update, $options);
    }

    public function aggregate(array $pipeline) {
        // Every aggregation entering this repository gets tenant_id
        // injected as the FIRST $match stage — before any $lookup,
        // $group, or $project a developer might add later.
        array_unshift($pipeline, ['$match' => ['tenant_id' => $this->tenantId]]);
        return $this->collection->aggregate($pipeline)->toArray();
    }
}
💡 Why this design, specifically

The isolation guarantee doesn't live in each of the 66 route handlers remembering to add a filter — it lives in one repository base class those handlers are structurally unable to bypass. Endpoint 41 (/workflows/{company_id}/{component_id}) and endpoint 48 (GET /specifications) both go through this same repository layer, so the isolation guarantee is identical whether the query is a simple lookup or a multi-stage aggregation feeding endpoint 64's dashboard counts.

Pillar B — Atomic Multi-Document Transactions & Cross-Tenant Leak Prevention

The core risk

Several endpoints are single API calls that must succeed or fail as one atomic unit across multiple documents, sometimes multiple collections: /product/{id}/clone (#6) writes a new product plus, transitively, cloned components; /specifications/{spec_id}/clone (#56) deep-copies a specification's full group/field tree into a new document; /module-workflows/clients/{client_id}/{module_id}/workflows (#35) rewrites workflow step arrays that active workflow instances (Module 8) may already be mid-execution against. A failure partway through any of these — a dropped connection, a validation error on write 3 of 5 — without transactional guarantees leaves the database in a state no single document's own consistency rules can catch: an orphaned clone with no parent reference, or a workflow instance mid-flight against step definitions that no longer exist.

Under the hood: WiredTiger, tickets, and the oplog

MongoDB's multi-document ACID transactions run against a consistent snapshot of data taken by the WiredTiger storage engine at transaction start, using MVCC (multi-version concurrency control) so readers outside the transaction see the pre-transaction state until commit. WiredTiger allocates a limited number of concurrent read/write tickets (default 128 each) to throttle how many operations can touch the storage engine simultaneously — a long-running transaction holds its ticket for its full duration, which is precisely why transaction runtime matters operationally, not just correctness-wise. On commit, the transaction's writes are recorded as a single logical unit in the oplog (the replication log every secondary tails), so replica set members apply the whole transaction atomically too — a secondary can never observe the transaction half-applied.

Production PHP: Transactional Clone Flow

// SpecificationCloneService.php — backs endpoint 56:
// POST /specifications/{spec_id}/clone
public function cloneSpecification(string $specId, string $tenantId): array {
    $client  = $this->mongoClient;
    $session = $client->startSession();

    try {
        $session->startTransaction([
            'readConcern'  => new \MongoDB\Driver\ReadConcern('snapshot'),
            'writeConcern' => new \MongoDB\Driver\WriteConcern(\MongoDB\Driver\WriteConcern::MAJORITY),
        ]);

        // 1. Read the source spec WITHIN the session so the snapshot
        //    is consistent with the writes that follow.
        $source = $this->specifications->findOne(
            ['_id' => new ObjectId($specId), 'tenant_id' => $tenantId],
            ['session' => $session]
        );

        if (!$source) {
            throw new NotFoundException("Specification $specId not found for tenant");
        }

        // 2. Deep-copy groups/fields, strip immutable identity fields.
        $clonePayload = $this->buildClonePayload($source);

        $insertResult = $this->specifications->insertOne(
            $clonePayload,
            ['session' => $session]
        );

        // 3. Write the audit trail entry as part of the SAME transaction —
        //    if this fails, the clone insert above rolls back too.
        $this->auditLog->insertOne([
            'tenant_id'   => $tenantId,
            'action'      => 'specification.clone',
            'source_id'   => $specId,
            'resulting_id' => $insertResult->getInsertedId(),
            'timestamp'   => new UTCDateTime(),
        ], ['session' => $session]);

        $session->commitTransaction();

        return ['cloned_id' => (string) $insertResult->getInsertedId()];

    } catch (\Exception $e) {
        $session->abortTransaction();
        throw new CloneFailedException("Clone aborted: " . $e->getMessage(), 0, $e);
    } finally {
        $session->endSession();
    }
}
⚠️ Deliberate design boundary

The transaction wraps the read of the source document too, not just the writes — using readConcern: snapshot so a concurrent edit to the source spec mid-clone can't produce a clone that's an inconsistent mix of pre- and post-edit field values. This matters specifically because #50 (PUT /specifications/{specid}) and #56 (clone) can legitimately race against the same source document under real usage.

Pillar C — Custom Snapshot Versioning Engine & Dynamic Schema Design

The architectural blueprint (endpoints 57–66)

A relational implementation of dynamic, per-tenant-configurable fields typically collapses into the EAV anti-pattern: an entity_id / attribute_id / value table, reassembled at read time via a self-join per attribute — a query that gets linearly more expensive as a specification grows more fields, and that turns a single logical "fetch this spec" operation into a many-row, many-join reconstruction problem in application code. Packspec's specifications instead embed groups and fields as nested arrays directly on the specification document:

{
  "_id": ObjectId("..."),
  "tenant_id": "acme-corp",
  "status": "draft",
  "groups": [
    {
      "grp_id": "g1",
      "label": "Material Composition",
      "fields": [
        { "f_id": "f3", "type": "number", "label": "Wall Thickness (mm)", "value": 1.8 },
        { "f_id": "f4", "type": "select", "label": "Resin Grade",     "value": "HDPE-2" }
      ]
    }
  ]
}

Reading a full specification (#49) is one findOne — no joins, no reconstruction. Mutating a single field (#61) is one targeted update using positional array filters, shown below — not a row update in a separate table plus an application-level cache invalidation.

Nested field mutation — endpoint 61

// PUT /specifications/{spec_id}/groups/g1/fields/f3
public function updateField(string $specId, string $grpId, string $fieldId, array $newValue, string $tenantId) {
    return $this->specifications->updateOne(
        [
            '_id'       => new ObjectId($specId),
            'tenant_id' => $tenantId,
        ],
        ['$set' => ['groups.$[g].fields.$[f].value' => $newValue['value']]],
        [
            'arrayFilters' => [
                ['g.grp_id' => $grpId],
                ['f.f_id'   => $fieldId],
            ],
        ]
    );
}

The relational equivalent of this single call is a targeted UPDATE against an EAV value table plus a transaction if the field's "last modified" audit trail lives in a related table — arguably comparable in that one specific case, but it stops being comparable the moment endpoint 49 needs to read the whole tree back, which is every read in the product.

Snapshot engine logic — isolating drafts from locked milestones

Packspec's architecture keeps the working draft as the live document (mutated in place by #50, #57–63) and writes full point-in-time copies into a dedicated spec_revisions collection at the two moments that matter for audit integrity: submission (#51) and explicit revision snapshotting (#65) — rather than accumulating an ever-growing embedded delta array inside the live specification document itself.

💡 Why a dedicated collection over an embedded delta array

An embedded revision-delta array on the live document means every read of the working spec (#49) drags along its entire history whether the caller needs it or not, and it pushes the document steadily toward MongoDB's 16MB document size ceiling on long-lived specs with many revisions. A dedicated spec_revisions collection keeps the hot, frequently-read working document lean, and makes endpoint 66 (GET /specifications/{specid}/versions) a simple indexed query — {spec_id, tenant_id} — against a collection that's purpose-built for append-only historical reads and never touched by the draft-editing hot path.

// SpecificationRevisionService.php — backs endpoint 65:
// POST /specifications/{spec_id}/revision
public function createRevision(string $specId, string $tenantId, string $triggeredBy): array {
    $spec = $this->specifications->findOne(['_id' => new ObjectId($specId), 'tenant_id' => $tenantId]);

    // Immutable snapshot: the FULL group/field tree copied as-is,
    // stamped with the revision number and the reason it was taken
    // (submit / approve / manual). Never mutated after insert.
    $revisionDoc = [
        'spec_id'       => $specId,
        'tenant_id'     => $tenantId,
        'revision_number' => $this->nextRevisionNumber($specId),
        'snapshot'       => $spec['groups'],
        'status_at_snapshot' => $spec['status'],
        'triggered_by'   => $triggeredBy,
        'created_at'     => new UTCDateTime(),
    ];

    $this->specRevisions->insertOne($revisionDoc);
    return ['revision_number' => $revisionDoc['revision_number']];
}
📊 On the 65% reconciliation-overhead claim

Frame this number by what it's measuring, precisely: before the dedicated spec_revisions collection existed, verifying "what changed between submission and approval" meant a verifier manually diffing exported spec snapshots by eye — a process tracked (informally, via team standup notes and ticket timestamps) at roughly 15–20 minutes per specification review across a sample of specs during early pilot use. With endpoint 66 surfacing the full revision array directly in the review UI, that dropped to a few minutes of automated diff review — the 65% figure is the reduction in that specific manual-comparison step, not a claim about total workflow turnaround time. Be precise about that distinction if pressed — it's a defensible number for what it actually measured, not a defensible number for "development velocity" broadly.

The aggregation pipeline — endpoint 64

// GET /specifications/counts — dashboard counts by status, tenant-scoped
$pipeline = [
    // Stage 1 — tenant isolation FIRST, exactly as Pillar A's
    // repository wrapper enforces automatically.
    ['$match' => ['tenant_id' => $tenantId]],

    // Stage 2 — group by status, count per bucket.
    ['$group' => [
        '_id'   => '$status',
        'count' => ['$sum' => 1],
    ]],

    // Stage 3 — reshape for direct UI consumption:
    // { draft: 12, submitted: 4, approved: 31, rejected: 2 }
    ['$group' => [
        '_id'    => null,
        'counts' => ['$push' => ['k' => '$_id', 'v' => '$count']],
    ]],
    ['$replaceRoot' => [
        'newRoot' => ['$arrayToObject' => '$counts'],
    ]],
];

$result = $this->specifications->aggregate($pipeline)->toArray();

A compound index on {tenant_id: 1, status: 1} lets Stage 1 and the grouping key of Stage 2 both resolve from the index directly (a covered-query-adjacent pattern) rather than scanning every specification document for the tenant.

Pillar D — Relational Concepts Mapped to MongoDB Realities

Normalization vs Embedding

The rule Packspec's schema follows: embed when the child data has no independent existence or query pattern apart from its parent, and is always read together with it — a specification's groups and fields (Module 9) fit this exactly, they're meaningless outside their parent spec and are always fetched as a whole tree (#49). Reference when the child is independently queried, independently sized, or shared across parents — a component referencing its product_id (Module 3) fits this: components are fetched on their own (#17), listed independently by product (#18), and a product can accumulate components over years without the parent document growing unbounded.

Joins vs $lookup

$lookup is a left-outer-join equivalent, but it's meaningfully more expensive than a well-indexed SQL join at scale, especially across a sharded cluster where the foreign collection may not be co-located with the querying shard — each $lookup can trigger scatter-gather across shards rather than a local index hop. Packspec's practical rule: use $lookup for low-frequency, admin-facing reads (e.g. joining client metadata onto a global billing list, #21) where query volume is low and correctness/freshness matters more than raw speed; for high-frequency reads on the hot path (e.g. rendering a specification with its component's name), duplicate the small, rarely-changing metadata field (like component_name) directly onto the specification document at write time instead — accepting eventual staleness on a field that changes rarely, in exchange for removing a join from every single spec read.

Traditional Indexes vs Compound/Multikey Indexes

PatternExampleWhat it prevents
Compound index{tenant_id: 1, product_id: 1}A collection scan on every #18 (/component/getbyproduct/{id}) call — the tenant filter and the product filter resolve from one index in a single seek

⚠️ Trap to watch for in your own schema

Index field order matters — {tenant_id: 1, status: 1} serves a query filtering on tenant_id alone or on both fields, but does not efficiently serve a query filtering on status alone. Every compound index in this system is deliberately built tenant_id-first, because there is no legitimate query path in Packspec that should ever filter across all tenants by status alone — that's a query shape the schema intentionally makes expensive.

The Interviewer's Callout Bank & High-Stakes QA Matrix

Direct, resume-defending answers written from the perspective of the engineer who built this. No hedging, no generic textbook answers.

QA — Multi-Tenancy

QShared collections mean one forgotten tenant_id filter leaks another tenant's data. How did you prevent that as a systemic risk, not a code-review hope?
A: By making it structurally impossible to query without a tenant filter rather than relying on every handler remembering one. Every Module 1/3/6/7/8/9 repository extends a TenantScopedRepository base class (Pillar A) that merges tenant_id into every filter — including the first stage of every aggregation pipeline — before the query ever reaches the driver. A developer would have to deliberately bypass the repository layer and call the raw MongoDB\Collection directly to produce a leak, which is a code-review-visible red flag, not a silent omission.
QWhat stops a malicious or buggy client from forging a tenant_id in the request body to escalate into another tenant's data?
A: The tenant scope never comes from the request body or query string in the first place — it's extracted exclusively from the verified JWT claims in TenantScopeMiddleware and attached to a request-scoped context object. Any tenant_id a client attempts to smuggle into a request payload is simply never read; the repository layer only consults the context value the middleware set from the signed token.

QA — Transactions

QWiredTiger transactions have runtime and oplog size limits. What happens if a deep clone on /specifications/{spec_id}/clone hits a multi-megabyte spec under heavy concurrent load?
A: Two separate risks, and they're handled differently. First, a long-running transaction holds its WiredTiger ticket for its full duration — under contention this can exhaust the ticket pool and stall unrelated writes, so the clone transaction is scoped as tightly as possible (read source, insert clone, write one audit entry — nothing else inside the transaction boundary) rather than wrapping the whole HTTP request handler. Second, a genuinely oversized specification approaching MongoDB's 16MB document ceiling is a modeling problem the transaction can't fix — that's the pressure that would force splitting extremely large group/field trees into referenced sub-documents rather than a single embedded array, a trade-off explicitly discussed in Pillar D. Today's specifications stay well under that ceiling, but it's the known scaling edge of the embedded-document design.
QWhy readConcern: snapshot specifically, instead of the driver's default?
A: Because the clone reads a source document and writes a derived document in the same transaction — without snapshot isolation, a concurrent edit to the source spec mid-transaction (via #50) could be partially visible, producing a clone that's an inconsistent mix of pre- and post-edit field values. Snapshot read concern guarantees every read inside the transaction sees the same point-in-time view, so the clone is always internally consistent with a single version of the source, whichever one that turns out to be.

QA — Versioning Engine

QYou claim the snapshot engine cut manual reconciliation effort by 65%. Walk me through the exact validation of that number.
A: That figure specifically measures the manual spec-diffing step verifiers previously did by eye when comparing a submitted spec against its prior approved state — tracked informally against pilot-phase review timestamps, roughly 15–20 minutes per review dropping to a few minutes once endpoint 66 surfaced the revision array directly in the UI for automated diff rendering. I'd be precise that it's a measurement of one specific manual step being automated, not a claim about total end-to-end workflow turnaround — which is affected by far more than the versioning engine alone.
QHow did your test coverage validate that revisions were actually immutable and accurate?
A: Through a Postman collection exercising the full spec lifecycle end-to-end per test case: create a spec, mutate fields across multiple groups, trigger a revision snapshot (#65), mutate the live draft further, then assert via #66 that the stored revision's snapshot array is byte-for-byte unchanged from its state at snapshot time while the live document has diverged. Running that assertion across the roughly 200+ cases covering different group/field shapes, tenant contexts, and status transitions is what gave confidence the revision collection was genuinely append-only and never mutated by later draft edits — rather than trusting that behavior by code inspection alone.

QA — Data Modeling

QWhy not embed components inside their parent product document, the same way you embed fields inside specifications?
A: Because the access pattern is different, and that's the actual test — not "is it hierarchically related." Fields are only ever read as part of their whole specification; components are frequently fetched and mutated independently of the product (#17), listed by product without needing the rest of the product's data (#18), and can accumulate across a product's lifecycle in a way that would push an embedded array toward the document size ceiling. Fields don't have that independent-access or unbounded-growth profile within a single spec, which is why one got embedded and the other got referenced.

QA — Named Scenarios

QYour route /workflows/deleteAll looks like a massive security liability. How did you ensure it was stripped from production or tightly restricted from accidental triggers?
A: I'll answer this directly rather than defend the endpoint's existence: a total-purge route reachable in a production build is a real liability regardless of intent, and the correct posture is that it should never have been deployable behavior in the first place — not merely access-restricted. The two layers that should gate this, and the ones I'd point to as the accountable design: (1) environment-based route registration, where sandbox-only routes are registered from a separate route file loaded only when APP_ENV=testing, so the route literally doesn't exist in the production router table rather than existing-but-blocked; (2) as defense in depth if that gate were ever misconfigured, a hard role check requiring a dedicated test-admin role that's never issued to any production JWT. If asked whether this was airtight in the actual deployed system, the honest answer is that route-level environment gating is the correct fix and the one to lead with — a role check alone is not sufficient for an endpoint this destructive.
QStructural overrides like /module-workflows/clients/{client_id}/{module_id}/workflows can rewrite workflow steps while instances are actively mid-execution against them. How is that race handled?
A: The workflow instance (Module 8) captures its own copy of the step sequence it's executing against at bind time (#40) rather than dereferencing the live template on every transition — so an in-flight instance keeps running against the step definitions it started with even if the template is edited underneath it via #35. New instances bound after the edit pick up the new step sequence. This trades perfect "always latest config" behavior for correctness of in-flight workflows, which is the right trade here: a Creator/Verifier/Approver chain silently changing shape mid-approval would be a much worse failure mode than a brief period of instances running on slightly stale step definitions.
QWalk me through what happens end-to-end if the process crashes between insertOne and commitTransaction in the clone flow.
A: If the process dies before commitTransaction() completes, the transaction is never committed — WiredTiger's MVCC snapshot means the insert was only ever visible within that uncommitted transaction's own session, so no other reader ever sees the partial clone, and it's rolled back implicitly once the session is recognized as abandoned (session timeout, default 30 minutes, or immediately if the driver detects the connection drop). The client-facing failure mode is a request that times out or errors without a cloned_id in the response — which is the correct outcome: no orphaned document, no partial state, and the caller can safely retry the whole clone operation from scratch.
