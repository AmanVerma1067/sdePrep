01 Indexing & database locking

How a B-Tree index actually helps

An index is a sorted structure. Sorted means you can binary-search it, so finding a row costs about log(N) steps instead of reading every row. For a million rows that's roughly 20 steps instead of a million.

A composite index on two columns is sorted by the first column, and within each value of the first, sorted by the second. Like a phone book sorted by surname, then first name. That one sentence explains every composite-index rule.

The ESR rule — Equality, Sort, Range

Order your index columns as: columns you match exactly, then columns you sort by, then columns you filter with a range.

IndexQueryWhat the DB does
(status, scheduled_at)status='PENDING' AND scheduled_at < now()Jumps straight to the PENDING block, then scans only pending rows in time order. ✅
(scheduled_at, status)Same queryScans every row before now — done, failed, cancelled — checking status on each. ❌
Index (status, scheduled_at) Index (scheduled_at, status) CANCELLED | 09:00 08:00 | DONE ← read CANCELLED | 11:00 08:30 | CANCELLED ← read DONE | 08:00 09:00 | CANCELLED ← read DONE | 10:00 09:15 | PENDING ← keep PENDING | 09:15 ← seek here 10:00 | DONE ← read PENDING | 09:40 ← scan 10:30 | PENDING ← keep PENDING | 10:30 ← scan 11:00 | CANCELLED ← read PENDING | 11:20 ← stop 11:20 | PENDING ← keep Reads only PENDING rows. Reads EVERYTHING before now, Already in scheduled_at order. throws most of it away.
🚨 Concurrency / Index Trap

The leftmost prefix rule. An index on (status, scheduled_at) can serve a query on status alone, or on both — but not on scheduled_at alone. You can't skip the first column, because the index is sorted by it first. The phone book is useless if you only know the first name.

Two more that cost real marks: putting a function on the column (WHERE DATE(created_at) = '2026-08-21') makes the index unusable — rewrite it as a range. And indexing everything is a real cost: every index must be updated on every insert, so on a write-heavy table each extra index directly slows ingestion.

Partial indexes — index only what you query

Partial index for a job queue 
-- Full index: every job ever created, forever. Gigabytes.
CREATE INDEX idx_jobs_all ON jobs (status, scheduled_at);

-- Partial index: only rows a worker could ever claim.
-- Done/failed jobs are 99% of the table and are never polled.
CREATE INDEX idx_jobs_pending
  ON jobs (scheduled_at)
  WHERE status = 'PENDING';

-- Tiny index, stays in RAM, and rows LEAVE the index when status changes.
-- The index size tracks the QUEUE DEPTH, not the table size.
💡 Implementation Pattern

Partial indexes are the most under-used tool in queue design. The insight: a queue table grows forever, but the queue is only the pending rows. A partial index means the structure the database keeps hot in memory is proportional to work-in-progress, not to history. A table with 50 million completed jobs and 200 pending ones has an index with 200 entries.

Pessimistic locking — SELECT ... FOR UPDATE

"I'm going to change this row, so nobody else touch it until I commit." The lock is held until the transaction ends.

FOR UPDATE vs FOR UPDATE SKIP LOCKED 
-- PLAIN FOR UPDATE: others WAIT in line for this row.
BEGIN;
SELECT * FROM seats WHERE id = 42 FOR UPDATE;   -- locks row 42
UPDATE seats SET status = 'HELD', held_by = $1 WHERE id = 42;
COMMIT;                                          -- lock released
-- Correct for "I need THIS specific row" (seat 42, account 7).


-- SKIP LOCKED: others silently SKIP locked rows and take the next free one.
BEGIN;
SELECT id FROM jobs
WHERE status = 'PENDING' AND scheduled_at <= now()
ORDER BY scheduled_at
LIMIT 1
FOR UPDATE SKIP LOCKED;        -- ← the magic
UPDATE jobs SET status = 'RUNNING', worker_id = $1 WHERE id = $2;
COMMIT;
-- Correct for "I need ANY row" — a worker pool. 10 workers poll
-- simultaneously and each gets a DIFFERENT job. Zero contention,
-- zero waiting, no job handed to two workers.
🛡️ LLD Blueprint

The distinction to state out loud in an interview: use plain FOR UPDATE when you need a specific row and it's correct for others to wait — booking seat 14A, debiting account 7. Use SKIP LOCKED when you need any row from a pool and waiting is pointless — a job queue, a task dispatcher.

Getting this backwards is a classic failure: plain FOR UPDATE on a job queue means all 10 workers queue behind the same oldest job, and you've built a single-threaded system with 10 processes.

Optimistic locking — version columns

No locks at all. Read the row with its version, and when you write, require the version to still be what you read. If someone changed it first, your update matches zero rows and you know you lost.

Version-column update 
-- 1. read
SELECT balance, version FROM accounts WHERE id = 1;   -- balance=500, version=5

-- 2. write, conditional on nothing having changed
UPDATE accounts
SET balance = balance - 100,
    version = version + 1
WHERE id = 1 AND version = 5;

-- rowsAffected = 1  → success
-- rowsAffected = 0  → someone else updated it first. Re-read and retry,
--                     or tell the user "this record changed, please review."
 PessimisticOptimistic
Holds a lockYes, until commitNo
Conflict costOthers waitLoser retries
Good whenConflicts are common, waits are shortConflicts are rare
Bad whenLong transactions — everything jamsConflicts are common — retry storms
ExampleSeat booking, inventoryEditing a Packspec document
💡 Implementation Pattern

Optimistic locking is the right answer for human-edited records, and Packspec's spec editing is the example. Two people rarely edit the same spec in the same second, so paying lock cost on every edit to protect against a rare collision is backwards. And when it does collide, the correct product behaviour isn't "wait" — it's "this changed while you were editing, here's what's different." Optimistic locking gives you that error naturally; pessimistic locking hides it by making one person wait.

Deadlocks

Two transactions each hold something the other wants, and both wait forever. The database detects the cycle and kills one.

Transaction A Transaction B ───────────── ───────────── lock row 1 → lock row 2 ↓ ↓ wants row 2 ←── waits ──┐ wants row 1 ↑ │ ↓ └──────── waits ────┴────────┘ DEADLOCK Postgres kills one with: "deadlock detected"
🚨 Deadlock Trap

The fix is boringly simple: always lock rows in the same order. If every transaction locks by ascending ID, a cycle is impossible — A holds 1 and wants 2 while B waits for 1, so B never holds 2. The cycle can't close.

In a transfer function that means sorting the two account IDs before locking, not locking "from" then "to". This is the single most common deadlock question, and the sort is the whole answer.

Also: keep transactions short. Never do a network call, an API request or a file upload inside one — you're holding locks for the duration of something you don't control.

Deadlock-free transfer 
async function transfer(fromId, toId, amount) {
  // ALWAYS lock in a deterministic order — smallest id first
  const [first, second] = [fromId, toId].sort((a, b) => a - b);

  await db.tx(async t => {
    await t.query('SELECT 1 FROM accounts WHERE id = $1 FOR UPDATE', [first]);
    await t.query('SELECT 1 FROM accounts WHERE id = $1 FOR UPDATE', [second]);

    const { rows } = await t.query('SELECT balance FROM accounts WHERE id = $1', [fromId]);
    if (rows[0].balance < amount) throw new Error('Insufficient funds');

    await t.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [amount, fromId]);
    await t.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, toId]);
  });
}

02 Idempotency, queues & state machines

Idempotency: doing it twice must equal doing it once

Networks are unreliable. A client sends "charge ₹500", the response is lost, the client retries. Without protection you charged twice. The client cannot tell the difference between "request never arrived" and "response never came back" — so it must retry, and the server must make that safe.

Idempotency key — the database version 
CREATE TABLE idempotency_keys (
  key            text PRIMARY KEY,        -- client-supplied UUID
  request_hash   text        NOT NULL,    -- guards against key reuse w/ different body
  response_body  jsonb,
  status         text        NOT NULL DEFAULT 'IN_PROGRESS',
  created_at     timestamptz NOT NULL DEFAULT now()
);

-- The unique PRIMARY KEY does the work. Two concurrent requests race;
-- exactly one INSERT succeeds and the other gets a conflict.
BEGIN;
  INSERT INTO idempotency_keys (key, request_hash)
  VALUES ($1, $2)
  ON CONFLICT (key) DO NOTHING;
  -- 0 rows inserted → this key was seen before:
  --   status = 'DONE'        → return the stored response_body
  --   status = 'IN_PROGRESS' → return 409, client retries shortly

  -- ...do the real work, in the SAME transaction...

  UPDATE idempotency_keys SET status = 'DONE', response_body = $3 WHERE key = $1;
COMMIT;
Idempotency key — the Redis version 
# SET with NX = "set only if it does not exist". Atomic — no race.
# EX 120 = auto-expire after 120 seconds.
SET idem:a1b2c3 "in-progress" NX EX 120

# Returns OK   → you are the first. Do the work.
# Returns nil  → someone already has this key. Reject or wait.
💡 Implementation Pattern

The cheapest idempotency of all is a conditional update — no extra table needed:

UPDATE orders SET status='PROCESSING', worker_id='w1' WHERE id=101 AND status='PENDING'

The AND status='PENDING' is the guard. If two workers run this simultaneously, the database serializes them: the first flips the row and gets rowsAffected = 1; the second finds no row still PENDING and gets 0. The loser simply stops. One atomic statement, no lock, no extra table. Reach for this before anything more complicated.

Redis sorted set as a delayed queue 
# schedule: score = the unix time it should run
ZADD jobs:scheduled 1755792000 "job:8817"

# worker: pull everything now due
ZRANGEBYSCORE jobs:scheduled -inf 1755792000 LIMIT 0 10

# claim atomically so two workers can't take the same job
ZREM jobs:scheduled "job:8817"     # returns 1 = you got it, 0 = someone else did

# ZADD/ZRANGEBYSCORE are O(log N) — a sorted set is a skip list,
# so "what's due now" is a range query, not a scan.

The outbox pattern

The problem it solves: you save an order to the database and publish "order created" to a queue. Two systems, no shared transaction. If the DB commit succeeds and the publish fails, the rest of the world never hears about the order. That's the dual-write problem.

❌ DUAL WRITE — can lose events ┌──────────────┐ commit ✓ ┌──────────┐ │ INSERT order │ ───────────► │ DB │ └──────────────┘ └──────────┘ ┌──────────────┐ publish ✗ │ publish evt │ ───────────► 💥 broker down └──────────────┘ event lost forever ✅ OUTBOX — one transaction, no loss ┌────────────────────────────────┐ │ BEGIN │ │ INSERT INTO orders ... │ ← both rows │ INSERT INTO outbox ... │ ← same commit │ COMMIT │ └────────────────────────────────┘ │ ▼ ┌────────────────────────────────┐ │ relay process (polls outbox) │ ──► broker │ marks published_at on success │ retries until it works └────────────────────────────────┘
Outbox table + relay 
CREATE TABLE outbox (
  id            bigserial PRIMARY KEY,
  aggregate_id  text        NOT NULL,
  event_type    text        NOT NULL,
  payload       jsonb       NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz
);
CREATE INDEX ON outbox (id) WHERE published_at IS NULL;   -- partial: only unsent

-- relay loop
BEGIN;
SELECT * FROM outbox WHERE published_at IS NULL
ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED;
-- publish each to the broker...
UPDATE outbox SET published_at = now() WHERE id = ANY($1);
COMMIT;
🛡️ LLD Blueprint

Say the guarantee precisely: the outbox gives you at-least-once delivery, not exactly-once. If the relay publishes and then crashes before marking published_at, the event is sent twice. That is not a flaw to apologise for — it's the standard guarantee, and the answer is that consumers must be idempotent. Every event carries an ID, and consumers skip IDs they've already processed. "Exactly-once delivery" doesn't really exist in distributed systems; "at-least-once delivery plus idempotent consumers" is how you get exactly-once effect.

Retries, backoff and circuit breakers

Exponential backoff with jitter (the RecrutAI shape) 
async function withRetry(fn, { retries = 2, base = 1000, timeoutMs = 6000 } = {}) {
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return await withTimeout(fn(), timeoutMs);      // hard 6s ceiling
    } catch (err) {
      if (!isRetryable(err) || attempt === retries) throw err;

      const backoff = base * 2 ** attempt;            // 1000ms, 2000ms
      const jitter  = Math.random() * backoff * 0.3;  // ±30% spread
      await sleep(backoff + jitter);
    }
  }
}
// isRetryable: timeouts, 429, 502/503/504 → yes.
// 400, 401, 422 → NO. Retrying a bad request just wastes time.
🚨 Thundering Herd Trap

Why jitter is not optional. A service goes down. A thousand clients all fail at the same moment, all wait exactly 1000 ms, and all retry at the same moment. You've built a synchronised hammer. The service comes back up, gets hit by a thousand simultaneous requests, and dies again.

Random jitter spreads those retries over a window so the recovering service sees a ramp instead of a wall. And retries alone make an overload worse — if the upstream is slow because it's drowning, retrying triples the load. That's what a circuit breaker fixes: after N consecutive failures it opens and fails instantly without touching the network, giving the upstream room to recover. Retries handle blips; breakers handle outages.

State machines

A state machine is a list of allowed states plus a table of legal transitions. Everything not in the table is rejected. It turns "did we handle that case?" into a data question.

Chessify game lifecycle WAITING ──join──► READY ──start──► IN_PROGRESS ──mate/resign──► FINISHED │ │ ▲ │ disconnect │ reconnect (within 30s) │ ▼ │ └──────────timeout─────────────► ABANDONED Any event not on an arrow is REJECTED. e.g. 'move' while WAITING → ignored, no crash, no special-case code.
Table-driven state machine (TypeScript) 
type State = 'WAITING' | 'READY' | 'IN_PROGRESS' | 'FINISHED' | 'ABANDONED';
type Event = 'JOIN' | 'START' | 'MOVE' | 'DISCONNECT' | 'RECONNECT' | 'END' | 'TIMEOUT';

// The whole design lives in this one object. Reviewable at a glance.
const TRANSITIONS: Record<State, Partial<Record<Event, State>>> = {
  WAITING:     { JOIN: 'READY', TIMEOUT: 'ABANDONED' },
  READY:       { START: 'IN_PROGRESS', DISCONNECT: 'WAITING' },
  IN_PROGRESS: { MOVE: 'IN_PROGRESS', END: 'FINISHED', DISCONNECT: 'IN_PROGRESS' },
  FINISHED:    {},                      // terminal
  ABANDONED:   {},                      // terminal
};

class GameMachine {
  constructor(private state: State = 'WAITING') {}

  can(e: Event) { return TRANSITIONS[this.state][e] !== undefined; }

  apply(e: Event): boolean {
    const next = TRANSITIONS[this.state][e];
    if (next === undefined) return false;    // illegal → reject, don't throw
    this.state = next;
    return true;
  }
}
💡 Implementation Pattern

Both Chessify and RecrutAI use this shape and it's worth naming the shared benefit: illegal transitions become impossible rather than unhandled. In RecrutAI the LLM returns one of four branch tokens — PROBE_DEEPER, SIMPLIFY, PIVOT_TOPIC, PROCEED — and anything else fails the transition table and triggers the fallback. A hallucinated value can't become a state. Constraining an unpredictable component with a state machine is how you make it safe to depend on.

03 Machine coding implementations

Machine coding rounds mark structure over cleverness. Separate models from services, use interfaces where a strategy could change, keep it runnable, and say your assumptions out loud.

💻 Machine Coding — Token Bucket (C++)

The trick that makes it O(1): don't run a refill timer. Compute tokens lazily from elapsed time on each request.

Token bucket + sliding window log — C++ 
#include <chrono>
#include <mutex>
#include <deque>
#include <unordered_map>

using Clock = std::chrono::steady_clock;

class IRateLimiter {                       // interface → strategies are swappable
public:
    virtual bool allow(const std::string& key) = 0;
    virtual ~IRateLimiter() = default;
};

// ---------- Token Bucket ----------
class TokenBucketLimiter : public IRateLimiter {
    struct Bucket { double tokens; Clock::time_point last; };

    double capacity_;      // max burst
    double refillPerSec_;  // steady rate
    std::unordered_map<std::string, Bucket> buckets_;
    std::mutex mu_;

public:
    TokenBucketLimiter(double capacity, double refillPerSec)
        : capacity_(capacity), refillPerSec_(refillPerSec) {}

    bool allow(const std::string& key) override {
        std::lock_guard<std::mutex> lock(mu_);
        auto now = Clock::now();

        auto it = buckets_.find(key);
        if (it == buckets_.end()) {
            buckets_[key] = { capacity_ - 1, now };
            return true;
        }
        Bucket& b = it->second;

        // LAZY REFILL — no background timer, no per-user thread
        double elapsed = std::chrono::duration<double>(now - b.last).count();
        b.tokens = std::min(capacity_, b.tokens + elapsed * refillPerSec_);
        b.last   = now;

        if (b.tokens >= 1.0) { b.tokens -= 1.0; return true; }
        return false;
    }
};

// ---------- Sliding Window Log ----------
class SlidingWindowLimiter : public IRateLimiter {
    int limit_;
    std::chrono::seconds window_;
    std::unordered_map<std::string, std::deque<Clock::time_point>> log_;
    std::mutex mu_;

public:
    SlidingWindowLimiter(int limit, int windowSec)
        : limit_(limit), window_(windowSec) {}

    bool allow(const std::string& key) override {
        std::lock_guard<std::mutex> lock(mu_);
        auto now = Clock::now();
        auto& q  = log_[key];

        while (!q.empty() && now - q.front() > window_) q.pop_front();  // evict old

        if ((int)q.size() < limit_) { q.push_back(now); return true; }
        return false;
    }
};
🚨 Concurrency Trap

Read-modify-write is not atomic. Checking tokens >= 1 and then doing tokens -= 1 is two operations. Two threads can both read 1 token and both decrement, letting through two requests when only one was allowed. The mutex must cover the check and the update together, not each separately.

Mention the distributed version unprompted: across many servers, an in-memory map means each server allows the full limit independently, so 5 servers = 5× the intended rate. The fix is Redis with an atomic Lua script, or the INCR-with-expiry pattern — one shared counter.

2 · Job scheduler with retries

Priority-queue scheduler with worker threads — C++ 
#include <queue>
#include <thread>
#include <condition_variable>
#include <unordered_set>
#include <functional>

struct Task {
    long long           id;
    Clock::time_point   runAt;
    int                 attempts = 0;
    int                 maxAttempts = 3;
    std::function<void()> fn;

    // priority_queue is a MAX-heap, so invert: earliest time = highest priority
    bool operator<(const Task& o) const { return runAt > o.runAt; }
};

class Scheduler {
    std::priority_queue<Task>        pq_;
    std::unordered_set<long long>    cancelled_;
    std::mutex                       mu_;
    std::condition_variable          cv_;
    bool                             stop_ = false;
    std::vector<std::thread>         workers_;

public:
    explicit Scheduler(int nWorkers) {
        for (int i = 0; i < nWorkers; ++i)
            workers_.emplace_back([this]{ loop(); });
    }

    void schedule(Task t) {
        { std::lock_guard<std::mutex> l(mu_); pq_.push(std::move(t)); }
        cv_.notify_one();
    }

    void cancel(long long id) {
        std::lock_guard<std::mutex> l(mu_);
        cancelled_.insert(id);      // lazy cancel: skipped when popped
    }

    void shutdown() {
        { std::lock_guard<std::mutex> l(mu_); stop_ = true; }
        cv_.notify_all();
        for (auto& w : workers_) w.join();
    }

private:
    void loop() {
        while (true) {
            std::unique_lock<std::mutex> lock(mu_);

            // wait until: shutdown, OR a task exists
            cv_.wait(lock, [this]{ return stop_ || !pq_.empty(); });
            if (stop_) return;

            auto now = Clock::now();
            if (pq_.top().runAt > now) {
                // earliest task is in the future → sleep until then,
                // but wake early if something sooner is scheduled
                cv_.wait_until(lock, pq_.top().runAt);
                continue;
            }

            Task t = pq_.top(); pq_.pop();
            if (cancelled_.count(t.id)) { cancelled_.erase(t.id); continue; }
            lock.unlock();                       // ← run OUTSIDE the lock

            try {
                t.fn();
            } catch (...) {
                if (++t.attempts < t.maxAttempts) {
                    t.runAt = Clock::now() +
                        std::chrono::seconds(1 << t.attempts);  // 2s, 4s, 8s
                    schedule(std::move(t));
                }
            }
        }
    }
};
🛡️ LLD Blueprint

Three decisions worth defending, because interviewers probe all three:

  • Run the task outside the lock. If you hold the mutex while executing, a slow task blocks every other worker and the scheduler becomes single-threaded. This is the most common bug in this problem.
  • wait_until, not sleep_for. Sleeping blindly means a newly-scheduled sooner task waits for your sleep to end. A condition variable wakes early when something changes.
  • Lazy cancellation. Removing from the middle of a heap is O(n). Marking the ID and skipping it on pop is O(1), and the only cost is a cancelled task briefly occupying heap space.

3 · Parking lot — resource allocation

Parking lot with strategy pattern — TypeScript 
// ---------- models ----------
enum VehicleType { MOTORCYCLE, CAR, TRUCK }

abstract class Vehicle {
  constructor(public plate: string, public type: VehicleType) {}
}
class Car        extends Vehicle { constructor(p: string){ super(p, VehicleType.CAR); } }
class Motorcycle extends Vehicle { constructor(p: string){ super(p, VehicleType.MOTORCYCLE); } }

class Slot {
  occupiedBy: string | null = null;
  constructor(public id: string, public size: VehicleType) {}
  get isFree() { return this.occupiedBy === null; }
  fits(v: Vehicle) { return this.size >= v.type; }   // bigger slot fits smaller vehicle
}

// ---------- strategy: pricing can change without touching the lot ----------
interface PricingStrategy { price(v: Vehicle, hours: number): number; }

class HourlyPricing implements PricingStrategy {
  private rates = { [VehicleType.MOTORCYCLE]: 10, [VehicleType.CAR]: 20, [VehicleType.TRUCK]: 40 };
  price(v: Vehicle, hours: number) { return this.rates[v.type] * Math.ceil(hours); }
}

class FlatThenHourly implements PricingStrategy {
  price(v: Vehicle, hours: number) {
    return hours <= 1 ? 30 : 30 + (Math.ceil(hours) - 1) * 20;
  }
}

// ---------- service ----------
class ParkingLot {
  private slots = new Map<string, Slot>();
  private tickets = new Map<string, { slotId: string; in: number }>();
  private freeBySize = new Map<VehicleType, Slot[]>();   // O(1) allocation

  constructor(private pricing: PricingStrategy) {}

  park(v: Vehicle): string {
    // find the SMALLEST slot that fits — don't waste a truck bay on a bike
    for (let size = v.type; size <= VehicleType.TRUCK; size++) {
      const pool = this.freeBySize.get(size);
      if (pool?.length) {
        const slot = pool.pop()!;             // O(1)
        slot.occupiedBy = v.plate;
        const ticket = `T-${Date.now()}-${v.plate}`;
        this.tickets.set(ticket, { slotId: slot.id, in: Date.now() });
        return ticket;
      }
    }
    throw new Error('Lot full');
  }

  unpark(ticket: string): number {
    const t = this.tickets.get(ticket);
    if (!t) throw new Error('Invalid ticket');
    this.tickets.delete(ticket);              // delete FIRST → ticket can't be reused

    const slot = this.slots.get(t.slotId)!;
    const vehicleType = slot.size;
    slot.occupiedBy = null;
    this.freeBySize.get(slot.size)!.push(slot);

    const hours = (Date.now() - t.in) / 3_600_000;
    return this.pricing.price({ plate: '', type: vehicleType } as Vehicle, hours);
  }
}
💡 Implementation Pattern

Two things that earn marks here beyond "it works." Free-list per size makes allocation O(1) instead of scanning every slot — and it's the difference between a toy and something that handles 10,000 slots. Strategy interface for pricing means weekend rates, EV surcharges or a flat-fee model are a new class, not an edit to ParkingLot. When the interviewer says "now add dynamic pricing" — and they will — you add a class instead of rewriting.

4 · Chess engine — command pattern with undo

Command pattern + server-authoritative validation — TypeScript 
interface Command {
  execute(board: Board): void;
  undo(board: Board): void;
}

class MoveCommand implements Command {
  private captured: Piece | null = null;      // remembered so undo can restore it

  constructor(private from: Square, private to: Square) {}

  execute(board: Board) {
    this.captured = board.at(this.to);         // save BEFORE overwriting
    board.set(this.to, board.at(this.from));
    board.set(this.from, null);
  }

  undo(board: Board) {
    board.set(this.from, board.at(this.to));
    board.set(this.to, this.captured);         // restore, including null
  }
}

class Game {
  private history: Command[] = [];
  private redoStack: Command[] = [];

  constructor(private board: Board, private state = 'IN_PROGRESS') {}

  // SERVER-SIDE gate. The client's board is a rendering, never the truth.
  tryMove(playerId: string, from: Square, to: Square): boolean {
    if (this.state !== 'IN_PROGRESS')            return false;  // 1. right phase?
    if (this.colourOf(playerId) === null)        return false;  // 2. player, not spectator?
    if (this.board.turn !== this.colourOf(playerId)) return false; // 3. their turn?
    if (!this.board.isLegal(from, to))           return false;  // 4. legal in OUR board?

    const cmd = new MoveCommand(from, to);
    cmd.execute(this.board);
    this.history.push(cmd);
    this.redoStack.length = 0;      // a new move invalidates redo
    return true;
  }

  undo() {
    const cmd = this.history.pop();
    if (!cmd) return;
    cmd.undo(this.board);
    this.redoStack.push(cmd);
  }

  redo() {
    const cmd = this.redoStack.pop();
    if (!cmd) return;
    cmd.execute(this.board);
    this.history.push(cmd);
  }
}
🛡️ LLD Blueprint

Why the command pattern rather than just storing board snapshots: a snapshot per move is 64 squares copied every time; a command is two squares plus a captured piece. For a 100-move game that's a meaningful difference, and undo/redo falls out for free instead of being bolted on.

And the ordering of the four checks matters — cheapest first. Phase and role are field comparisons; legality is the expensive one, so it runs last, after the cheap rejections have already filtered out most bad input. Same principle as short-circuit evaluation.

Flash sale / inventory reservation

DDL + the one query that prevents negative stock 
CREATE TABLE products (
  id     bigserial PRIMARY KEY,
  sku    text UNIQUE NOT NULL,
  name   text NOT NULL
);

CREATE TABLE inventory_pools (
  product_id bigint PRIMARY KEY REFERENCES products(id),
  total      int NOT NULL CHECK (total >= 0),
  reserved   int NOT NULL DEFAULT 0 CHECK (reserved >= 0),
  version    int NOT NULL DEFAULT 0,
  CHECK (reserved <= total)          -- the invariant, enforced by the DB itself
);

CREATE TABLE reservations (
  id              bigserial PRIMARY KEY,
  product_id      bigint NOT NULL REFERENCES products(id),
  user_id         bigint NOT NULL,
  qty             int NOT NULL CHECK (qty > 0),
  status          text NOT NULL DEFAULT 'HELD',   -- HELD | CONFIRMED | EXPIRED
  idempotency_key text UNIQUE NOT NULL,           -- ← stops double-submit
  expires_at      timestamptz NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON reservations (expires_at) WHERE status = 'HELD';   -- for the sweeper

CREATE TABLE audit_ledger (
  id         bigserial PRIMARY KEY,
  product_id bigint NOT NULL,
  delta      int    NOT NULL,     -- +ve released, -ve reserved
  reason     text   NOT NULL,
  at         timestamptz NOT NULL DEFAULT now()
);

-- ============ THE ATOMIC RESERVATION ============
-- One statement. No SELECT-then-UPDATE. No lock held by the app.
UPDATE inventory_pools
SET reserved = reserved + $2,
    version  = version + 1
WHERE product_id = $1
  AND total - reserved >= $2      -- ← the guard: only if stock actually remains
RETURNING total - reserved AS remaining;

-- 1 row returned → reserved successfully
-- 0 rows         → sold out. Not an error, just a fact. Return 409.
💡 Implementation Pattern

The whole trick is putting the business rule in the WHERE clause. The naive version — SELECT stock, check it in application code, then UPDATE — has a gap between the read and the write where a thousand other requests can slip through. All of them read "10 left", all decide it's fine, all decrement, and you've oversold.

UPDATE ... WHERE total - reserved >= qty is a single atomic statement. The database serializes concurrent updates to the same row, so each one re-evaluates the condition against the current value. Overselling is not merely unlikely — it's impossible. And the CHECK (reserved <= total) constraint is a second net: even a buggy future query cannot violate the invariant.

Time-series telemetry (SahYatri pattern)

Partitioned table + BRIN + rollup 
CREATE TABLE telemetry (
  bus_id       int         NOT NULL,
  recorded_at  timestamptz NOT NULL,     -- when it HAPPENED (on the device)
  ingested_at  timestamptz NOT NULL DEFAULT now(),  -- when we RECEIVED it
  occupancy    int         NOT NULL,
  lat          double precision,
  lng          double precision,
  PRIMARY KEY (bus_id, recorded_at)      -- doubles as the idempotency key
) PARTITION BY RANGE (recorded_at);

CREATE TABLE telemetry_2026_08 PARTITION OF telemetry
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

-- BRIN: kilobytes, not gigabytes. Works because inserts arrive in time order,
-- so the table is ALREADY physically sorted by recorded_at.
CREATE INDEX ON telemetry_2026_08 USING BRIN (recorded_at);

-- Idempotent batch insert — a retried burst cannot double-count
INSERT INTO telemetry (bus_id, recorded_at, occupancy, lat, lng)
SELECT * FROM unnest($1::int[], $2::timestamptz[], $3::int[], $4::float[], $5::float[])
ON CONFLICT (bus_id, recorded_at) DO NOTHING;

-- Hourly rollup, safe to re-run (late data recomputes the bucket)
INSERT INTO telemetry_hourly (bus_id, hour, avg_occupancy, max_occupancy, samples)
SELECT bus_id, date_trunc('hour', recorded_at), avg(occupancy), max(occupancy), count(*)
FROM telemetry
WHERE recorded_at >= $1 AND recorded_at < $2
GROUP BY 1, 2
ON CONFLICT (bus_id, hour) DO UPDATE
  SET avg_occupancy = EXCLUDED.avg_occupancy,
      max_occupancy = EXCLUDED.max_occupancy,
      samples       = EXCLUDED.samples;
💻 Why partitioning pays three times

Query pruning — a last-7-days query skips every other partition without reading it. Small hot index — writes only touch the current partition, so the index that must stay in RAM is one month's worth, not five years'. Instant retention — deleting old data becomes DROP TABLE, which is metadata-only, instead of a DELETE that writes dead tuples and then makes VACUUM clean them up for hours.

  SET body = $3, version = version + 1, updated_at = now()

🚨 Multi-tenancy Trap

Soft delete silently breaks every query you forget it in. Once deleted_at exists, every single read must include AND deleted_at IS NULL — and the one that forgets shows deleted specs to users, or worse, counts them in a billing query. Same class of bug as a missing company_id filter.

The structural fixes: a database view (active_specs) that bakes both filters in and is what application code actually queries; or a repository layer that injects them. And note the UNIQUE problem — a unique constraint on (company_id, title) will block re-creating a spec with a deleted one's title. Use a partial unique index: UNIQUE (company_id, title) WHERE deleted_at IS NULL.

WITH RECURSIVE tree AS (
  SELECT id, parent_id, name, 1 AS depth
  FROM categories
  WHERE parent_id IS NULL                 -- anchor: the roots

  UNION ALL

  SELECT c.id, c.parent_id, c.name, t.depth + 1

💡 Implementation Pattern

The mental model for window functions: they add a column computed across a group of rows, without collapsing those rows. That's exactly what separates them from GROUP BY, which collapses. If a question sounds like "for each X, the top N" or "compare each row to the previous one", it's a window function — and the ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) pattern in query 1 solves an enormous share of them.

05 Bottlenecks & capacity sizing

Connection pool exhaustion

PostgreSQL forks a process per connection — several MB each plus scheduling cost. So connections are scarce, and more is not better.

SymptomReal causeFix
Timeouts, but DB looks idleEveryone queued at the poolFind the slow query holding connections
Throughput drops as pool growsToo many processes thrashingShrink the pool
Serverless kills the DBEach invocation opens its own connectionPgBouncer transaction mode
💡 Implementation Pattern

The counter-intuitive result worth stating: a smaller pool is often faster. A 4-core machine can genuinely execute about 4 queries at once; 100 connections just means 100 processes fighting over 4 cores with context-switch overhead. A common starting point is (cores × 2) + effective_spindles — so single digits, not hundreds.

PgBouncer in transaction mode is what breaks the linkage: thousands of application connections multiplex onto a few real ones, because a connection is only borrowed for the duration of a transaction rather than the lifetime of a client. This is mandatory for serverless.

Hot row contention

Every request updates the same row — a global counter, a popular product's stock. Even with correct locking, they serialize: 1,000 requests become 1,000 sequential updates on one row.

❌ HOT ROW ✅ SHARDED COUNTER (write to a random shard) 1000 req/s 1000 req/s │ ├──► counter_shard_0 (100/s) ▼ ├──► counter_shard_1 (100/s) ┌─────────┐ all queue ├──► ... │ row id=1│ behind each other └──► counter_shard_9 (100/s) └─────────┘ ~500/s ceiling read = SUM(all shards) 10x the write throughput
Sharded counter 
CREATE TABLE counter_shards (
  name     text NOT NULL,
  shard_id int  NOT NULL,
  value    bigint NOT NULL DEFAULT 0,
  PRIMARY KEY (name, shard_id)
);

-- write: pick a random shard → contention drops by the shard count
UPDATE counter_shards SET value = value + 1
WHERE name = 'page_views' AND shard_id = floor(random() * 10);

-- read: sum them (slightly more expensive, and that's the trade)
SELECT sum(value) FROM counter_shards WHERE name = 'page_views';

The trade in one line: writes get N× cheaper, reads get N× more expensive. Correct when writes dominate — view counts, likes, metrics. Wrong when you read constantly and write rarely.

Cache stampede (thundering herd)

A popular cache key expires. In the same millisecond, 5,000 requests all miss, and all 5,000 hit the database with the same expensive query. The database falls over — because the cache was working well.

FixHowTrade-off
Mutex / single-flightFirst miss takes a lock and recomputes; others wait or serve staleSimple, but the waiters block briefly
Probabilistic early expiry (XFetch)As TTL approaches, each request has a rising chance of refreshing earlyNo lock, no stampede; slightly more recomputes
Stale-while-revalidateServe the stale value instantly, refresh in the backgroundBest latency; users briefly see old data
Single-flight cache in TypeScript 
const inFlight = new Map<string, Promise<any>>();

async function getCached<T>(key: string, ttl: number, compute: () => Promise<T>): Promise<T> {
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);

  // If another request is ALREADY computing this key, wait for it
  // instead of starting a second identical query.
  if (inFlight.has(key)) return inFlight.get(key)!;

  const p = (async () => {
    try {
      const value = await compute();
      await redis.set(key, JSON.stringify(value), 'EX', ttl);
      return value;
    } finally {
      inFlight.delete(key);
    }
  })();

  inFlight.set(key, p);
  return p;
}
// Note: this dedupes per PROCESS. Across many servers you need a
// distributed lock (SET NX) to get the same guarantee cluster-wide.
🚨 Thundering Herd Trap

Never give many keys the same TTL. Warming a cache at deploy time with EX 3600 on everything means they all expire in the same second an hour later — a self-inflicted stampede, on a timer, in production. Add random jitter: EX 3600 + random(0..300). Same principle as retry jitter, and the same failure if you skip it.

Capacity estimation — do the arithmetic out loud

Worked example: SahYatri at 10,000 buses 
ASSUMPTIONS (state them; interviewers care about the method, not the number)
  buses            = 10,000
  reading interval = 3 s
  row size         ≈ 60 bytes (ids, timestamp, int, 2 floats + overhead)

WRITE THROUGHPUT
  10,000 / 3 s              ≈ 3,333 writes/s
  peak (2x)                 ≈ 6,700 writes/s
  → single-row inserts: too many round trips.
  → batch 100 rows/statement → ~67 statements/s. Comfortable.

STORAGE
  3,333 rows/s x 86,400 s   ≈ 288M rows/day
  288M x 60 bytes           ≈ 17 GB/day raw
  x 30 days                 ≈ 520 GB/month
  → raw retention 7 days (~120 GB hot) + hourly rollups forever.
  → rollup: 10,000 buses x 24 h = 240k rows/day ≈ 15 MB/day. Negligible.

READ / RAM
  dashboard: ~50 concurrent users, ~2 queries/s each ≈ 100 QPS
  working set = last 24h of the current partition ≈ 17 GB
  → won't fit in typical RAM. Serve dashboards from ROLLUPS, not raw.
  → this is WHY downsampling exists — it's a memory decision, not tidiness.

BANDWIDTH
  6,700 writes/s x 200 bytes JSON ≈ 1.3 MB/s ≈ 11 Mbps. Trivial.

CONCLUSION
  Bottleneck is DISK GROWTH and the read working set, not CPU or network.
  Levers, in order: batch inserts → partition → rollups → tiered retention.
🛡️ LLD Blueprint

The point of capacity estimation is never the number — it's identifying which resource runs out first. Say the assumptions out loud, use round numbers, and finish with a named bottleneck. "Writes are easy, disk growth is the problem, so retention policy is the real design decision" is a complete answer. Numbers to keep handy: a day is ~86,400 s (call it 100k), a month is ~2.6M s, and 1M rows × 100 bytes = 100 MB.

CREATE TABLE seats (
  id          bigserial PRIMARY KEY,
  show_id     bigint NOT NULL,
  seat_label  text   NOT NULL,
  status      text   NOT NULL DEFAULT 'FREE',   -- FREE | HELD | BOOKED
  held_by     bigint,
  held_until  timestamptz,
  version     int    NOT NULL DEFAULT 0,
  UNIQUE (show_id, seat_label)
);
CREATE INDEX ON seats (show_id) WHERE status = 'FREE';        -- pick-any queries
CREATE INDEX ON seats (held_until) WHERE status = 'HELD';     -- the sweeper

-- ---------- HOLD a specific seat ----------
BEGIN;
  INSERT INTO idempotency_keys (key, request_hash) VALUES ($1, $2)
  ON CONFLICT (key) DO NOTHING;          -- 0 rows → replay, return stored result

  UPDATE seats
  SET status = 'HELD', held_by = $3,
      held_until = now() + interval '10 minutes',
      version = version + 1
  WHERE id = $4 AND status = 'FREE';     -- ← the guard. No SELECT-then-UPDATE.
  -- 0 rows → someone got it first. 409 Conflict.
COMMIT;

-- ---------- HOLD any N seats (pick-any) ----------
BEGIN;
  SELECT id FROM seats
  WHERE show_id = $1 AND status = 'FREE'
  ORDER BY id
  LIMIT $2
  FOR UPDATE SKIP LOCKED;                -- concurrent users get DIFFERENT seats
  UPDATE seats SET status='HELD', held_by=$3, held_until=now()+interval '10 min'
  WHERE id = ANY($4);
COMMIT;

-- ---------- CONFIRM ----------
UPDATE seats SET status = 'BOOKED', held_until = NULL
WHERE id = ANY($1) AND status = 'HELD' AND held_by = $2 AND held_until > now();
-- row count must equal the number of seats, else the hold expired → 410 Gone

-- ---------- SWEEPER (cron, every 30s) ----------
UPDATE seats SET status='FREE', held_by=NULL, held_until=NULL
WHERE status = 'HELD' AND held_until < now();
🛡️ LLD Blueprint — what to say

"Two-phase booking with a TTL hold." Holding is separate from paying, because payment takes minutes and you cannot keep a database lock open across a payment gateway call.

  • Specific seat → conditional UPDATE ... WHERE status='FREE'. Atomic, no lock held by the app, loser gets 409.
  • Any N seats → FOR UPDATE SKIP LOCKED, so concurrent users are handed different seats instead of queueing for the same one.
  • Idempotency key → a double-tapped "Book" button doesn't create two holds.
  • Expiry → a sweeper frees abandoned holds. Also check held_until > now() at confirm time, so a hold that expired one second ago can't sneak through between sweeps.

The failure mode to name unprompted: if the sweeper dies, seats stay held forever and the show looks sold out. So confirm-time validation is the real guarantee and the sweeper is just cleanup — never let correctness depend on a cron job running.

2 · In-memory key-value store with TTL + LRU

O(1) get/put with LRU eviction and TTL — TypeScript 
// JS Map preserves insertion order, so it doubles as the recency list.
// (In C++ or Java: HashMap<K, ListNode> + a doubly linked list.)

interface Entry<V> { value: V; expiresAt: number | null; }

class LRUCacheTTL<K, V> {
  private map = new Map<K, Entry<V>>();

  constructor(private capacity: number) {}

  get(key: K): V | undefined {
    const e = this.map.get(key);
    if (!e) return undefined;

    // LAZY EXPIRY — check on read, not with a timer
    if (e.expiresAt !== null && Date.now() > e.expiresAt) {
      this.map.delete(key);
      return undefined;
    }

    // touch: delete + re-insert moves it to the most-recent end
    this.map.delete(key);
    this.map.set(key, e);
    return e.value;
  }

  put(key: K, value: V, ttlMs?: number): void {
    if (this.map.has(key)) this.map.delete(key);
    else if (this.map.size >= this.capacity) {
      const oldest = this.map.keys().next().value;   // first = least recent
      this.map.delete(oldest);
    }
    this.map.set(key, {
      value,
      expiresAt: ttlMs ? Date.now() + ttlMs : null,
    });
  }

  // ACTIVE expiry — sample a few keys periodically so memory is reclaimed
  // even for keys nobody reads again. This is roughly what Redis does.
  sweep(sampleSize = 20): void {
    let checked = 0;
    for (const [k, e] of this.map) {
      if (checked++ >= sampleSize) break;
      if (e.expiresAt !== null && Date.now() > e.expiresAt) this.map.delete(k);
    }
  }
}
💻 Machine Coding — the two things they're checking

Is everything O(1)? Hash map for lookup, ordered structure for recency. Scanning to find the least-recently-used is the mistake — insertion-ordered Map (or hashmap + doubly linked list) makes eviction O(1).

Lazy vs active expiry, and why you need both. Lazy alone (check on read) is O(1) and free, but a key nobody ever reads again occupies memory forever — a leak. Active alone (scan everything) is O(n) and expensive. Redis samples ~20 random keys periodically, which is the pragmatic middle: bounded cost, memory still gets reclaimed. Saying "both, because lazy alone leaks" is the answer.

  user_id    bigint PRIMARY KEY,
  score      bigint NOT NULL DEFAULT 0,
  updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON scores (score DESC);

🛡️ LLD Blueprint — what to say

"Redis for ranking, Postgres for truth." Ranking a million players in SQL means ORDER BY score DESC over the whole table — fine for the top 10 with an index, but "what's my rank?" requires counting everyone above me, which is a full scan. A sorted set answers it in O(log N) because rank is maintained as part of the structure.

Redis is a cache, never the record. If Redis is lost you must be able to rebuild, so every score change is also written durably. Write to Postgres first, then update Redis — if the Redis write fails you have stale ranks (recoverable) rather than lost scores (not).

Ties need a deterministic rule or ranks flicker between equal scores. The standard trick is encoding the timestamp into the score's fractional part so earlier achievers rank higher.

    }
  }
  res.json({ accepted, conflicts, syncedAt: new Date().toISOString() });
});

🚨 Sync Trap

Never use client timestamps for last-write-wins. Device clocks are wrong, sometimes by hours, and a user can change theirs. A phone set five minutes fast wins every conflict forever. Use server-assigned timestamps or version counters.

And deletes must be explicit. If a deleted row simply disappears from the server's response, the client cannot distinguish "deleted" from "unchanged" and will keep it forever. You need tombstones — soft-deleted rows that still get synced — and a retention policy so tombstones don't accumulate indefinitely.

💡 Implementation Pattern

The honest simplification for StudySync, and it's a good thing to volunteer: the app is read-only offline. Students view a timetable that only admins edit, so there are no client-side writes and therefore no conflicts to resolve at all. Pull-only sync with a cached last-good response is the entire design.

That's the strongest version of this answer — "I recognised the write path didn't exist, so I didn't build a conflict engine nobody needed. Here's what I'd add if students could edit." Knowing which half of a hard problem you're allowed to skip is worth more than implementing all of it.
