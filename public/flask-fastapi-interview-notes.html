Flask Fundamentals

Covered at the depth an interviewer would actually probe for a candidate who shipped a Flask REST API — not full docs.

Routing

Routes are registered with @app.route(), which maps a URL pattern + HTTP method(s) to a view function. Flask uses Werkzeug's URL routing under the hood (a trie-based matcher, not simple string comparison).

@app.route("/get_bot_move", methods=["POST"])
def get_bot_move():
    ...

# variable rule + type converter
@app.route("/user/<int:user_id>")
def get_user(user_id):
    ...
  • methods=[...] defaults to GET only — POST/PUT/DELETE must be declared explicitly.
  • url_for('view_name') generates URLs from the function name instead of hardcoding paths — decouples routes from templates/redirects.
  • Route matching is most-specific-first; static segments beat variable segments.

Blueprints

Blueprints let you split a large app into modular components (e.g. auth, api, admin) that get registered onto the main app — each with its own routes, templates, and static folder, optionally under a URL prefix.

auth_bp = Blueprint("auth", __name__, url_prefix="/auth")

@auth_bp.route("/login")
def login(): ...

app.register_blueprint(auth_bp)
⚠ Honesty Check
Chessify's Flask backend is a single-file main.py with one route (/get_bot_move) — it does not use blueprints. If asked "did you use blueprints in your project," the honest answer is no — the app was small enough (one endpoint) that it didn't need the modularity. Know the concept, don't overclaim usage.

Request / Response Lifecycle

1WSGI server (dev: Flask's built-in server / prod: Gunicorn) receives the HTTP request
2Flask pushes a request context — makes the global request object available for that thread
3URL router dispatches to the matching view function
4View reads request.json / request.args / request.form, does work, returns a value
5Flask converts the return value into a Response object (dict → JSON via jsonify, or use make_response directly)
6Request context torn down; response sent back through WSGI

Key point for interviews: Flask's dev server (app.run(debug=True)) is single-threaded and synchronous by default — it handles one request at a time unless threaded=True is passed. Production deployments use Gunicorn with multiple worker processes to get concurrency (this is exactly what Chessify's render.yaml does — see Chessify section).

Jinja2 Templating — Overview

Flask's default templating engine for server-rendered HTML: render_template("page.html", data=x), with {{ }} for expressions, {% %} for control flow, and template inheritance via {% extends %} / {% block %}.

⚠ Not used in Chessify's web app
Chessify's Flask backend is a pure JSON REST API — it never calls render_template. All UI is rendered client-side by the Next.js frontend. Know Jinja2 conceptually (it's a very likely quiz item since it's "the" Flask-specific feature), but don't claim you used it in the web app — say plainly: "this backend is headless, Jinja2 wasn't relevant; the frontend is a separate Next.js app." (Fun fact for yourself: the earlier standalone Pygame version of this bot didn't use Flask at all — see Testing section.)

FastAPI Fundamentals

You didn't use FastAPI in Chessify, but comparison questions are near-guaranteed — know these four pillars cold.

Async Support

FastAPI is built on Starlette and runs on an ASGI server (Uvicorn), so routes can be declared async def and use await for non-blocking I/O (DB calls, HTTP requests, file I/O) — all served on a single event loop without spawning OS threads per request.

@app.get("/items/{item_id}")
async def read_item(item_id: int):
    result = await db.fetch(item_id)
    return result

Regular def routes are still supported and get automatically run in a threadpool — so FastAPI doesn't force async everywhere, but it's the headline feature.

Pydantic Validation

Request/response schemas are declared as Python classes (type hints), and FastAPI validates, coerces, and auto-documents them — no manual if "x" not in data checks.

class MoveRequest(BaseModel):
    fen: str
    depth: int = 3

@app.post("/get_bot_move")
def get_bot_move(req: MoveRequest):
    # req.fen is guaranteed to be a str, req.depth an int
    # invalid body -> automatic 422 with detailed error, no code needed
    ...
🔍 Direct contrast with your code
Chessify's Flask endpoint validates manually: if not data or "fen" not in data: return jsonify({"error":...}), 400. In FastAPI, that whole block disappears — a malformed body is rejected automatically before your function even runs. This is the single cleanest "why FastAPI over Flask" talking point.

Automatic OpenAPI Docs

Because routes are typed with Pydantic models, FastAPI auto-generates an OpenAPI 3.0 schema and serves interactive docs for free at /docs (Swagger UI) and /redoc (ReDoc) — zero extra config. Flask needs an extension (e.g. flask-smorest, flasgger) to get the same thing.

Dependency Injection

Depends() lets you declare reusable, composable dependencies (DB sessions, auth checks, shared query params) that FastAPI resolves and injects automatically — including support for nested dependencies and caching per-request.

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@app.get("/games/{id}")
def get_game(id: int, db: Session = Depends(get_db)):
    ...

Mental model: DI in FastAPI is function-parameter based, not a decorator/container pattern like Spring — much lighter weight.

🔍 The nuance interviewers actually want
Async doesn't make CPU-bound work faster — it makes I/O-bound, high-concurrency work faster by not blocking the event loop while waiting on network/disk. A single Minimax search or a Stockfish subprocess call is CPU/subprocess-bound, not I/O-bound — so async buys you nothing there unless you're serving many concurrent users and want to avoid one slow search blocking others.

When to choose which

  • Choose Flask — quick prototypes, CPU-bound compute services, teams that want sync simplicity, projects needing Jinja2 server-rendered pages, huge existing extension ecosystem (Flask-Login, Flask-Admin, etc).
  • Choose FastAPI — APIs that fan out to many DB/network calls concurrently, teams that want free schema validation + auto docs, microservices talking to other async services, projects that benefit from Python type hints end-to-end.

from bot.minimax import find_best_move

@app.route("/get_bot_move", methods=["POST"])
def get_bot_move():
    data = request.json
    if not data or "fen" not in data:
        return jsonify({"error": "FEN not provided"}), 400

    fen = data["fen"]
    board = chess.Board(fen)

    move = None
    if board.fullmove_number <= 10:
        move = book.get_move(board)
    if move is None:
        move = get_stockfish_move(board, time_limit=0.5, elo=1800)
    if move is None:
        move = find_best_move(board, depth=3)

    board.push(move)
    return jsonify({"move": move.uci(), "new_fen": board.fen()})

Inside Flask itself, the engine priority is opening book (first 10 full moves) → Stockfish (ELO 1800, primary engine) → custom Minimax (depth 3, fallback only if Stockfish is unavailable). Your custom Minimax/alpha-beta engine is not the main move generator — it's a resilience fallback within Flask. How Minimax is wired in

Chess-AI/bot/minimax.py 
transposition_table = {}

def minimax(board, depth, alpha, beta, maximizing):
    key = board.fen()
    if key in transposition_table and transposition_table[key]["depth"] >= depth:
        return transposition_table[key]["value"]

    if depth == 0 or board.is_game_over():
        eval_score = quiescence(board, alpha, beta, maximizing)
        transposition_table[key] = {"depth": depth, "value": eval_score}
        return eval_score

    best_value = float('-inf') if maximizing else float('inf')
    for move in board.legal_moves:
        board.push(move)
        value = minimax(board, depth - 1, alpha, beta, not maximizing)
        board.pop()

        if maximizing:
            best_value = max(best_value, value)
            alpha = max(alpha, best_value)
        else:
            best_value = min(best_value, value)
            beta = min(beta, best_value)

        if beta <= alpha:
            break   # <- the alpha-beta prune

    transposition_table[key] = {"depth": depth, "value": best_value}
    return best_value

Three things layered on top of textbook Minimax here, worth naming proactively:

  • Transposition table — caches evaluated positions by FEN so transposing move orders that reach the same board don't get re-searched.
  • Quiescence search — at depth 0, instead of evaluating the raw static position, quiescence() keeps searching capture sequences until the position is "quiet." This avoids the classic horizon effect (e.g. stopping mid-recapture and misjudging material).
  • find_best_move() (the entry point called from main.py) does the top-level move loop itself and calls minimax() one ply down for each candidate move — it doesn't just call minimax on the root.
Chess-AI/bot/evaluation.py 
piece_values = {
    chess.PAWN: 100, chess.KNIGHT: 320, chess.BISHOP: 330,
    chess.ROOK: 500, chess.QUEEN: 900, chess.KING: 20000
}

def evaluate_board(board):
    if board.is_checkmate():
        return -99999 if board.turn else 99999
    if board.is_stalemate() or board.is_insufficient_material():
        return 0
    score = 0
    for square, piece in board.piece_map().items():
        value = piece_values.get(piece.piece_type, 0)
        score += value if piece.color == chess.WHITE else -value
    return score

# builds a { fen : move } dict for instant O(1) opening lookups
class OpeningBook:
    def __init__(self, pgn_path="assets/openings.pgn"):
        self.moves = {}
        with open(pgn_path) as f:
            while True:
                game = chess.pgn.read_game(f)
                if game is None: break
                board = game.board()
                for move in game.mainline_moves():
                    self.moves.setdefault(board.fen(), move)
                    board.push(move)

The actual proxy code

Frontend/pages/api/chess.ts 
export default async function handler(req, res) {
  const { fen, depth } = req.body;
  const flaskUrl = process.env.NEXT_PUBLIC_FLASK_URL || "http://localhost:5000";

  try {
    // 6-second timeout to avoid hanging on a sleeping free-tier instance
    const controller = new AbortController();
    const timeoutId = setTimeout(() => controller.abort(), 6000);

    const flaskRes = await fetch(`${flaskUrl}/get_bot_move`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ fen }),
      signal: controller.signal,
    });
    clearTimeout(timeoutId);

    if (flaskRes.ok) {
      const data = await flaskRes.json();
      return res.status(200).json(data);   // ✅ Flask move used
    }
    throw new Error(`Flask backend returned status ${flaskRes.status}`);
  } catch (error) {
    // Flask failed or timed out -> fall back to the public API
    const fallbackRes = await fetch("https://chess-api.com/v1", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ fen, depth, maxThinkingTime: 100 }),
    });
    const data = await fallbackRes.json();
    return res.status(200).json(data);   // 🟡 public API move used
  }
}

Why this specific shape

  • CORS avoidance: the browser only ever talks to its own origin (/api/chess); the server-to-server call to Flask (or the fallback API) happens outside the browser, so no cross-origin headers are needed on Flask itself for this path — flask-cors is still there for direct/local testing, but production traffic never needs the browser to cross origins.
  • Hides infra details: the deployed Flask URL is never visible in browser dev tools — only /api/chess is.
  • Cold-start resilience: Render's free tier spins down idle services; a sleeping Flask instance can take tens of seconds to wake. The 6-second timeout means the user gets a fast fallback move instead of a frozen UI.
  • Defense in depth: even if both backends are unreachable, the app still produces a legal move client-side rather than crashing.
🎯 How to say this in an interview
"My Flask backend with the custom Minimax engine is the primary path in production — the frontend calls it first through a Next.js proxy route. I added a public Stockfish API as a secondary fallback with a 6-second timeout to handle Render free-tier cold starts, and a third, fully client-side fallback using chess.js so the app never hard-fails even if both backends are down. It's a defense-in-depth design, not an abandonment of the custom engine."

Minimax + Alpha-Beta Pruning — Conceptually

This is a DSA talking point wearing a web-project costume. Expect it to be quizzed independently of Flask.

Minimax

Two-player, zero-sum, perfect-information game search. One player (MAX) tries to maximize the evaluation score, the other (MIN) tries to minimize it. The algorithm recursively explores the game tree to a fixed depth, and each node's value bubbles up as the best choice available to whichever player is "to move" at that node.

  • Time complexity: O(bd) — b = branching factor (~35 average legal moves in chess), d = search depth.
  • Space complexity: O(bd) with depth-first search (only one path held in memory at a time).

Alpha-Beta Pruning

An optimization on top of Minimax that skips branches which cannot possibly affect the final decision. It tracks two bounds while searching:

  • alpha — the best (highest) value MAX is guaranteed so far.
  • beta — the best (lowest) value MIN is guaranteed so far.

If at any point beta <= alpha, the current branch can never be chosen by either player under optimal play — so the rest of it is pruned (skipped) without evaluating it. With perfect move ordering, alpha-beta reduces the effective branching factor from b to roughly √b, i.e. worst case O(bd) becomes closer to O(bd/2) — the same depth search runs dramatically faster, or equivalently you can search roughly twice as deep in the same time budget.

Worked trace (depth 2, MAX at root)

MAX (root) ├── MIN A │ ├── A1 = 3 │ └── A2 = 5  → A returns min(3,5) = 3 │ root: alpha = 3 │ ├── MIN B │ ├── B1 = 2  → beta(B) drops to 2. Now beta(2) ≤ alpha(3) │ └── B2 = PRUNED  ← never evaluated, can't beat 3 anyway │ B returns 2 (root ignores it, 2 < alpha 3) │ └── MIN C ├── C1 = 9  → beta(C) = 9, still > alpha(3), keep going └── C2 = 1  → beta(C) drops to 1. 1 < alpha(3) → C returns 1 root = max(3, 2, 1) = 3 — chooses branch A. B2 was never computed.

Walk-through logic: as soon as MIN finds a child (B1 = 2) that's already worse for MAX than a value MAX can guarantee elsewhere (A = 3), MIN doesn't need to keep looking under B — MAX will never route through B regardless of what B2 is. That's the prune.

How this maps onto your code

In minimax.py, the swap between alpha = max(alpha, best_value) (maximizing branch) and beta = min(beta, best_value) (minimizing branch), followed by if beta <= alpha: break, is exactly this cutoff condition applied at every node of the recursion — not just the root.

Resume Tie-Ins

🎯 "Why did you build the AI backend in Python/Flask instead of Node/Next.js?"
  • Ecosystem: python-chess is the de facto standard library for board representation, legal move generation, and PGN/FEN parsing — nothing comparable exists in the Node ecosystem.
  • Binary integration: Stockfish is a C++ engine; Python's stockfish package gives clean subprocess-based control over it (set position, get best move, set ELO).
  • Isolation of blocking work: a Minimax search or a Stockfish subprocess call is synchronous, CPU-bound work. Running that inside a single-threaded Node process risks blocking the event loop for every other connected user — exactly the failure mode Node is worst at. Keeping it in a separate Flask process (behind Gunicorn workers) isolates that blocking work from the real-time layer entirely.
🎯 "Why Flask for the AI backend but Node for the real-time layer?"

You split the backend by workload shape, not by preference:

  • AI backend (Flask): CPU-bound, short-lived, stateless — one synchronous computation per request, full board state passed via FEN each time. Fits Flask's sync model plus Gunicorn workers well, and matches Python's chess tooling.
  • PvP backend (Node + Socket.IO): needs to hold many concurrent persistent WebSocket connections open (players + spectators per room) and broadcast low-latency events. That's an I/O-concurrency problem — exactly what Node's non-blocking event loop is built for, and Socket.IO's room abstraction maps cleanly onto "one room per game."

One-line answer to memorize: "I split the backend by workload shape — CPU-bound, stateless move computation went to Flask/Python for the chess engine ecosystem; high-concurrency, stateful real-time connections went to Node because its event loop is built for exactly that."

🎯 "Walk me through your resilience/fallback design"

This is genuinely your strongest system-design talking point in the whole project — a real four-tier degrade-gracefully chain (client fallback → Next.js proxy → Flask internal fallback chain → public API fallback). See the Production Chain section for the full breakdown and the exact code. Naming Render free-tier cold starts and the 6-second AbortController timeout as the concrete trigger shows you understand real infra constraints, not just the happy path.

🎯 Other angles worth having ready
  • Stateless API design — passing full FEN state per request rather than server-side sessions — is a clean, scalable REST decision worth naming explicitly.
  • DSA-to-production bridge — Minimax/alpha-beta with a transposition table and quiescence search is graduate-level game-tree search applied in a live, deployed system, not just a LeetCode exercise.
  • Standalone-first development — the Pygame harness proves you build and validate core logic in isolation before wrapping it in a web layer, which is a strong engineering habit to name unprompted.

Flagged Follow-Ups — Have Answers Ready

❓ "Why depth 3?" (or "why depth 2 in the GUI tool?")

Chess has an average branching factor of ~35. Depth 3 is ~35³ ≈ 42,875 worst-case nodes (far fewer in practice with alpha-beta pruning + the transposition table). This keeps the fallback engine's response time low enough for a web request/response cycle on a free-tier host. Minimax is a fallback engine both in Flask (behind Stockfish) and now behind the public API too — so it only needs to be "good enough and fast," not maximally strong. The GUI tool uses depth 2 for faster manual testing iteration; that's a separate, uncentralized constant worth acknowledging as a small code-quality gap.

❓ "How would you increase the engine's strength?"
  • Move ordering — search captures/checks first (e.g. MVV-LVA) so alpha-beta prunes more branches earlier; currently moves are iterated in whatever order python-chess generates them, unordered.
  • Better evaluation function — add piece-square tables, king safety, pawn structure, mobility; current eval is material-count only.
  • Iterative deepening — search depth 1, 2, 3... within a time budget instead of a fixed depth, so it always returns a legal move even under time pressure and gets progressively stronger.
  • Centralize the depth constant — one config value instead of hardcoded depth=3 in main.py and depth=2 in chess_gui.py.
  • Practically: since Stockfish is already primary, the highest-leverage move is tuning Stockfish's elo/time_limit parameters rather than the fallback engine.
❓ "How does Flask talk to your Node.js server?"

It doesn't — directly. Flask (AI moves) and Node (Socket.IO PvP) are two completely independent, stateless services with no backend-to-backend communication between them. Each is called separately: AI moves go browser → /api/chess (Next.js) → Flask (with its own fallback chain); PvP goes browser → Socket.IO directly to the Node server. Say this plainly — don't imply a direct integration that isn't in the code.

❓ "How does your Minimax algorithm handle the Horizon Effect?"

At depth 0, a purely static evaluation could stop mid-capture-sequence and misjudge material. quiescence() keeps searching capture moves recursively past the nominal depth limit until the position is "quiet," and only then returns an evaluation — avoiding a false read on a position that's about to change.

❓ "What is a transposition table and how did you implement it?"

Different move orders can reach the same board position (a transposition). minimax.py caches evaluated positions in a plain Python dict keyed by FEN string, storing the depth the value was computed at. Before searching a node, it checks whether that FEN is already cached at an equal or greater depth and returns the cached value instantly if so.

❓ "Why Socket.IO instead of raw WebSockets for PvP?" (bonus, outside Flask/FastAPI scope but likely to come up in the same breath)

Socket.IO gives room management, automatic reconnection, heartbeats, and HTTP long-polling fallback out of the box — all boilerplate you'd otherwise hand-roll with raw WebSockets. The room abstraction maps directly onto "one room per chess game" with players + spectators.
