The question behind most React interview questions: when does this component re-render, and what does it capture when it does? Stale closures, wasted renders, duplicate socket listeners and hydration mismatches are all answers to that one question. If you're stuck, start there.

01 React internals, Fiber & reconciliation

The Virtual DOM and its two assumptions

React builds a tree of plain objects describing the UI, diffs the new tree against the old, and applies the minimum set of real DOM changes. A general tree diff is O(n³), which is unusable — so React makes two assumptions to get to O(n):

  1. Different element types produce different trees. A <div> becoming a <span> means React tears down the whole subtree rather than diffing it — including all its state.
  2. Keys tell React which children are which across renders.
🚨 Interview Trap

Why key={index} corrupts stateful lists. Keys are React's identity mechanism. With index keys, deleting the first of three items means the item previously at index 1 now claims key 0 — so React thinks item 0 merely changed its props rather than being removed. DOM state that React doesn't control comes along for the ride: typed input values, focus, scroll position, CSS transitions. You delete the first row and the second row inherits the first row's typed text.

Index keys are fine only when the list is static and never reordered, filtered or spliced. Use a stable ID — and note that key is a message to the reconciler, not a prop your component can read.

Fiber: render vs commit

Fiber rewrote reconciliation as a linked list of units of work instead of a recursive tree walk — which is what makes it interruptible.

💡 Senior Insight

"Render must be pure" stops being an abstract rule once you know the render phase can be discarded and re-run. If you mutate a ref, fire an analytics event or push to an external store during render, that side effect happens once for work React threw away and again for the work it kept — a double-count with no error. This is also exactly what StrictMode's double-invoke in development is designed to surface: it's not a bug, it's a purity test you're being given for free.

React 18 concurrent features

  • Automatic batching — React 17 batched state updates only inside React event handlers; React 18 batches inside promises, timeouts and native handlers too. Three setState calls in a .then() now cause one render, not three.
  • useTransition — marks an update as non-urgent, so React can interrupt it to handle typing. The classic case: a search input where keystrokes are urgent and re-filtering 5,000 rows is not.
  • useDeferredValue — the same idea from the consuming side: render an expensive child from a lagging copy of a value while the input stays instantly responsive.
📊 ML / Data Eng Defense

These are the right tools for a data-heavy dashboard. On SahYatri, changing a date range triggers re-aggregating and re-charting thousands of telemetry points. Wrapped in startTransition, the filter control updates instantly and stays clickable while the chart recomputes in the background — React will even abandon that work if the user changes the filter again. Without it, every click freezes the UI for the duration of the recompute, and the app feels broken even though nothing is wrong.

02 Hooks & state architecture

The stale closure — the single most-tested bug

Every render creates new functions that capture that render's values. If a function outlives its render — inside a setInterval, a socket handler, a debounce — it keeps looking at the old value forever.

Stale closure: broken, then three fixes 
// ❌ BROKEN — logs 0 forever. The interval captured count from the first render.
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []);                                  // empty deps = frozen in render #1

// ✅ FIX 1 — functional update. Never reads the captured value at all.
setCount(prev => prev + 1);

// ✅ FIX 2 — a ref always points at the latest value.
const countRef = useRef(count);
useEffect(() => { countRef.current = count; });
useEffect(() => {
  const id = setInterval(() => console.log(countRef.current), 1000);
  return () => clearInterval(id);
}, []);

// ✅ FIX 3 — honest deps: re-subscribe when the value changes.
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, [count]);                             // correct, but tears down every change
🚨 Interview Trap

"Just remove it from the dependency array to stop the re-runs." This is the wrong instinct and interviewers listen for it. The lint warning isn't noise — it's telling you the effect reads something it hasn't subscribed to. Silencing it converts a visible re-render problem into an invisible stale-data problem, which is far harder to debug.

The right moves are: use a functional update so you don't need the value; move the function inside the effect; wrap it in useCallback; or store it in a ref. Pick one based on whether the effect should re-run when the value changes.

Default to useEffect. Reach for useLayoutEffect only when you measure the DOM and immediately change it based on the measurement — otherwise the user sees one frame of the wrong position before it corrects.

Memoization: when it's worth it

  • useMemo — caches a computed value.
  • useCallback — caches a function reference.
  • React.memo — skips re-rendering a child when its props are shallow-equal.
🚨 Interview Trap

useCallback without React.memo on the child usually does nothing. The stable reference only matters if something compares it. An unmemoized child re-renders when the parent does, regardless of prop identity — so you've paid the memo cost and bought nothing.

The inverse trap too: React.memo on a child that receives style={{...}} or onClick={() => ...} inline never hits, because those are new objects every render. Memoization only works if every prop is referentially stable — one inline object defeats the whole thing.

Context vs an external store

💡 Senior Insight

Context has no selector. When the context value changes, every consumer re-renders — even one reading a field that didn't change. So a single context holding { user, theme, notifications, socketStatus } re-renders the entire consuming subtree whenever a notification arrives.

Zustand solves exactly this: useStore(s => s.user.name) subscribes to a slice, and the component re-renders only when that slice changes. Context is genuinely good for values that are stable — theme, locale, an auth object — and bad for anything that updates frequently. The mitigation without leaving Context is to split it into several contexts by update frequency, which is a fine answer when the app doesn't warrant a new dependency.

Controlled vs uncontrolled

Controlled — React state is the source of truth, re-renders on every keystroke. Needed for live validation or interdependent fields. Uncontrolled — the DOM holds the value, read via useRef on submit, zero re-renders. Right for large simple forms where per-keystroke state is pure overhead.

💡 Senior Insight

The App Router's real shift is that these stop being app-wide settings and become per-route, even per-component. RecrutAI can server-render the recruiter dashboard shell for a fast first paint while the Monaco editor and live interview panel stay client-side — one app, both strategies. "It depends on the route" is the answer that shows you've shipped App Router rather than read about it.

Server Components and the serialization boundary

A Server Component runs on the server only and ships zero JavaScript to the browser. It can read a database or filesystem directly with no API layer. Anything interactive — state, effects, event handlers, browser APIs — needs 'use client'.

🚨 Interview Trap

The serialization boundary. Props crossing from a Server Component into a Client Component must be serializable — plain objects, arrays, strings, numbers, dates, Promises. You cannot pass a function, a class instance, or a Map. Try it and you get a runtime error many people misread as a bundler problem.

The related misconception: 'use client' does not mean "renders only on the client." Client Components are still server-rendered for the initial HTML, then hydrated. It marks a bundling boundary — this and everything it imports ships to the browser — not a rendering location. Getting this right is a strong signal.

Hydration mismatches

Hydration is React attaching event listeners to server-rendered HTML while assuming its own render produces identical markup. When it doesn't, you get the mismatch error and React discards the server HTML.

Streaming, Suspense and Server Actions

loading.tsx or a <Suspense> boundary lets the server flush the shell immediately and stream slow sections in as they resolve — TTFB stops being hostage to the slowest query on the page.

Server Actions are functions marked 'use server' that run on the server but are callable from a client component, so a form mutation needs no API route. Two things to say about them unprompted: they're a public HTTP endpoint regardless of where they're imported, so they must do their own auth and validation; and useOptimistic pairs with them to show the result instantly and roll back if the action rejects.

04 Real-time UI, optimistic updates & charting

The socket hook

One connection, clean teardown, no duplicate listeners 
'use client';

export function useGameSocket(roomId) {
  const socketRef = useRef(null);
  const [fen, setFen] = useState(START_FEN);
  const [status, setStatus] = useState('connecting');

  useEffect(() => {
    const socket = io(URL, { transports: ['websocket', 'polling'] });
    socketRef.current = socket;

    const onState   = ({ fen }) => setFen(fen);
    const onConnect = () => { setStatus('connected'); socket.emit('join', { roomId }); };
    const onDrop    = () => setStatus('reconnecting');

    socket.on('connect', onConnect);
    socket.on('state', onState);
    socket.on('disconnect', onDrop);

    return () => {                    // ← the line that prevents the leak
      socket.off('connect', onConnect);
      socket.off('state', onState);
      socket.off('disconnect', onDrop);
      socket.disconnect();
    };
  }, [roomId]);                       // re-subscribe only when the room changes

  return { fen, status, socket: socketRef.current };
}
🚨 Interview Trap

Duplicate listeners in StrictMode. React 18 development mounts, unmounts and remounts every component to surface missing cleanup. Without the socket.off teardown, you now have two handlers for 'state', and each server event fires your setState twice. In production it's worse and subtler: every navigation back to the board stacks another listener, so by the fifth visit one move triggers five updates and the app slows down for reasons that look like a server problem.

Two rules: always return a cleanup that removes exactly the handlers you added, and never create the socket inside the component body — the body runs on every render, so you'd open a new connection each time. Ref plus effect, or a module-level singleton.

Optimistic updates with rollback

Chessify: render the move instantly, reconcile with the server 
function onDrop(from, to) {
  const snapshot = fen;                          // 1. remember how to undo

  const local = new Chess(fen);
  const legal = local.move({ from, to, promotion: 'q' });
  if (!legal) return false;                      // 2. client-side check = fast UX only

  setFen(local.fen());                           // 3. paint immediately — feels instant

  socket.timeout(5000).emit('move', { from, to }, (err, res) => {
    if (err || !res?.ok) setFen(snapshot);       // 4. server said no → roll back
  });
  return true;
}

// The server ALSO broadcasts authoritative state; that always wins.
useEffect(() => { socket.on('state', ({ fen }) => setFen(fen)); }, []);
🛡️ SDE Defense

The framing that matters: the client-side chess.js check is a UX optimization, never a security control. It exists so an obviously illegal drag doesn't cost a round trip. The server runs its own independent validation against its own board, and its broadcast is authoritative — so a modified client that skips the local check gains nothing except a desynced view of a game everyone else sees correctly.

Two details worth volunteering: snapshot the previous state before mutating, since without it there's nothing to roll back to. And use a timeout on the ack — without one, a dropped packet leaves the board optimistically wrong forever with no error and no correction.

High-frequency dashboards

Telemetry arriving every few seconds will re-render the whole dashboard tree unless you stop it. Four techniques, in order of payoff:

  1. Buffer, don't stream to state. Accumulate incoming points in a ref and flush to state on an interval. Ten updates per second becomes one render per second, and the chart looks identical.
  2. Colocate the state. Live data lives in the chart's own subtree, not a top-level provider — otherwise every tick re-renders the header, sidebar and filters too.
  3. Memoize the chart and its data. React.memo on the component, useMemo on the transformed array. Both are needed: a new array identity every render defeats the memo.
  4. Bound the window. Keep the last N points, not all of them, or the array grows without limit and each render gets slower.
📊 ML / Data Eng Defense

Canvas vs SVG is the choice that decides whether the dashboard survives. SVG (Recharts, D3-with-DOM) creates a real DOM node per data point — beautiful, inspectable, and it collapses somewhere around a few thousand points because the browser is laying out thousands of elements every frame. Canvas (Chart.js, uPlot) paints pixels: one element, no layout cost, comfortable with tens of thousands of points.

So: SVG for a chart with dozens of points and rich interactivity; canvas for streaming telemetry. And downsample before rendering — a 1920px-wide chart cannot display more than 1920 distinct x-values, so plotting 50,000 raw readings burns CPU to draw pixels no one can see. Aggregate to roughly one point per pixel column and the chart is visually identical at a fraction of the cost.

For long tables of inference results, virtualize — render only the ~20 rows in the viewport, not all 10,000.

05 Interview defense bank

One-line reason → supporting mechanic → the trade-off you accepted.

Track A — SDE

A · Q1
1. How do you manage Socket.IO lifecycle in Client Components without accumulating listeners?

One connection in a ref, subscriptions in an effect, and a cleanup that removes exactly what it added.

The socket is never created in the component body — that runs on every render, so you'd open a new connection each time. It goes in useRef, created inside a useEffect whose dependency is the room ID, so it re-subscribes when the room genuinely changes and not otherwise.

The cleanup is the whole answer: socket.off(event, handler) for each handler, then disconnect(). Named handler references matter — calling socket.off('state') with no handler removes all listeners for that event, including ones another hook registered.

Why it bites in Next.js specifically: StrictMode in development mounts, unmounts and remounts every component, which doubles listeners immediately if cleanup is missing. That's not a React bug — it's the framework showing you the leak that would otherwise appear in production as "the board updates five times per move after navigating around."

Trade-off: tearing down on every room change costs a reconnect. If a socket must persist across routes, it belongs in a module-level singleton or a provider above the router — but then you own its lifecycle, and it never gets cleaned up automatically.

A · Q2
2. Walk me through optimistic move rendering and rollback in Chessify.

The problem: waiting for a server round trip before the piece moves makes the board feel laggy, even at 80 ms. So the UI renders the move immediately and reconciles afterwards.

The sequence: snapshot the current FEN; validate the move locally with chess.js so an obviously illegal drag doesn't cost a round trip; apply it to local state so the piece moves instantly; emit to the server with an acknowledgement callback and a timeout; on rejection or timeout, restore the snapshot.

The rule underneath it: the server's broadcast is always authoritative and always wins. Local state is a prediction, not a source of truth — so if the two ever disagree, the server's FEN overwrites mine without argument.

Two details worth volunteering: snapshot before mutating, or there's nothing to roll back to. And always set an ack timeout — without one, a dropped packet leaves the board optimistically wrong permanently, with no error anywhere.

Trade-off: a rejected move causes a visible flicker as the piece snaps back. Acceptable, because rejection is rare (the local check catches most illegal moves) while the latency it hides is on every single move.

A · Q3
3. What causes hydration mismatches, and how do you debug them?

Cause: the HTML React generates on the client during hydration doesn't match what the server sent. React expects them to be identical, so it warns and discards the server markup — which throws away the SSR benefit you paid for.

The usual culprits, in order of frequency: anything time-based (new Date(), toLocaleString() — server and client differ in clock and timezone); anything random (Math.random(), UUID generation); reading window or localStorage during render, since neither exists on the server; invalid HTML nesting, because the browser silently repairs <div> inside <p> so the real DOM no longer matches your JSX; and browser extensions injecting attributes.

Debugging: the error names the mismatched element, so start there. Reproduce in incognito to rule out extensions. Then bisect — comment out subtrees until it disappears.

Fixes, from best to worst: make the value deterministic (pass an ISO string from the server and format in an effect); move browser-only reads into useEffect with a stable fallback for the first paint; next/dynamic with ssr: false for genuinely client-only components; and suppressHydrationWarning only on a single leaf node like a timestamp, never as a general silencer — it hides the symptom and the next mismatch too.

A · Q4
4. Why App Router (RSC) for RecrutAI instead of a Vite SPA?

Because rendering strategy becomes a per-route decision instead of one app-wide answer. RecrutAI has two opposite kinds of page: a recruiter dashboard that's mostly data display and should paint fast, and a live interview workspace with a code editor and real-time state that's inherently client-side. An SPA forces one answer for both — everything client-rendered behind a loading spinner.

Concretely: Server Components fetch and render the dashboard's report data with zero JS shipped for those components, so the bundle stays small even as report views grow. The Monaco editor and interview panel are 'use client' islands. Route handlers colocate the API with the app, so there's no separate server to deploy for the monorepo's web package.

It also removes request waterfalls — an SPA loads JS, renders, discovers it needs data, then fetches, and nested components repeat that. Server components fetch during render, close to the data.

Trade-off, honestly: the server/client boundary is a real source of bugs — serialization errors, hydration mismatches, and needing to always know which side a component runs on. For something like the Chessify board, where the entire app is interactive, an SPA genuinely is simpler and I'd choose it.

A · Q5
5. When does Context become a bottleneck versus Zustand or Redux?

The moment the value updates frequently — because Context has no selector. Any change to the context value re-renders every consumer, even one reading a field that didn't change. A context holding { user, theme, notifications, socketStatus } re-renders the whole consuming subtree every time a notification arrives.

Zustand fixes it structurally: useStore(s => s.user.name) subscribes to a slice, and the component re-renders only when that slice changes. The store lives outside React, so updates don't propagate through the tree at all.

Mitigations if you're staying with Context: split into multiple contexts grouped by update frequency (stable auth in one, fast-changing socket state in another) — usually enough on its own. Memoize the provider value with useMemo, or a new object identity every render makes every consumer re-render regardless. And React.memo the components between provider and consumer so re-renders don't cascade further than necessary.

My default: Context for stable, rarely-changing values — theme, locale, the auth object. An external store for anything high-frequency. And most state doesn't belong in either: colocating it in the component that uses it beats both, and "lift it only when something else genuinely needs it" prevents most of these problems from existing.

Track B — ML / AI / Data Engineering

B · Q1
1. How do you visualize live telemetry bursts without dropping frames?

Decouple the data arrival rate from the render rate. That's the core idea — everything else follows from it.

Incoming readings accumulate in a useRef buffer, which doesn't trigger renders. A single interval flushes the buffer into state on a fixed cadence — say once per second. Ten updates a second becomes one render, and the chart looks identical because nobody perceives sub-second chart updates anyway.

Then contain the blast radius: live data state lives inside the chart's own subtree, not a top-level provider, so a tick doesn't re-render the header, sidebar and filters. The chart component is React.memo'd and its transformed data is useMemo'd — both are required, since a new array identity every render defeats the memo.

Bound the window: keep the last N points rather than the full history, or the array grows without limit and every render gets progressively slower — a leak that presents as "the dashboard gets sluggish after an hour."

And use startTransition for filter changes that trigger heavy re-aggregation, so the control stays responsive while the chart recomputes in the background.

B · Q2
2. How did you structure the audit dashboard to render LLM state transitions and score matrices?

Treat the interview as an append-only event log, and render it as a timeline. Each turn produces a record: the question asked, the candidate's answer, the scores across the rubric dimensions, and the branch decision the model made — PROBE_DEEPER, SIMPLIFY, PIVOT_TOPIC or PROCEED. The dashboard is a rendering of that log, not a separate data model.

Why that shape matters: a recruiter's real question isn't "what was the score" but "why did the interview go this way." An event log answers that directly — each transition sits next to the answer and the scores that triggered it, so the model's reasoning is auditable rather than opaque.

Rendering: the report route is dynamic (/admin/reports/[id]) and the data is fetched server-side, since a completed report is static, read-only and non-interactive — it ships essentially no JavaScript. Only the parts that need interaction (expanding a turn, replaying the transcript) are client components. The score matrix is a memoized table component; branch decisions are a constrained enum, so they map to badges from a lookup rather than free-text parsing.

Design constraint worth naming: because the branch decision is one of four valid tokens, the UI can never receive an unexpected state — a hallucinated value is rejected at the service boundary before it's ever persisted or rendered.

B · Q3
3. How do you handle client-side transformation and memoization before charting?

First question: should this run on the client at all? Aggregating thousands of rows in the browser burns the user's battery and blocks the main thread. Rollups belong in the database — an hourly summary query returns 168 rows for a week instead of 200,000 raw readings. Push the work down before optimizing it up here.

For what genuinely must happen client-side: useMemo keyed on the raw data plus the filter parameters, so the transform re-runs only when inputs actually change. Chain it — parse once, filter, then aggregate, each memoized separately, so a filter change doesn't re-parse.

The trap to avoid: transforming inside the render body creates a new array identity every render, which defeats React.memo on the chart and re-renders it even when nothing changed. Memoizing the data and the component are two halves of one fix; either alone does nothing.

Downsample before you draw. A 1920px chart cannot display more than 1920 distinct x-values, so plotting 50,000 points burns CPU rendering pixels nobody can see. Aggregate to roughly one point per pixel column — visually identical, fraction of the cost.

If a transform is genuinely heavy, a Web Worker moves it off the main thread entirely — the only way to keep the UI at 60fps during a multi-hundred-millisecond computation, since useMemo makes work happen less often, never faster.

B · Q4
4. Why dynamic-import Monaco with ssr: false?

Two independent reasons, and both are worth stating.

It can't be server-rendered. Monaco is the editor from VS Code and it reaches for window, document and navigator at module load. On the server those don't exist, so the import throws during SSR — this isn't a preference, it's a hard requirement.

It's large. Monaco with its language workers is one of the heaviest things you can put in a bundle. A static import puts it in the initial JS for every page that touches that route, so a candidate loading the interview intro downloads a full code editor before seeing any text. next/dynamic code-splits it into a chunk fetched only when the coding round actually starts.

What this looks like in practice: dynamic(() => import('@monaco-editor/react'), { ssr: false, loading: () => <EditorSkeleton /> }). The skeleton matters — without it there's a visible gap while the chunk loads, and users read that as the app being broken.

Trade-off: a delay when the editor first appears. Mitigated by prefetching the chunk during the preceding interview stage, so it's already cached by the time it's needed — you spend idle time rather than the user's attention.
