Every bullet on the SDE resume, with the follow-ups you should expect, an answer you can say out loud in 20 to 40 seconds, and an honest check of each claim against what is actually in the repos.

Written for an interviewer who has your resume open in one tab and your GitHub in another. That second tab is the one most prep docs ignore.

The three things that can sink this interview

Everything else on the resume holds up. These three do not, or not fully, and all three are visible to anyone who opens the repo.

  1. SahYatri does not run inference on the Raspberry Pi. The detection service is a separate FastAPI app that loads yolov5xu.pt and takes an uploaded image over HTTP.   2. Your cheating claim is only half true. Move validation is genuinely server-side in Chessify, and that is a real strength. Clocks are not. A modified client can still lie about time. Say this yourself before they find it.

If an interviewer notices the pattern across all three, they will ask whether you have ever thought about durability. Have the answer ready.

No public repo: be specific, not grand
"Engineered 20+ RESTful API endpoints in PHP with MongoDB Atlas for Packspec, designing document schemas and query patterns for multi-tenant, company-scoped data isolation."

Say this first

Plain-English version

"Packspec is a tool where companies write up packaging specifications and route them through approvals. I built the backend API for it, so roughly twenty-odd endpoints covering the products, the components inside them, the specs themselves, and the users."

Likely follow-ups

QName me eight of those endpoints.
Say: "Create a specification, list specs for a company, fetch one by ID, update a spec revision, submit for approval, approve or reject, create a product, attach a component to a product, invite a user, change a user's role. Most resources needed the standard five, and specifications needed extra ones for the workflow steps, which is how you get to twenty quickly."
Have this list memorised. Being able to rattle off actual endpoint names is the single strongest signal that the work was real, and it costs you five minutes to prepare.
QWhy MongoDB and not a relational database for something this structured?
Say: "It was already the stack when I joined, so I did not pick it. It fits reasonably well though, because a packaging spec has a different shape for every client, and modelling that relationally means either a very wide sparse table or an entity-attribute-value mess. A document per spec lets each one carry its own field set. The cost is that I gave up joins and had to be deliberate about denormalising."
Answering "I did not choose it" honestly and then defending it anyway is a much better look than pretending you made an architecture decision you did not make.
QWhat does "designing query patterns" mean concretely?
Say: "Mainly that every query is scoped by company ID first, and that field is indexed, so a lookup never scans across tenants. And for the list views I kept the fields the UI actually renders on the parent document rather than fanning out to fetch each child, because that turns one round trip into twenty."

Stress-testing "20+"

Where this number came from

20+ is the figure on your own portfolio, which makes it the safe one to quote. An earlier draft said 30+. Pick one and never say the other number out loud again, because the fastest way to lose a panel is to give two different figures for the same thing across two rounds.

If pressed on exactness: "Somewhere north of twenty. I did not keep a running count while I was building, so I would rather say twenty than invent a precise number."

No public repo: be specific, not grand
"Implemented JWT authentication and RBAC across 5 tenant tiers over a multi-tenant, company-scoped data model with invite-based onboarding, workspace provisioning, and plan-based quota enforcement."

Say this first

Plain-English version

"Several client companies share the same running application and the same database. My job was making sure one company can never see another's data, and that within a company an ordinary user cannot do admin things."

Likely follow-ups

QWhere exactly do you enforce the tenant boundary?
Say: "In middleware, before the route handler runs. The JWT carries the company ID, the middleware pulls it out and puts it on the request, and every query builds its filter from that value rather than from anything in the request body. So a handler cannot accidentally forget, because it never sees a company ID it could have got wrong."
This is the correct answer and it is worth rehearsing until it is smooth. The wrong answer, the one that loses points, is "I check it in each controller." That means one forgotten check is a data leak.
QWhat are the five tiers?
Say: Name them. Something like super admin, company admin, manager, editor, viewer. Confirm the real names with your team lead before the interview. "Five" is a claim you have made in writing and being unable to list them is worse than never having said it.
QWhat is in your JWT payload, and how do you handle a user whose role changes?
Say: "User ID, company ID, role, expiry. The honest weakness is that a role change does not take effect until the token expires, because the role is baked into the token rather than looked up per request. For a tool used by a few hundred people that was an acceptable trade. If it mattered more I would keep a short-lived access token with a refresh token, or check a revocation list on sensitive routes."
Volunteering the weakness here is a strong move. Every interviewer knows this trade-off, and naming it yourself puts you on the right side of it.
QYou mention atomic transactions. In MongoDB?
Say: "Single document writes are atomic in MongoDB by default, and I leaned on that heavily by keeping things that must change together inside one document. Multi-document transactions need a replica set, which Atlas gives you, and I used those for the flows that genuinely spanned collections, like provisioning a workspace and creating the owner record."
Careful. If you did not actually use multi-document transactions, do not claim you did. Say: "Mostly I relied on single-document atomicity and shaped the schema so that was enough." That is a real design answer and it is safer than a claim that unravels in one follow-up.
No public repo: be specific, not grand
"Designed workflow-state transitions, revision versioning, and cascading soft-deletes so every specification change stays auditable and recoverable; validated the API surface with Postman collections and PHPUnit suites."

Say this first

Plain-English version

"Nothing gets destroyed. Editing a spec writes a new revision instead of overwriting the old one, deleting flags a record rather than removing it, and every spec moves through a fixed set of states so you can always see who changed what and when."

Likely follow-ups

QDraw me the state machine.
Say: "Draft, submitted, under review, approved or rejected, then archived. Draft to submitted is the author. Submitted to approved or rejected is a reviewer. Rejected goes back to draft. The transitions are checked server-side, so you cannot jump from draft straight to approved by calling the endpoint directly."
Ask for the whiteboard or just talk through it with your hands. Interviewers like candidates who reach for a diagram.
QSoft deletes sound tidy but they cause problems. Which ones did you hit?
Say: "Every query needs the deleted filter, and forgetting it once means deleted records reappear in a list. I handled it in the shared query layer rather than per endpoint. The other one is uniqueness, because a soft-deleted record still occupies a unique name, so creating a new spec with the same name as a deleted one fails in a confusing way."
Naming a real problem you hit is worth more than describing the feature. This is the answer that separates people who built it from people who read about it.
QWhat did your PHPUnit tests actually cover?
Say: "Mostly the auth and permission paths, because that is where a bug is expensive, plus the workflow transitions, so the invalid ones actually get rejected. It was not full coverage. It was the parts where a silent failure would have been worst."
Do not claim a coverage percentage. If you have one, use it; if not, "not full coverage, deliberately targeted" is a mature answer.

Projects: Chessify AI

Repo: AmanVerma1067/Chessify-WebApp  |  Live: chessify.aman1067.xyz
This is your strongest SDE project by a distance. Real concurrency, real client-server trust boundary, three deployed services. Expect the deepest questioning here, and be glad of it.

Verified in Chess-PvP/server.js
"Engineered a room-based real-time multiplayer server on Node.js and Socket.IO that assigns white, black and spectator roles per game, replays board state to late joiners and detects opponent disconnects; moved all move validation server-side so a tampered client cannot submit an illegal move."

Say this first

Plain-English version

"Two people share a link and play chess in real time, and anyone else who opens the link watches. The important bit is that the server decides whether a move is legal, not the browser, so you cannot cheat by editing the page."

What the code actually shows

let rooms = {} is a plain object keyed by room ID. Each room holds fen, a players object with white and black socket IDs, and a spectators array.

On a move the server runs new Chess(room.fen), applies the move, and only then updates the room and broadcasts. That is a genuine server-side validation path, not a claim.

Events are all there: join-room, move, chat inbound; role, sync-board, move-confirmed, opponent-move, spectator-count, opponent-disconnected outbound.

Likely follow-ups

QWalk me through everything that happens when I drag a piece.
Say: "The client emits a move event with the room ID, the from square, the to square and a promotion piece if there is one. The server looks up the room, builds a chess.js board from the stored FEN, and tries the move. If chess.js rejects it, nothing happens and the client's optimistic update gets reverted. If it is legal, the server writes the new FEN back into the room, sends move-confirmed to the mover and opponent-move to everyone else in the room."
QYou rebuild a Chess object from FEN on every single move. Why not keep one board in memory per room?
Say: "FEN is the whole state in one string, so storing that instead of a live object keeps the room record simple and serialisable, which would matter the moment I moved rooms into Redis. The cost is real though. FEN carries the halfmove clock but not the position history, so I cannot detect threefold repetition, and I would need to keep the move list alongside it to do that properly."
This is the best answer in the whole document. Almost nobody spots the threefold repetition consequence, and volunteering it marks you as someone who thinks past the happy path. Rehearse it.
QYour server restarts. What happens to games in progress?
Say: "They are gone. Rooms live in a process-local object, so a restart wipes everything. For a hobby project on a free tier that was the right call, and moving room state to Redis is the obvious fix. That also unblocks running more than one instance, which is the other thing this design cannot do today."
QHow would you run this on ten servers?
Say: "Two problems. Sockets in the same game can land on different instances, so I would add the Socket.IO Redis adapter to make broadcasts cross instances. And room state has to move out of process memory into Redis so any instance can serve any move. Sticky sessions help with reconnects but they are not sufficient on their own."
QYour disconnect handler loops over every room in the server. Is that a problem?
Say: "Yes, it is a linear scan on every disconnect. With a handful of concurrent games it is invisible, but it is the wrong shape. The fix is a map from socket ID to room ID so a disconnect is a single lookup. I would take that in review."
They can see this in the code, so having already noticed it yourself is worth more than the fix itself.

The trap in this bullet

Do not oversell "cannot cheat"

Move legality is server-authoritative. Good. But the clocks are not. The README lists Blitz, Rapid and Unlimited timers, and there is no timer logic in the server, which means time is tracked in the browser and a modified client can claim it has more of it than it does.

Say it before they ask: "Move validation is server-side, so illegal moves are impossible. Clocks are not, and that is the honest gap. A patched client could lie about its remaining time. Making that airtight means the server owns the clock and the client only renders it, which is what I would do next."

There is a second one. There is no auth, so anyone with the link can take an open seat. That is a deliberate design choice for a share-a-link game, so say it as a choice rather than letting them find it as an oversight.

Verified in Chess-AI/
"Built a decoupled Flask AI microservice that plays book openings from a Polyglot database, delegates search to the Stockfish engine (ELO 1800), and degrades to a custom minimax with alpha-beta pruning at depth 3 when the engine binary is unavailable; deployed three services independently."

Say this first

Plain-English version

"The bot is its own Python service. Early moves come out of a real opening book, the middle game goes to Stockfish, and if the Stockfish binary will not start on the host I fall back to a search algorithm I wrote myself so the bot still plays instead of erroring out."

What the code actually shows

Files line up exactly with the claim: bot/minimax.py, bot/evaluation.py, bot/stockfish_bot.py, bot/opening_book.py, plus a bundled Stockfish binary and assets/openings.pgn.

One endpoint, POST /get_bot_move, takes a FEN and returns a move and the new FEN. Clean, stateless, easy to describe.

Likely follow-ups

QWhat does "Stockfish ELO 1800" mean? Stockfish is stronger than 3500.
Say: "It is the strength limiter, not the engine's real rating. Stockfish has a setting that caps how well it plays so it is a reasonable opponent for a human, and I set that to 1800. If I said the bot plays at Stockfish's actual level nobody would ever beat it."
This question is close to guaranteed if the interviewer plays chess. Getting it right is easy points; getting it wrong makes the number look copy-pasted.
QWhy depth 3? That is shallow.
Say: "Latency. It is a fallback path running on a free Render instance, and chess branches around 35 moves wide, so depth 3 is roughly forty thousand positions before pruning. Alpha-beta cuts that a long way when the move ordering is decent, but going deeper made the bot take long enough that the game felt broken. It is meant to keep playing, not to play well."
QExplain alpha-beta to me.
Say: "You carry two bounds through the search, the best score the maximising side can already guarantee and the best the minimising side can. The moment a branch proves worse for the player to move than something they have already secured, you stop looking at that branch, because they would never choose it. It gives the same answer as plain minimax and just skips work. How much it skips depends almost entirely on move ordering, since good moves first means more cuts."
Expect this. It is the most natural DSA question your own resume invites, and answering it fluently pays for the whole project.
QWhat is in your evaluation function?
Say: "Material weights plus piece-square tables, so a knight in the centre scores higher than one on the rim. It is a standard simple evaluation. No pawn structure, no king safety term, no mobility. Those are the things I would add next and each one costs search speed."
QWhy a separate Python service instead of doing the AI in Node?
Say: "Stockfish is a binary you talk to over UCI and python-chess wraps that well, so Python was the path of least resistance. It also means the bot can go down without touching multiplayer, which has actually happened, because the two deploy independently."
The second half is the better half. Fault isolation is a real architectural benefit and it is stronger than "Python has nicer libraries."

Stress-testing "three services deployed independently"

Verified, and worth more than it sounds

Next.js frontend on Vercel, Flask AI on Render, Node PvP on Render. Three deploy targets, environment-scoped config, CORS across origins. That is genuinely more operational surface than most student projects have, so do not undersell it as "I deployed it."

Deep dive: where this project goes three levels down

If an interviewer likes Chessify they will keep pulling. These are the next questions after the obvious ones.

QTwo players move at the same instant. What happens?
Say: "Node is single threaded, so the two move events are handled one after the other, not concurrently. The first one validates against the current FEN and updates it. The second one then validates against the new FEN and chess.js rejects it, because it is not that player's turn. So the race resolves itself, but by luck of the runtime model rather than by anything I designed. In a multi-instance setup with shared state I would need an actual lock or a compare-and-set on the FEN."
Excellent answer, because it is honest about why it works.
QA player's wifi drops for ten seconds and comes back. What do they see?
Say: "Socket.IO reconnects with a new socket ID, so as far as the room is concerned they are a new person. They rejoin, and since both seats are taken they come back as a spectator of their own game. That is the bug I would fix first. The right shape is a game token in local storage that lets a returning player reclaim their seat."
Do not hide this. It is a well-known hard problem and having diagnosed it correctly is the point.
QHow do you stop me joining a random room ID and interfering?
Say: "You cannot interfere, because a third connection is assigned spectator and the move handler checks that the socket ID matches the seat whose turn it is. You could watch a stranger's game if you guessed their room ID, which is a privacy leak rather than an integrity one. Longer, random IDs and an optional private flag would close it."
QHow would you add matchmaking against a stranger?
Say: "A waiting queue in Redis. A player joins the queue, and if someone is already waiting you pop them, create a room ID and push both clients into it. Once you want rating-based matching you need buckets and a widening search window over time, so somebody waiting thirty seconds gets matched more loosely."

The questions that are not about any one bullet

"You are an ECE student. Why software?"

You will get this, probably in the first five minutes, at almost every company. Branch-mismatch is the standard opening probe for non-CSE candidates in SDE roles and a weak answer here colours everything after it.

Say this

"I picked ECE and then found the software half more interesting, so I went and did the work. My core CS is coursework plus what I taught myself, my DSA is 863 problems and a Knight rating, and I have shipped a real-time multiplayer platform and an app my batch actually uses. I would rather be judged on that than on the name of my branch."

QHave you done operating systems and DBMS formally?
Say: They are on your coursework line, so say yes and be ready to prove it. Expect processes versus threads, deadlock conditions, paging, normal forms, indexing, ACID, and isolation levels. An ECE candidate gets these asked more thoroughly than a CSE one, not less. Revise them.
QDoes your ECE background help at all?
Say: "For SahYatri it did directly, since somebody had to make the Pi, the camera, the GPS module and the I2C display behave before any of the software mattered. Most SDE candidates have never had to debug something where the bug might be in the wiring."
Turn it into a differentiator instead of an apology. You have hardware experience that CSE candidates do not.

System design they will actually ask you

At intern and fresher level this is not distributed-systems trivia. It is "can you reason about a system you have not seen." Your resume points them at two obvious prompts.

QDesign a real-time multiplayer game backend.
You have lived this, so lead with it. Walk through rooms, role assignment, server-authoritative state, the client's optimistic update and rollback, reconnection with a resume token, then scale it out with a Redis adapter and shared room state. Naming what your own build does not do yet, clocks and persistence, is what makes it a design discussion rather than a project summary.
QDesign a system that collects sensor readings from ten thousand vehicles.
Say: Devices push to an ingest endpoint, which writes to a queue rather than straight to the database. Workers batch-insert into a time-partitioned table. Recent data stays hot, older data gets downsampled or rolled up. Reads go through an aggregation layer or a cache, because dashboards ask the same questions repeatedly. Then talk about what happens when a bus loses signal for an hour and reports late, which is the interesting part.
QHow do you handle a service that depends on something unreliable?
Say: You have two real examples. Stockfish falling back to your own minimax, and RecrutAI's timeout and retry layer with deterministic fallbacks. Use them. "Timeout, bounded retries with backoff, and a degraded path that still returns something usable" is the answer, and you have shipped it twice.

What to ask them

Have three. Not one, because the first might get answered during the interview.

  • "What does the first three months look like for someone joining this team?" Tells you whether onboarding exists.
  • "How does code get from a branch to production here? Who reviews, what has to pass?" Sounds like curiosity, actually tells you their engineering maturity.
  • "What is the part of the codebase everyone is slightly afraid of?" Gets a real answer surprisingly often, and interviewers enjoy the question.
Do not ask

Anything you could have found on the careers page. Compensation in a first round. "Do you have work-life balance." All three land badly.
