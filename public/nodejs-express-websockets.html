One idea underneath everything here: Node has exactly one thread running your JavaScript. Almost every Node interview question — blocking, scaling, race conditions, memory leaks — is a consequence of that single sentence. If you're stuck mid-answer, reason from it.

01 Node internals & the event loop

The phases, in order

libuv runs a loop with fixed phases. Each tick walks through them:

PhaseRunsYou'll be asked
TimerssetTimeout, setInterval callbacks whose time has elapsedWhy timers fire late, never early
Pending callbacksDeferred system-level I/O callbacks (e.g. some TCP errors)Rarely
Idle / prepareInternal libuv useJust name it
PollRetrieves new I/O events; runs their callbacks. Blocks here when idleWhere a Node process actually waits
ChecksetImmediate callbackssetImmediate vs setTimeout(fn,0)
Close'close' events — socket.on('close')Cleanup ordering

Microtasks jump the queue

Between every phase (and after each callback), Node drains two queues before continuing:

  1. process.nextTick queue — drained completely first.
  2. Promise microtask queue — .then, await continuations — drained next.
Ordering puzzle — be able to explain this output 
console.log('1 sync');

setTimeout(()  => console.log('5 timeout'), 0);
setImmediate(() => console.log('6 immediate'));

Promise.resolve().then(() => console.log('4 promise'));
process.nextTick(()  => console.log('3 nextTick'));

console.log('2 sync');

// 1 sync → 2 sync → 3 nextTick → 4 promise → then 5/6
// nextTick beats promises. Both beat every phase.
// timeout-vs-immediate order at top level is NOT guaranteed —
// it depends on how long the process took to boot.
// Inside an I/O callback, setImmediate ALWAYS wins (check comes right after poll).
🚨 Interview Trap

Recursive process.nextTick starves the loop. Because the nextTick queue drains completely before the loop advances, a nextTick that schedules another nextTick never lets I/O run. Your server accepts no connections and shows no error — it just goes silent at 100% CPU. This is why setImmediate is the safe choice for "run after the current operation": it yields to the loop.

V8 vs the libuv threadpool

"Single-threaded" describes your JavaScript, not the process. Node has background threads — they're just not running your code.

WorkHandled byBlocks JS?
Network I/O (sockets, HTTP)OS kernel — epoll/kqueueNo, and no thread used
File I/O (fs)libuv threadpoolNo, but consumes a pool slot
crypto.pbkdf2, bcryptlibuv threadpoolNo, consumes a slot
DNS lookup()libuv threadpoolNo, consumes a slot
Your for loop, JSON.parseThe one JS threadYes
💡 Senior Insight

The threadpool defaults to 4 threads (UV_THREADPOOL_SIZE). That number matters more than people expect: bcrypt hashing runs there, so five concurrent logins mean the fifth waits for a free thread even though the event loop is idle. Sockets don't touch the pool at all — the kernel handles them. So the mental split is: network scales to thousands; file and crypto work scales to four unless you raise it.

Scaling past one core

ToolGives youUse forWatch out
Worker ThreadsExtra JS threads in one processCPU work: parsing, image ops, computeNo shared objects — messages are copied
ClusterN forked processes sharing a portScaling an HTTP server across coresNothing in memory is shared
PM2Cluster + restarts, logs, zero-downtime reloadProduction process managementSame shared-state problem
🚨 Interview Trap

"Just add cluster mode to scale Chessify." That breaks it instantly. Room state lives in a plain object in one process's memory. Fork four workers and player A lands on worker 1, player B on worker 3 — different objects, so they're in different games with the same room code. Clustering a stateless REST API is free; clustering a stateful socket server requires externalizing state first. Knowing which of your services can be clustered safely is the actual answer.

Streams & backpressure

Four types: Readable (source), Writable (sink), Duplex (both — a TCP socket), Transform (duplex that modifies — gzip).

Backpressure is the whole point. writable.write() returns false when its internal buffer is over the high-water mark. That boolean is the sink saying "I'm behind — stop." Ignore it and Node keeps buffering in RAM until the process dies.

Respecting backpressure manually (and why pipeline is better) 
// manual — this is what pipe() does for you
function writeAll(rows, dest, done) {
  let i = 0;
  (function next() {
    while (i < rows.length) {
      const ok = dest.write(JSON.stringify(rows[i++]) + '\n');
      if (!ok) return dest.once('drain', next);   // stop; resume when flushed
    }
    done();
  })();
}

// production: pipeline handles backpressure AND cleanup on error
const { pipeline } = require('node:stream/promises');
await pipeline(readStream, transformStream, writeStream);
📊 ML / Data Eng Defense

Backpressure is the concept that makes an ingestion service survive. If SahYatri's Node layer accepted telemetry faster than PostgreSQL could absorb it, the excess would sit in process memory and the container would OOM — the failure looks like a random crash, not a database problem, which makes it miserable to debug. Streams give you the signal to slow down. At larger scale you push that signal further upstream: a queue holds the backlog on disk instead of in RAM, and the ingest endpoint returns 202 Accepted immediately.

02 Express, middleware & error handling

The middleware pipeline

Express is a list of functions run in order. Each gets (req, res, next). Call next() to continue, send a response to stop, or call next(err) to jump to error handling. Registration order is execution order — that's the source of most Express bugs.

TypeSignatureExample
Applicationapp.use(fn)helmet(), cors(), express.json()
Routerrouter.use(fn)requireAuth on /api/admin
Routeapp.get(path, fn, handler)Per-endpoint validation
Error(err, req, res, next)Central error responder
🚨 Interview Trap

Express identifies error middleware by arity — it counts the function's parameters. Write (err, req, res) with three params and Express treats it as normal middleware, so your error handler silently never fires. Same class of bug: register the error handler before your routes and it can never catch them, because it's already run.

Async errors — the one that bites

Express 4 catches thrown errors in synchronous handlers only. An async handler that rejects produces an unhandled rejection: the client hangs until timeout, and nothing reaches your error middleware.

The asyncHandler wrapper + centralized error hierarchy 
// Express 4 fix — wrap every async route
const asyncHandler = fn => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

// Custom error hierarchy — status lives on the error, not the route
class AppError extends Error {
  constructor(message, status = 500) {
    super(message);
    this.status = status;
    this.isOperational = true;      // expected vs programmer bug
  }
}
class NotFoundError     extends AppError { constructor(m='Not found')    { super(m, 404); } }
class UnauthorizedError extends AppError { constructor(m='Unauthorized') { super(m, 401); } }
class ConflictError     extends AppError { constructor(m='Conflict')     { super(m, 409); } }

app.get('/timetable/:id', asyncHandler(async (req, res) => {
  const t = await Timetable.findById(req.params.id);
  if (!t) throw new NotFoundError('Timetable not found');   // just throw
  res.json(t);
}));

// ONE error responder, registered LAST
app.use((err, req, res, next) => {
  const status = err.status || 500;
  if (!err.isOperational) console.error(err);              // log real bugs
  res.status(status).json({
    error: status === 500 ? 'Internal server error' : err.message
  });
});

Express 5 handles rejected promises from async handlers natively, so the wrapper becomes unnecessary. Say which version you targeted — it shows you know why the wrapper exists rather than cargo-culting it.

💡 Senior Insight

Distinguish operational errors (bad input, missing record, expired token — expected, handle and continue) from programmer errors (undefined property, blown invariant — a bug, state is now suspect). On uncaughtException, the correct move is to log and exit, letting PM2 or the container restart you. Continuing after an unknown crash means serving requests from a process you no longer trust.

REST design that survives review

CodeMeansUse when
200 / 201 / 204OK / Created / No contentGET · POST that created · DELETE

Idempotency: GET, PUT and DELETE produce the same end state when repeated; POST doesn't. This isn't trivia — it's exactly why a client can safely retry a GET on a flaky mobile connection but must use an idempotency key to retry a POST.

Pagination: offset vs cursor

📊 ML / Data Eng Defense

For SahYatri's telemetry history, cursor pagination isn't a preference — it's required. Rows arrive continuously, so between page 1 and page 2 the offsets have already shifted and a user paging backwards through history sees the same reading twice while missing another. Keyset on (recorded_at, id) is stable under concurrent writes and stays fast at any depth. Rule: offset for static tables, cursor for anything append-heavy.

03 Real-time communication & Socket.IO

Pick the lightest thing that works

TechniqueHowCostRight for
Short pollingRequest every N secondsWasteful, laggyAlmost nothing
Long pollingServer holds request until dataReconnect per messageFallback only
SSEOne open stream, server → clientCheap, HTTP-nativeLive scores, LLM token streaming
WebSocketUpgraded TCP, both directionsStateful, sticky sessionsChess, chat, collaboration
💡 Senior Insight

Ask who initiates. Only the server pushes → SSE, and it's underrated: it runs over plain HTTP, reconnects automatically, and needs no special proxy config. Both sides push → WebSocket. Chess qualifies genuinely — both players send moves, and the server also emits join, disconnect and spectator events unprompted. A dashboard that only receives telemetry does not qualify, and choosing SSE there is the senior call.

How Socket.IO actually connects

Engine.IO starts with HTTP long-polling, then attempts an upgrade to WebSocket once the connection is proven. That's why it works behind corporate proxies that block ws:// — it degrades instead of failing.

  • Namespace — a separate logical endpoint (/admin) sharing one TCP connection. Multiplexing.
  • Room — a server-side set of socket IDs inside a namespace. Not a connection; just a label to broadcast to. One chess game = one room.
  • Heartbeats — pingInterval / pingTimeout detect a dead connection that never sent a TCP FIN (phone entering a tunnel).
Chessify room lifecycle — the shape that matters 
const rooms = {};   // roomId → { chess, white, black, spectators[] }

io.on('connection', (socket) => {

  socket.on('join', ({ roomId }) => {
    const room = rooms[roomId] ||= { chess: new Chess(), white: null, black: null, spectators: [] };
    socket.join(roomId);                          // Socket.IO room
    socket.data.roomId = roomId;

    // assign a ROLE — this is the security boundary, not a UI detail
    if (!room.white)      { room.white = socket.id; socket.data.color = 'w'; }
    else if (!room.black) { room.black = socket.id; socket.data.color = 'b'; }
    else                  { room.spectators.push(socket.id); socket.data.color = null; }

    socket.emit('joined', { color: socket.data.color, fen: room.chess.fen() });
  });

  socket.on('move', ({ from, to, promotion }) => {
    const room = rooms[socket.data.roomId];
    if (!room) return;
    if (socket.data.color === null) return;                    // spectator: reject
    if (room.chess.turn() !== socket.data.color) return;       // not your turn: reject

    const legal = room.chess.move({ from, to, promotion });    // chess.js is the referee
    if (!legal) return;                                        // illegal: reject silently

    io.to(socket.data.roomId).emit('state', { fen: room.chess.fen(), last: legal });
  });

  socket.on('disconnect', () => {
    const room = rooms[socket.data.roomId];
    if (!room) return;
    io.to(socket.data.roomId).emit('opponent-left', { color: socket.data.color });
    // NOTE: don't delete the seat immediately — see reconnection Q3
  });
});
🛡️ SDE Defense

Three checks, in this order, and they must all live on the server: (1) is this socket a player or a spectator? (2) is it their turn? (3) is the move legal in the server's board state? The client's board is a rendering, never a source of truth. A modified client can emit any payload it likes — {from:'a1', to:'h8'} from the spectator seat — and every one of those is rejected by a check that doesn't consult the client at all. If validation lived only in the browser, the game would be trivially cheatable.

🚨 Interview Trap

Socket memory leaks. Two versions worth knowing. Server-side: never removing a room from rooms after both players leave — the object grows forever, and it looks like a slow memory climb with no obvious cause. Client-side: registering socket.on('state', ...) inside a React component without removing it on unmount, so every remount stacks another listener and one server event fires the handler five times. Fix: return a cleanup that calls socket.off, and sweep empty rooms on disconnect.

Scaling real-time horizontally

The moment you run two instances, rooms = {} becomes a bug: instance A has no idea a socket on instance B joined the same game. Two things must change.

  1. Pub/sub adapter — @socket.io/redis-adapter forwards emits between instances via Redis, so io.to(room).emit() reaches sockets on every node.
  2. Externalize state — the authoritative board FEN moves into Redis, so any instance can validate a move.

Also needed: sticky sessions at the load balancer, because Engine.IO's polling handshake must reach the same instance each time.

💡 Senior Insight

Be honest that single-instance is the right choice for a project at this scale — and then show you know the exact upgrade path. "The adapter solves message routing; it does not solve shared state. If two instances both hold a board in local memory, they diverge. Redis has to become the single source of truth for the FEN, and then the move handler needs a per-room lock or an atomic compare-and-set, because two instances can now process moves for the same game concurrently." That last sentence is the one that signals real distributed-systems thinking.

04 Auth, JWT & access control

Anatomy of a token

Three base64url segments joined by dots: header (algorithm), payload (claims — sub, role, tenantId, exp, iat), signature.

🚨 Interview Trap

A JWT is signed, not encrypted. Anyone can decode the payload — paste it into jwt.io and read it. Signing proves it wasn't altered; it hides nothing. So never put anything sensitive in the claims. Related classic: the alg: none attack, where a client submits an unsigned token hoping the server trusts the header. Always verify against an algorithm you specify, never one the token names.

 HS256RS256
KeysOne shared secretPrivate signs, public verifies
Who can forgeAnyone holding the secretOnly the private-key holder
Best forA single monolith signing its own tokensMany services verifying a central auth server's tokens

The trade is straightforward: HS256 means every verifying service can also mint tokens. RS256 lets services verify while only the auth server can issue.

Access + refresh token rotation

The problem: a stateless JWT stays valid until it expires, so you can't really log someone out. The standard resolution is two tokens with different jobs.

  • Access token — short (~15 min), sent on every request, never stored server-side. Damage from theft is time-boxed.
  • Refresh token — long-lived, stored server-side (DB/Redis), used only against /auth/refresh. Because it is tracked, it can be revoked.

Rotation with reuse detection is the part interviewers want:

Refresh rotation + reuse detection 
// Refresh tokens are single-use. Each refresh issues a NEW one and
// retires the old. Tokens are grouped by "family" (one login session).

app.post('/auth/refresh', asyncHandler(async (req, res) => {
  const raw = req.cookies.refreshToken;
  const stored = await RefreshToken.findOne({ hash: sha256(raw) });

  if (!stored) throw new UnauthorizedError();

  // THE KEY CHECK: an already-used token means it was stolen and replayed.
  // The legitimate user already rotated it — so someone else has a copy.
  if (stored.usedAt) {
    await RefreshToken.deleteMany({ family: stored.family });   // nuke the session
    throw new UnauthorizedError('Token reuse detected — session revoked');
  }

  stored.usedAt = new Date();
  await stored.save();

  const next = await RefreshToken.create({
    hash: sha256(newRaw), family: stored.family, userId: stored.userId,
    expiresAt: addDays(new Date(), 30),
  });

  res.cookie('refreshToken', newRaw, {
    httpOnly: true, secure: true, sameSite: 'strict', path: '/auth/refresh',
  });
  res.json({ accessToken: signAccess(stored.userId, '15m') });
}));
💡 Senior Insight

Reuse detection is elegant because it turns theft into a detectable event rather than a silent one. A refresh token is single-use, so if the server ever sees one presented twice, exactly one of the two holders is an attacker — and since you can't tell which, you kill the whole family and force a re-login. The user is mildly inconvenienced; the attacker loses access. That asymmetry is the entire design.

Where do you store the token?

 HttpOnly cookieAuthorization: Bearer
XSS reachableNo — JS can't read itYes if stored in localStorage
CSRF riskYes — needs SameSite + CSRF tokenNo — not sent automatically
Cross-origin / mobileFiddlySimple — StudySync's Flutter client

There's no free option — you're choosing which attack to defend explicitly. Cookies with SameSite=Strict for browser apps; bearer headers for mobile clients that have no cookie jar.

RBAC and tenant isolation

Role middleware + tenant-scoped repository 
const requireRole = (...allowed) => (req, res, next) =>
  allowed.includes(req.user.role) ? next() : next(new AppError('Forbidden', 403));

router.delete('/specs/:id', requireAuth, requireRole('owner', 'admin'), handler);

// Isolation must be structural, not remembered.
// Every query goes through a repo that injects tenantId from the VERIFIED token.
class TenantScopedRepo {
  constructor(model, tenantId) { this.model = model; this.tenantId = tenantId; }
  find(filter = {})       { return this.model.find({ ...filter, tenantId: this.tenantId }); }
  findById(id)            { return this.model.findOne({ _id: id, tenantId: this.tenantId }); }
  update(id, patch)       { return this.model.updateOne({ _id: id, tenantId: this.tenantId }, patch); }
}
🛡️ SDE Defense

Two rules that make multi-tenancy actually safe. First: the tenant ID comes only from the verified token — never from a request body, query string or header. If a client can send tenantId, a client can send someone else's. Second: make isolation structural, not disciplined. Relying on every developer to remember a tenantId filter guarantees that one endpoint eventually forgets, and that endpoint leaks. Route everything through a scoped repository and the filter cannot be omitted — the only way to write an unscoped query is to bypass the repo entirely, which is visible in code review.

05 Interview defense bank

One-line reason → supporting mechanic → the trade-off you accepted.

Track A — SDE

A · Q1
1. How does Chessify validate moves server-side, and what happens when a client emits an illegal move?

The server holds the only real board. Each room has a chess.js instance; the browser's board is a rendering of state the server owns.

Three gates, in order: is this socket a player or spectator (spectators are rejected outright); is it their colour's turn (checked against the server's turn(), not a client claim); and is the move legal in the server's position. chess.js returns null for anything illegal, so a fabricated move — teleporting a piece, moving into check, moving an opponent's piece — fails the same way.

Rejected moves are dropped without broadcasting, so the cheater's own UI desyncs from the authoritative FEN and every honest client is unaffected. The board they see is a lie only to them.

Trade-off: server-side validation costs a round trip before a move is confirmed. That's why the client renders optimistically and reconciles against the server's FEN — responsive UI, authoritative state.

A · Q2
2. What if two players move in the same millisecond? How does single-threading resolve the race?

It doesn't need resolving — the race can't happen inside one process. Node runs one JS thread, so the two 'move' handlers are queued and executed one after the other, never interleaved. Each runs to completion before the next begins.

Whichever socket's packet the event loop picks up first is processed first; that move mutates the board and flips turn(). The second handler then reads the already-updated state and fails its turn check. So simultaneous submissions resolve into "first one wins, second is rejected" for free.

The nuance that earns the point: this guarantee only holds because the handler is fully synchronous. Put an await in the middle — a DB write between validating and mutating — and you've created a real interleaving window where both moves pass validation. And it holds only on one instance: add a second server and you need a per-room lock or an atomic Redis compare-and-set, because two event loops genuinely can run concurrently.

A · Q3
3. How do you handle a 10-second network drop without demoting a player to spectator?

The bug to avoid: roles are assigned by seat availability, so if disconnect frees the white seat and both players are still in the room, the returning player gets whatever's left — spectator in their own game. Socket IDs are ephemeral and change on every reconnect, so identity can't be the socket ID.

The fix: give each player a stable playerId (persisted client-side) sent on join. On disconnect, mark the seat disconnected with a timestamp rather than freeing it, and start a grace timer (~30s). On reconnect, match by playerId, restore the seat, update the stored socket ID, and replay the current FEN plus move history so their board catches up. Only when the timer expires is the seat released and the game forfeited or abandoned.

Trade-off: holding seats means memory for abandoned games, so the sweep has to actually run. It's also why Socket.IO's pingTimeout matters — that's what decides how fast a silent drop (phone in a tunnel, no TCP FIN) is even noticed.

A · Q4
4. Why offline-first HTTP caching in StudySync rather than WebSockets?

Because a timetable changes a few times a semester, and WebSockets solve a problem it doesn't have. Real-time transport earns its cost when data changes while the user is watching. A weekly schedule doesn't.

The actual requirement was the opposite of real-time: render instantly with zero network, because students open the app between classes on bad campus wifi. So the app renders the cached schedule immediately and refreshes in the background — a plain GET plus a local cache. A socket would need a live connection to show anything, which is worse in exactly the conditions the app is used in.

REST also gets HTTP caching for free and needs no sticky sessions or reconnection logic on mobile.

Trade-off: an admin edit isn't pushed — it appears on next refresh. Perfectly acceptable here. If it weren't, the lightest fix is a push notification triggering a re-fetch, not a persistent socket.

A · Q5
5. Design a secure refresh-token rotation flow that detects reuse.

Short access token (15 min) + long refresh token stored server-side, single-use. Every refresh issues a new token and retires the old one; tokens are grouped into a family representing one login session.

Detection: if a refresh token that's already been used is presented again, one of two parties is an attacker — the legitimate client already rotated, so a second presentation means someone else has a copy. You can't tell which is which, so you delete the entire family and force re-login. Theft becomes a detectable event instead of a silent one.

Hardening: store only a hash of the refresh token (a DB leak then yields nothing usable), serve it in an HttpOnly; Secure; SameSite=Strict cookie scoped to /auth/refresh so it's never sent on ordinary requests, and cap absolute session lifetime so rotation can't extend a session forever.

Trade-off: refresh is now stateful — you gave up pure statelessness to gain revocation. That's the correct trade, and being able to name it is the point.

Track B — ML / AI / Data Engineering

B · Q1
1. Why a Node ingestion layer instead of writing to PostgreSQL from the Python detection service?

Because inference and ingestion have opposite performance profiles, and coupling them makes the slower one dictate the faster one. The Pi's job is running YOLO frame by frame; if that same loop also opened a database connection and waited on a network write, every slow write would stall detection.

A Node ingestion endpoint is I/O-bound — accept JSON, write, respond — which is precisely what an event loop does well: hundreds of concurrent buses, no thread per connection. It also gives you one place to own the database concerns that don't belong on an edge device: a connection pool (a Pi shouldn't hold a direct DB connection over the public internet), validation, auth, and schema changes deployed once instead of pushed to every vehicle.

Trade-off: an extra hop and a service to keep up. Worth it — the Pi now only needs to speak HTTP to one endpoint, and the database is never directly exposed to the fleet.

B · Q2
2. Why decouple the chess engine from the Socket.IO server?

Because they have opposite concurrency shapes and one event loop can't serve both. Multiplayer is hundreds of idle sockets exchanging tiny messages — pure I/O. A Stockfish search or a depth-3 minimax pins a core for hundreds of milliseconds — pure CPU.

In one Node process there is one thread executing JavaScript, so a single bot move would freeze every live game on the server. Split into a Flask service, an engine slowdown makes bot moves slower and nothing else. They also deploy, restart and scale independently, and Python is where the chess tooling lives.

Trade-off: a network hop per bot move and a second service to operate. Cheap next to a global stall triggered by one user.

If pushed on alternatives: Worker Threads would keep it in one process, but you'd be reimplementing engine integration in JS to avoid a hop that costs milliseconds. Spawning a child process per move is worse — process startup dominates the actual search.

B · Q3
3. How do you stop high-frequency JSON parsing from blocking the event loop?

Name the real mechanism first: JSON.parse is synchronous and runs on the one JS thread. It isn't I/O — nothing about it is async — so a large body genuinely freezes every other request for its duration.

What actually helps:

  • Cap body size — express.json({ limit: '100kb' }). A telemetry payload is small; anything large is a bug or an attack, and rejecting it is better than parsing it.
  • Batch on the device, not the server — one request with 20 readings beats 20 requests. Fewer parses, fewer round trips, fewer inserts.
  • Validate cheaply, respond early — return 202 Accepted once the payload is durable (queue or buffer), and do the heavy write asynchronously. The device isn't waiting on your database.
  • Stream genuinely large payloads — for a 2,400-reading backlog upload, a streaming JSON parser processes incrementally instead of materializing the whole array in memory.
  • Worker thread if parsing is unavoidably heavy — but this is the last resort, not the first move.

The honest framing: at SahYatri's actual volume this never bit. Knowing the shape of the fix is what matters, along with knowing you didn't need it yet.

B · Q4
4. How would you evolve the ingestion layer for a 100× spike in vehicles?

The bottleneck moves from Node to PostgreSQL long before Node struggles. The event loop happily handles the connections; what falls over is one INSERT per reading, each with its own round trip, transaction and index update.

In order of impact:

  • Batch inserts — buffer briefly and write multi-row inserts or COPY. Usually an order-of-magnitude win on its own, and it's the cheapest change.
  • Connection pooling — Postgres forks a process per connection, so 10,000 clients must funnel through a bounded pool. PgBouncer in transaction mode multiplexes many app connections onto few server ones.
  • Decouple with a queue — the endpoint validates, pushes to Kafka or RabbitMQ, returns 202. Writers drain in batches at whatever rate the DB sustains. Now a database slowdown creates a backlog on disk instead of dropped requests, and a DB restart doesn't lose data.
  • Partition by time — writes concentrate on the current partition, keeping the hot index small; retention becomes DROP TABLE.
  • Cluster the Node layer — safe here precisely because ingestion is stateless, unlike the socket server.
  • Idempotency — (bus_id, recorded_at) unique with ON CONFLICT DO NOTHING, so a retry after a timeout can't double-count.

What I'd change last: the database engine. Switching to Timescale or Influx is a real answer at extreme scale, but doing it before batching and partitioning means paying a migration to avoid a config change.
