01 WSGI vs ASGI & concurrency models

The two interfaces

WSGI (Flask) is a synchronous contract: one callable takes a request, returns a response, and owns its worker for the entire duration. Wait 200 ms on a database and that worker does nothing else for 200 ms.

ASGI (FastAPI/Starlette on Uvicorn) is async: a coroutine that hits await yields control back to the event loop, which runs other requests until the awaited thing is ready.

💡 Senior Insight

Async does not make anything faster — it makes waiting cheaper. A route that spends 200 ms in a matrix multiply takes 200 ms either way; async can't parallelize it, because there's still one thread and one GIL. A route that spends 200 ms waiting on the USDA API can overlap with hundreds of others. The correct question is never "is this slow?" but "is this slow because it's waiting, or slow because it's working?" Async fixes the first; only processes or C extensions fix the second.

Workers, threads and the GIL

The GIL allows one thread to execute Python bytecode at a time per process. Two consequences that decide your deployment:

  • Threads don't parallelize Python compute — 4 Gunicorn threads running inference give you roughly the throughput of 1.
  • Processes do — each has its own interpreter and its own GIL. That's why the unit of CPU scaling in Python is the worker, not the thread.
  • C extensions release the GIL — PyTorch and NumPy drop it during heavy kernels, so some genuine parallelism sneaks back in. Don't over-claim it.
Deployment commands worth memorizing 
# Flask (WSGI) under Gunicorn — sync workers
gunicorn app:app --workers 4 --threads 2 --timeout 120 --bind 0.0.0.0:8000

# FastAPI (ASGI) — Uvicorn directly
uvicorn main:app --host 0.0.0.0 --port 8000 --workers 4

# FastAPI under Gunicorn, using Uvicorn workers (process mgmt + async)
gunicorn main:app -k uvicorn.workers.UvicornWorker --workers 4 --bind 0.0.0.0:8000

# Rule of thumb for I/O-bound: workers = (2 x cores) + 1
# For ML serving: workers = however many model copies fit in RAM. Usually far fewer.
🚨 Interview Trap

The 4 GB arithmetic. "Set --workers 8 for throughput" is the wrong instinct for ML serving. Gunicorn workers are separate processes with separate memory — a 500 MB model loaded in 8 workers is 4 GB of RAM for eight identical copies. In a container with a 2 GB limit, the OOM killer takes workers down and the failures look random.

Fork-time copy-on-write helps a little if you preload, but PyTorch tensors get touched during inference, so pages get copied anyway — don't lean on it. For model serving, worker count is decided by memory, not by CPU cores. Often the right answer is 1–2 workers and a request queue.

02 FastAPI, Pydantic & dependency injection

Pydantic V2 does three jobs

  1. Parses — JSON body → typed Python object.
  2. Coerces — "150" → 150 where the type allows it, with strict mode available when you don't want that.
  3. Rejects — anything invalid returns 422 automatically, with a field-level error path, before your code runs.
Nutri-Vision request/response schemas 
from pydantic import BaseModel, Field, field_validator

class MealTextRequest(BaseModel):
    text: str = Field(min_length=1, max_length=500)
    servings: float = Field(default=1.0, gt=0, le=20)

    @field_validator("text")
    @classmethod
    def not_blank(cls, v: str) -> str:
        if not v.strip():
            raise ValueError("text cannot be blank")
        return v.strip()

class FoodItem(BaseModel):
    name: str
    quantity_g: float
    calories: float
    protein_g: float
    carbs_g: float
    fat_g: float
    confidence: float = Field(ge=0, le=1)   # how sure the USDA match was
    source: str                              # "ner+usda" | "image" | "fallback"

class MealResponse(BaseModel):
    items: list[FoodItem]
    totals: FoodItem | None = None
    warnings: list[str] = []                 # e.g. "quantity not parsed, assumed 1 serving"
💡 Senior Insight

The underrated win isn't validation — it's that the schema is the contract, the docs and the types simultaneously. One BaseModel generates the OpenAPI spec, so the frontend integrates without you writing a spec by hand and without the spec drifting from reality. Pydantic V2's core is written in Rust, which is why it's fast enough to sit in the request path without being a cost you think about.

File uploads: UploadFile vs bytes

🚨 Interview Trap

Declaring image: bytes = File(...) looks harmless and is a memory bomb — FastAPI reads the entire body into RAM before your function starts, so ten concurrent 20 MB uploads is 200 MB with no upper bound you control. UploadFile spools to disk past a threshold (~1 MB) and keeps memory flat. And neither enforces a size limit — a client can send 2 GB. Cap it at the reverse proxy (client_max_body_size) or check content-length yourself. Validate the actual image too: trusting content_type from the client is trusting the attacker.

Dependency injection with Depends

Auth, roles, and a singleton model loader 
from fastapi import Depends, HTTPException, status

# --- auth: one function, reused everywhere ---
async def current_user(token: str = Depends(oauth2_scheme)) -> User:
    try:
        payload = jwt.decode(token, SECRET, algorithms=["HS256"])
    except JWTError:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Invalid token")
    return await get_user(payload["sub"])

# --- roles: a dependency FACTORY, so it parameterizes cleanly ---
def require_role(*allowed: str):
    async def checker(user: User = Depends(current_user)) -> User:
        if user.role not in allowed:
            raise HTTPException(status.HTTP_403_FORBIDDEN, "Forbidden")
        return user
    return checker

@router.delete("/meals/{id}")
async def delete_meal(id: str, user: User = Depends(require_role("admin", "owner"))):
    ...

# --- apply to a whole router instead of 20 routes ---
router = APIRouter(prefix="/admin", dependencies=[Depends(require_role("admin"))])

# --- yield dependency: setup + guaranteed teardown ---
async def db_session():
    session = SessionLocal()
    try:
        yield session
    finally:
        session.close()     # runs even if the route raises
🛡️ SDE Defense

Across 20+ routes the pattern that scales is router-level dependencies plus dependency factories. Attach require_role("admin") once to the admin router and every route under it inherits the check — you cannot forget it on a new endpoint, because you'd have to actively register the route somewhere else. That's the same principle as a tenant-scoped repository: make the safe thing structural rather than remembered.

Two bonuses worth naming: dependencies are cached per request, so current_user resolving in three places decodes the token once. And because they're just functions, tests override them with app.dependency_overrides — no auth mocking, no monkeypatching.

The async def vs def rule

Route is…Declare asRuns on
Awaiting async I/O (httpx, async DB)async defEvent loop
Blocking I/O (requests, sync DB driver)defanyio threadpool
CPU-bound (PyTorch, spaCy, YOLO)defanyio threadpool
CPU-bound and heavy/longSeparate service or process poolElsewhere
🚨 Interview Trap

This is the counter-intuitive one, and it's a favourite: the "modern" choice is wrong. Writing async def around a synchronous model call blocks the entire event loop — every other request on that worker stalls for the full inference. Writing plain def lets FastAPI run it in a threadpool and the loop stays free.

So for CPU-bound inference, def is more concurrent than async def. The failure mode is nasty because it's invisible under light load and only appears as latency spikes in production.

Three correct shapes 
# 1. Sync inference — plain def. FastAPI threadpools it automatically.
@app.post("/predict")
def predict(req: MealTextRequest):
    return run_model(req.text)          # blocking, but off the loop

# 2. Async route that must call something blocking — offload explicitly.
@app.post("/analyze")
async def analyze(req: MealTextRequest):
    usda = await fetch_usda(req.text)                    # real async I/O
    result = await asyncio.to_thread(run_model, req.text) # blocking → thread
    return merge(usda, result)

# 3. Heavy CPU — a process pool escapes the GIL entirely.
pool = ProcessPoolExecutor(max_workers=2)

@app.post("/heavy")
async def heavy(req: Req):
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(pool, expensive_fn, req.data)

03 Flask architecture & contexts

The two contexts

 Application contextRequest context
Objectscurrent_app, grequest, session
LifetimePer app operation (usually per request)Exactly one request
HoldsConfig, DB handle, loaded modelHeaders, body, args
Outside a requestPush manually — CLI, scriptsUnavailable

Both are thread-local proxies. request is a global you can import anywhere, yet it resolves to this thread's request — which is exactly why Flask's synchronous, thread-per-request model is the assumption baked into its design.

🚨 Interview Trap

"Working outside of application context." Everyone hits it; few can explain it. It means you touched current_app or g when no context was pushed — typically in a background thread, a CLI command, or at import time. Fix: with app.app_context():.

The deeper version: g is not global state despite the name. It's per-context, so a value stashed in g during a request is gone in a background thread. People use it as a cache and are baffled when it's empty.

Blueprints

Blueprint + app factory + centralized errors 
from flask import Blueprint, jsonify

bp = Blueprint("chess_ai", __name__, url_prefix="/api")

@bp.post("/get_bot_move")
def get_bot_move():
    fen = request.get_json().get("fen")
    if not fen:
        raise BadRequest("fen is required")
    return jsonify(compute_move(fen))

def create_app(config=None):          # app factory — testable, no import-time globals
    app = Flask(__name__)
    app.config.from_object(config or "config.Production")
    CORS(app, origins=app.config["ALLOWED_ORIGINS"])
    app.register_blueprint(bp)

    @app.errorhandler(BadRequest)
    def handle_bad_request(e):
        return jsonify(error=str(e)), 400

    @app.errorhandler(Exception)      # catch-all: never leak a stack trace
    def handle_unexpected(e):
        app.logger.exception(e)
        return jsonify(error="Internal server error"), 500

    return app
🛡️ SDE Defense

Flask was the right call for Chess-AI precisely because the workload is CPU-bound and stateless. FastAPI's async advantage is worth nothing when the endpoint never waits on I/O — it computes a move and returns. Meanwhile Flask's synchronous per-worker model gives clean isolation: one slow search occupies one worker, and Gunicorn's --timeout kills a search that hangs without touching the others.

The endpoint is deliberately stateless — board in (FEN), move out. No session, no memory of the game. That's what lets it scale by adding workers, restart without losing anything, and be tested with a single curl.

04 Serving ML models in production

Load once, at startup

The single most common ML-serving bug is loading the model inside the request handler. A ResNet-50 checkpoint is seconds of disk read and hundreds of MB — per request that's catastrophic, and it usually ships because it works fine with one test user.

Lifespan loading + a correct inference path 
from contextlib import asynccontextmanager

ml = {}

@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup — runs once per worker process
    model = models.resnet50()
    model.fc = nn.Sequential(nn.Dropout(0.5), nn.Linear(2048, NUM_CLASSES))
    model.load_state_dict(torch.load(CKPT, map_location="cpu"))
    model.eval()                       # CRITICAL: disables dropout + BN updates
    ml["model"] = model
    ml["nlp"] = spacy.load("models/food_ner")
    yield
    ml.clear()                         # shutdown

app = FastAPI(lifespan=lifespan)

@app.post("/predict")                  # plain def → threadpool
def predict(file: UploadFile = File(...)):
    img = preprocess(Image.open(file.file).convert("RGB"))
    with torch.inference_mode():       # no autograd graph, no grad memory
        logits = ml["model"](img.unsqueeze(0))
        probs  = torch.softmax(logits, dim=1)
        conf, idx = probs.max(1)
    return {"label": CLASSES[idx.item()], "confidence": round(conf.item(), 4)}
                                       # .item() → Python float, drops the tensor
🚨 Interview Trap

Two one-line bugs that both produce silently wrong or slowly dying services:

  • Forgetting model.eval() — dropout stays active at inference, so the same image returns different predictions on each call. Nothing errors. You just have a randomly wrong model.
  • Forgetting torch.no_grad() / inference_mode() — PyTorch builds an autograd graph for every forward pass and holds the activations. In a long-running server that's a steady memory climb that eventually OOMs, hours or days after deploy.

inference_mode() is the stronger, newer version of no_grad() — same intent, a bit faster. Knowing both names is worth a point.

📊 ML / Data Eng Defense

Memory hygiene checklist for a long-running service — say these as a list and it lands:

  • eval() + inference_mode() — non-negotiable.
  • Never accumulate tensors in a module-level list or cache. Call .item() or .detach().cpu() before storing anything, or you keep the whole graph alive by holding one tensor.
  • On GPU, torch.cuda.empty_cache() releases cached blocks — but understand it frees the allocator's cache, not leaked references. It's a symptom-reliever, not a fix.
  • Bound concurrency: N parallel inferences = N copies of activation memory. A semaphore around the model is cheaper than an OOM.
  • Pin your batch size. Variable batches fragment the allocator over time.

Fallback cascades

Every ML service should degrade rather than fail. The pattern across all your projects is the same three tiers:

Aggressive timeout + backoff calling an upstream 
import httpx, asyncio

TIMEOUT = httpx.Timeout(6.0, connect=2.0)   # match RecrutAI's 6s ceiling

async def call_upstream(payload, retries=2):
    delay = 1.0
    async with httpx.AsyncClient(timeout=TIMEOUT) as client:
        for attempt in range(retries + 1):
            try:
                r = await client.post(UPSTREAM, json=payload)
                r.raise_for_status()
                return r.json()
            except (httpx.TimeoutException, httpx.HTTPStatusError):
                if attempt == retries:
                    return None            # caller runs the deterministic fallback
                await asyncio.sleep(delay)
                delay *= 2                 # 1s → 2s
💡 Senior Insight

Retries make things worse when the upstream is overloaded rather than flaky — three clients each retrying twice is triple the load on a service already struggling. That's what a circuit breaker fixes: after N consecutive failures the breaker opens and calls fail instantly for a cooldown, going straight to the fallback without touching the network. It gives the upstream room to recover instead of pinning it down. Retries handle transient blips; breakers handle sustained outages. Naming both, and when each applies, is the senior answer.

05 Interview defense bank

One-line reason → supporting mechanic → the trade-off you accepted.

Track A — SDE

A · Q1
1. Why a Flask microservice for the chess engine rather than child processes from Node?

Because spawning a process per move pays startup cost on every single request. A child process must boot a Python interpreter, import chess libraries and initialize Stockfish — that overhead is comparable to or larger than the search itself, and it repeats for every move.

A long-lived Flask service pays that cost once at startup. It also gets you a real HTTP contract instead of parsing stdout, independent deploys and restarts, the ability to scale engine capacity separately from the game server, and testability with a single curl.

Trade-off: a network hop (milliseconds, irrelevant next to search time) and a second service to run. The decisive point is that the engine is stateless — FEN in, move out — so it scales by adding workers and loses nothing on restart.

A · Q2
2. How do you structure JWT auth and RBAC cleanly across 20+ FastAPI routes?

Dependency factories plus router-level dependencies — so the check is attached to the router, not repeated per route.

current_user decodes and validates the token. require_role(*allowed) is a factory returning a dependency that itself depends on current_user — so roles compose on top of auth without duplicating decode logic. Then APIRouter(dependencies=[Depends(require_role("admin"))]) covers every route underneath at once.

Why this beats decorators or middleware: dependencies are cached per request (token decodes once even if three dependencies need the user), they appear in the OpenAPI schema so the docs show which routes need auth, and they're overridable in tests via app.dependency_overrides — no monkeypatching.

The structural argument: a new route added under the admin router is protected by default. You'd have to work to make it insecure.

A · Q3
3. 20 MB image via UploadFile vs bytes — what happens to memory?

bytes: FastAPI reads the entire body into RAM before your function is called. One request is 20 MB; ten concurrent is 200 MB, growing linearly with no ceiling you control. That's an availability bug an attacker can trigger deliberately.

UploadFile: wraps Python's SpooledTemporaryFile — kept in memory up to a threshold (~1 MB), then transparently spilled to a temp file on disk. Memory stays roughly flat regardless of file size, and you additionally get filename and content_type.

What neither does: enforce a maximum. A client can send 2 GB either way. Real protection is a body-size cap at the reverse proxy plus a content-length check, and validating the file is actually an image by decoding it — content_type is client-supplied and therefore attacker-controlled.

For a detection endpoint you also want to resize immediately after decode, because a 20 MP image decoded to a tensor is far larger in RAM than the 20 MB on the wire.

A · Q4
4. How do you size Gunicorn/Uvicorn workers in a memory-limited container?

For an ML service, workers are bounded by memory, not by cores. Start from the arithmetic: worker_count × model_size must fit inside the container limit with headroom for activations and request buffers. A 500 MB model in a 2 GB container means 2 workers, not 8 — and the standard (2 × cores) + 1 heuristic is for I/O-bound web apps, where it's fine and here it's actively harmful.

Concretely: gunicorn -k uvicorn.workers.UvicornWorker --workers 2 --timeout 120. Gunicorn for process supervision and restarts, Uvicorn workers for async. Set the timeout above worst-case inference or Gunicorn will kill mid-inference requests.

Then bound concurrency inside each worker — a semaphore around the model, so N threadpool threads don't hold N copies of activation memory. Queuing under load is the correct failure mode; OOM-killing is not.

And set the container limit explicitly, because otherwise the OOM killer takes a worker down and the symptom looks like a random crash rather than a memory problem.

A · Q5
5. How would you implement a circuit breaker between a Node gateway and a FastAPI ML service?

Three states. Closed — requests flow, failures counted. After N consecutive failures (or a failure rate over a window), the breaker opens: every call fails instantly with no network attempt, straight to the fallback. After a cooldown it goes half-open and lets one probe through — success closes it, failure re-opens it with a longer cooldown.

Why not just retries: retries assume the failure is transient. If the ML service is overloaded, every retry is more load on something already drowning — you turn a slow service into a dead one. The breaker does the opposite: it removes load so recovery is possible.

What "fail fast" buys you: without a breaker, an ML service that hangs makes every gateway request wait the full 6-second timeout, so the gateway's own connection pool fills with waiting requests and the outage spreads upstream. That's cascading failure, and fast rejection is what stops it.

Practically: opossum on the Node side wrapping the call, a timeout below the client's patience threshold, and a deterministic fallback per endpoint — cached last result, rule-based response, or an honest "inference unavailable" with a 503. Emit breaker state as a metric; an open breaker is the alert you actually want to page on.

Track B — ML / AI / Data Engineering

B · Q1
1. Sync CPU inference in FastAPI — async def or plain def?

Plain def. And the reason is the whole answer.

async def is a promise to the event loop that you'll yield at every await. A PyTorch forward pass or a spaCy parse contains no awaits — it just runs. So the loop is stuck inside your function for the entire inference, and every other request on that worker is frozen, including health checks.

Declare it def and FastAPI detects the sync function and runs it in the anyio threadpool (40 threads by default). The loop stays free to accept and serve other requests while inference happens on a worker thread.

The counter-intuitive summary: for CPU-bound work, def gives you more concurrency than async def. The "more modern" keyword is the wrong one.

The honest limit: threads don't escape the GIL, so this buys responsiveness, not parallel throughput — PyTorch releasing the GIL inside C++ kernels is what provides some real overlap. For genuine CPU parallelism you need a process pool or separate workers. And the failure mode of getting it wrong is nasty: fine in dev with one user, latency spikes in production.

B · Q2
2. How does one JSON schema serve both the spaCy NER path and the image classifier?

By making USDA the convergence point. Both paths are treated as hypothesis generators that output the same thing: a food name and a confidence. Text goes free-form → NER extracts food entities → rule parser extracts quantities. Image goes upload → classifier → predicted food label. Neither path produces a nutrition number.

Then a single resolution stage takes (name, quantity) and matches it against USDA FoodData Central, returning the canonical item with per-100g macros. Portion scaling happens once, in one place: macro × grams / 100. So both routes emit the identical FoodItem shape, differing only in a source field and their confidence value.

Why this design holds up: nutrition numbers come from a government database, never from a model. Adding a third input path — barcode scan, voice — means writing one more hypothesis generator, not touching the response schema or the frontend. And Pydantic enforces the shape, so a path that returns something malformed fails at the boundary rather than reaching a client.

Be precise about the image path if asked: the trained ResNet-50 lives in its own service, and the food-logging API can also route images to a managed vision provider. Two options behind one schema — which is exactly the point of resolving through USDA.

B · Q3
3. What happens when concurrent requests hit /detect running YOLO?

Walk the path in order — that structure is what they're marking.

(1) Uvicorn accepts all connections immediately; the event loop parses multipart headers and spools each upload to SpooledTemporaryFile, so memory stays flat even with several large images in flight.

(2) The route is sync def, so each request is dispatched to an anyio threadpool thread. The loop is now free again.

(3) Here's the real constraint: the threads all share one GIL and one model instance. Ultralytics releases the GIL inside its C++/ATen kernels, so there's partial overlap, but Python-level pre/post-processing serializes. You do not get N× throughput from N threads.

(4) Memory scales with concurrency — each in-flight inference holds its own activations. Ten simultaneous requests is ten sets of intermediate tensors.

What I'd do about it: a semaphore capping concurrent inferences (queue rather than thrash), and for real load, batching — collect requests arriving within a short window and run one batched forward pass, since GPU/vectorized inference on a batch of 8 costs far less than 8 separate passes. Add a queue depth metric so you can see saturation before users do.

Also worth saying: a shared model object is fine for read-only inference in eval() mode. It would not be if anything mutated model state per request.

B · Q4
4. How do you prevent memory leaks serving PyTorch in a long-running service?

The main leak is autograd. By default every forward pass builds a computation graph and retains intermediate activations for a backward pass that never comes. In a server that runs for days, that's a steady climb ending in OOM — and it's invisible in a short test.

Fix: wrap inference in torch.inference_mode() (or no_grad()) and call model.eval() at load. Two different jobs, both required: eval() switches dropout and BatchNorm to inference behaviour; inference_mode() stops graph construction.

The second leak is retained references. Storing a raw output tensor in a cache or metrics list keeps its entire graph alive. Always .item() for scalars or .detach().cpu() before storing — one held tensor can pin hundreds of MB.

On GPU: torch.cuda.empty_cache() returns cached blocks to the driver, but be precise that it frees the allocator cache, not leaked references — it makes nvidia-smi look better without fixing a real leak. Use torch.cuda.memory_allocated() to tell the difference.

Operationally: bound concurrency so activation memory is capped, log RSS per request, and keep a worker max-requests recycle as a safety net — restarting periodically is a legitimate belt-and-braces measure, not an admission of defeat.

B · Q5
5. Why FastAPI over Flask for Nutri-Vision, and what did Pydantic actually do?

Because the endpoint's dominant cost is waiting, not computing. A meal-logging request calls out to USDA FoodData Central and potentially a vision provider — mostly network wait. Flask would hold an entire worker idle for each of those; FastAPI's event loop overlaps them, so one worker serves many concurrent requests.

Pydantic did three concrete things:

  • Guarded the boundary — malformed input returns 422 with a field-level error path before reaching the NLP pipeline. Without it, bad input surfaces as a confusing exception deep inside the extractor.
  • Made portion scaling safe — servings: float = Field(gt=0, le=20) means the scaling multiplier can never be zero or negative, so a malicious or accidental value can't produce absurd macro numbers. Constraints on the input are cheaper than defensive checks scattered through the math.
  • Generated the contract — one schema produced the OpenAPI docs, so the frontend integrated without a hand-written spec that drifts.

The honest caveat: FastAPI's async advantage disappears the moment you put synchronous model inference in the same process — which is exactly why the ResNet-50 classifier runs as its own service rather than inside this API. Same reasoning as Chessify: don't put CPU work on an I/O event loop.
