Core ML/DL Concepts

Overfitting / Underfitting & the Bias-Variance Tradeoff

Underfitting: the model is too simple to capture the real pattern — high error on both training and test data. Overfitting: the model has essentially memorized the training data, including its noise — low training error, high test error.

CP-flavored intuition: underfitting is like a solution that only handles the easiest subtask and gets partial score everywhere; overfitting is like hardcoding the exact sample test cases instead of solving the general problem — it aces the samples and fails every hidden test case with different input.

Bias is error from wrong assumptions (an underfit model — too rigid). Variance is error from sensitivity to the specific training data (an overfit model — too flexible, different training samples would produce wildly different models). You can't drive both to zero with a fixed amount of data and model capacity — more capacity reduces bias but raises variance, and vice versa; the sweet spot is what techniques like regularization, dropout, and early stopping are trying to find.

📌 Likely to be asked

"How do you detect overfitting in practice?" → Training loss keeps dropping while validation loss starts rising — that widening gap between the two curves is the signature. The fix set: more data, data augmentation, regularization (L2, dropout), or a simpler model.

Gradient Descent

Training a model means finding parameters that minimize a loss function. Gradient descent does this iteratively: compute the gradient (the direction of steepest increase in loss with respect to each parameter), then step the parameters a small amount in the opposite direction, repeat.

CP-flavored intuition: think of it as hill-climbing / local search over a continuous parameter space instead of a discrete one — you can't enumerate all possible weight settings (infinite, continuous), so instead of trying every neighbor state, calculus tells you directly which direction is downhill and by how much (the gradient), and the learning rate is your step size.

# one parameter update, conceptually
gradient = compute_gradient(loss, params)
params = params - learning_rate * gradient
📌 Likely to be asked

"What happens if the learning rate is too high or too low?" → Too high: steps overshoot the minimum and loss can diverge/oscillate instead of converging. Too low: convergence is extremely slow and can get stuck in a shallow local dip. This is why adaptive optimizers (Adam, RMSProp) that adjust the effective step size per-parameter are the default over plain gradient descent in practice.

Backpropagation Basics

A neural network is a chain of function compositions (layer 1 → layer 2 → ... → loss). Backpropagation is just the chain rule applied systematically to that chain: compute how much the final loss changes with respect to each layer's output, working backward from the loss to the first layer, reusing intermediate results instead of recomputing them from scratch for every single weight.

CP-flavored intuition: it's the same idea as memoized DP — instead of recomputing "how does this weight affect the final loss" independently for every one of millions of weights (which would re-walk the whole forward computation each time), you compute and cache each layer's local gradient once, then combine cached values going backward. Same principle as reusing subproblem results instead of recomputing them.
🎯 Common follow-up

"What's the vanishing gradient problem?" → In a deep network, gradients are products of many chain-rule terms; if those terms are consistently <1 (common with sigmoid/tanh activations), the product shrinks toward zero across many layers, so early layers barely update. ReLU-family activations and architectures like residual connections (skip connections that let gradients bypass layers) are the standard fixes.

CNN Basics for Vision Tasks

A convolution slides a small learnable filter (kernel) across the image, computing a weighted sum at each position — the same filter is reused across the whole image, so the network learns "detect this pattern anywhere" instead of a separate detector per pixel location.

CP-flavored intuition: it's a sliding-window operation, exactly like a sliding-window sum/max over an array, just 2D and with a learned weight vector instead of a fixed sum. Pooling (max/average over small regions) is a downsampling/compression step — reduces spatial resolution while keeping the strongest signal, cutting computation for deeper layers.

Stacked conv layers build a feature hierarchy: early layers detect edges/textures, middle layers detect parts (an eye, a wheel), deeper layers detect whole objects — each layer operates on the previous layer's output, building up abstraction the same way composed functions build up complexity.

📌 Likely to be asked

"Why convolutions instead of a fully-connected layer for images?" → Parameter sharing (the same small filter reused everywhere means far fewer weights than connecting every pixel to every neuron) and translation invariance (a learned pattern is detected regardless of where it appears in the image) — both of which a fully-connected layer doesn't give you.

NLP / LLM Concepts

Embeddings

An embedding maps a discrete token (a word, a sentence, an image) to a dense vector of real numbers, positioned in a continuous space such that semantic similarity becomes geometric closeness — "king" and "queen" end up near each other; "king" and "banana" don't.

CP-flavored intuition: the opposite goal of a hash function. A hash wants unrelated inputs to scatter apart and even similar inputs to land far apart (avoiding collisions); an embedding wants related concepts to land close together on purpose — it's a similarity-preserving mapping, not a collision-avoiding one.

This is what makes semantic search possible: to find documents "about" a query, you don't string-match keywords — you embed the query and find nearby vectors.

Transformers Overview

Before transformers, sequence models (RNNs) processed tokens one at a time, in order — inherently sequential, slow to train, and prone to losing information over long distances. Transformers process the whole sequence in parallel and use an attention mechanism (below) to let every token directly look at every other token, regardless of distance, in a single step.

Two broad shapes: encoder-decoder (original transformer, translation-style tasks — encode the input fully, then generate output attending back to it) and decoder-only (GPT-style — generate one token at a time, each new token attending only to what came before it). Almost every modern LLM you'd discuss in an interview is decoder-only.

📌 Likely to be asked

"Why did transformers replace RNNs for most NLP tasks?" → Parallelizable training (no need to wait for token t-1 before processing token t, so you can use all your GPU compute at once) and no long-range information bottleneck (attention connects distant tokens directly, instead of information having to survive being passed through every intermediate step like in an RNN).

Attention Mechanism (conceptual)

For each token, attention computes a weighted average of every other token's representation, where the weights reflect "how relevant is that other token to understanding this one right now." Concretely, each token produces a Query (what am I looking for), a Key (what do I contain, for others to match against), and a Value (the actual content to pass along if matched). A token's new representation is the weighted sum of all Values, weighted by how well its Query matches every other token's Key.

CP-flavored intuition: like computing, for every array element, a weighted sum over all other elements — but instead of fixed weights (like a convolution kernel) the weights are computed dynamically per-input, based on a similarity score between each pair. It's an all-pairs relevance computation, run fresh for every input sequence.

"Self-attention" means a sequence attending to itself (used to build context-aware representations); "multi-head" just means running several of these attention computations in parallel with different learned Q/K/V projections, so different heads can specialize in tracking different kinds of relationships (e.g. one head tracks grammatical subject-verb links, another tracks coreference).

RAG Architecture

Retrieval + Generation Pipeline

RAG (Retrieval-Augmented Generation) answers a question by first retrieving relevant source text, then generating an answer grounded in that retrieved text — instead of relying purely on what the LLM memorized during pretraining.

1. User asks a question
2. Embed the question → a query vector
3. Search a vector store for the most similar document chunks (top-k)
4. Stuff those chunks into the LLM's prompt as context:
     "Answer using ONLY this context: {retrieved_chunks}
      Question: {user_question}"
5. LLM generates an answer grounded in the retrieved text
📌 Likely to be asked

"What's the single biggest failure mode of a naive RAG pipeline?" → Retrieval quality caps answer quality — if step 3 pulls irrelevant or incomplete chunks, the LLM either hallucinates to fill the gap or confidently answers from the wrong context. Debugging a bad RAG answer should always start by checking what was actually retrieved, before assuming the LLM itself is the problem.

Vector Databases

A vector database stores embeddings and answers "which stored vectors are closest to this query vector" efficiently at scale — that's approximate nearest neighbor (ANN) search, since exact nearest-neighbor search over millions of high-dimensional vectors is too slow to do by brute force on every query.

CP-flavored intuition: conceptually similar to a spatial index (like a KD-tree) that lets you avoid comparing against every point — vector DBs typically use graph-based structures (HNSW) instead, trading a small amount of accuracy for large speed gains, which is why it's "approximate" nearest neighbor, not exact.

Common choices: FAISS (library, not a full DB — good for local/prototype use), Pinecone/Weaviate/Chroma (managed or self-hosted full vector DBs with metadata filtering, persistence, and APIs).

Chunking Strategies

Source documents get split into chunks before embedding, because (a) LLM context windows are limited, and (b) embedding a whole long document into one vector blurs together too many distinct ideas to be useful for precise retrieval.

StrategyHowTrade-off
Fixed-sizeSplit every N tokens/characters, with some overlapSimple, fast — but can cut a sentence or idea in half at the boundary
Sentence/paragraph-basedSplit on natural boundariesPreserves meaning better; chunk sizes become uneven
Semantic chunkingSplit where embedding similarity between adjacent sentences drops (topic shift)Best retrieval relevance; more expensive to compute upfront

Overlap (e.g. a 50-token overlap between consecutive chunks) is the standard fix for the fixed-size boundary problem — it means an idea split across a chunk boundary still appears whole in at least one chunk.

💼 Resume tie-in — PDF Query Engine

"For the PDF Query Engine, RAG was the natural fit over fine-tuning because the whole point was answering questions about whatever PDF a user uploads — content the model has never seen and that changes per user session. Fine-tuning would mean retraining per document, which doesn't make sense for arbitrary user-uploaded content; RAG lets the same deployed system handle any new document by just embedding and indexing it, with answers traceable back to the actual source text instead of the model's memorized parameters."

LangChain / CrewAI Fundamentals

Chains

A chain is a fixed sequence of steps wired together — e.g. prompt template → LLM call → output parser → next prompt. The control flow is decided by you at build time, not by the model at run time.

# conceptual LangChain-style chain
prompt = PromptTemplate("Summarize this document: {text}")
chain = prompt | llm | output_parser
result = chain.invoke({"text": document_text})

Think of a chain as a fixed pipeline — function composition where each stage's output is the next stage's input, always in the same order.

Agents

An agent is different from a chain in one key way: the LLM itself decides which tool to call, in what order, and when to stop — the control flow is dynamic, driven by the model's own reasoning at each step, instead of hardcoded by you.

Pattern to know: ReAct (Reason + Act). The agent loops: think about what to do next → pick a tool and call it → observe the result → think again → ... → produce a final answer once it decides it has enough information.
🎯 Common follow-up

"When would you use a plain chain instead of an agent?" → Whenever the steps are actually fixed and known in advance — an agent's dynamic decision-making adds latency, cost (more LLM calls to reason at each step), and unpredictability you don't need if the task genuinely always follows the same steps in the same order.

Multi-Agent Orchestration (CrewAI)

CrewAI structures a task around multiple specialized agents, each with a defined role, goal, and backstory (a system-prompt-like persona), coordinated by a process that passes outputs between them — e.g. a "Researcher" agent gathers information, hands it to a "Writer" agent that drafts a response, which a "Reviewer" agent checks before finalizing.

Intuition: like a small team with a manager delegating subtasks to specialists, instead of one generalist doing everything — each agent's prompt is narrower and more focused, which tends to produce better results per-step than asking one agent to do the whole task in one shot.
💼 Resume tie-in — PDF Query Engine

"The multi-agent setup split the RAG pipeline's responsibilities instead of using one monolithic prompt — one agent focused on retrieval/context assembly, another focused on composing the final answer from that context, which made it easier to debug which stage was responsible when an answer came back wrong: a retrieval problem (wrong chunks) versus a generation problem (right chunks, bad answer)."

🎯 Common follow-up

"How would you reduce hallucination in your RAG system?" → The levers, roughly in order of impact: (1) improve retrieval quality first — better chunking/embeddings so the right context actually gets retrieved, since no prompting trick fixes bad retrieval; (2) constrain the generation prompt explicitly ("answer only using the provided context; say 'not found in the document' if the answer isn't present"); (3) add a citation/verification step where the agent points to which retrieved chunk supports each claim, making unsupported claims visible; (4) lower generation temperature for more deterministic, less "creative" completions on factual QA.

YOLOv5 Fundamentals

Object Detection Basics

Object detection = localization (where is it — a bounding box) + classification (what is it) for potentially multiple objects in one image. YOLO ("You Only Look Once") is a single-shot detector: one forward pass through the network predicts all boxes and classes at once, rather than a two-stage approach (first propose candidate regions, then classify each one separately, like R-CNN-family models) — which is the core reason YOLO is fast enough for real-time/edge use.

Conceptually, the image is divided into a grid, and each grid cell predicts: is there an object centered here, what box dimensions, and what class — all as one big regression problem solved in a single network pass.

Anchor Boxes

Instead of predicting a bounding box's width/height from scratch (a hard, unconstrained regression problem), classic YOLOv5 predicts an offset from a set of predefined anchor box shapes — reference box sizes (e.g. tall-and-narrow, wide-and-short, square) chosen ahead of time to match the typical object shapes in the training data (often via k-means clustering on the training set's ground-truth boxes). The network only has to learn small adjustments to a reasonable starting guess, not the raw dimensions.

📌 Likely to be asked

"Are all YOLO/Ultralytics models anchor-based?" → No — this is a real and current distinction worth knowing: classic YOLOv5 is anchor-based, but Ultralytics' newer unified models (YOLOv8, and the "u"-suffixed YOLOv5u variants served through the same ultralytics package) use an anchor-free, decoupled detection head instead — predicting object centers and sizes directly rather than offsets from predefined anchor shapes. Worth checking which head a specific weights file actually uses before describing "anchor boxes" as a certainty.

Non-Max Suppression (NMS)

A single object often gets multiple overlapping candidate boxes predicted around it (from neighboring grid cells/anchors all firing on the same object). NMS cleans this up: sort all candidate boxes by confidence score, keep the highest-scoring one, then discard any other box whose overlap (IoU — Intersection over Union) with it exceeds a threshold; repeat for the remaining boxes.

CP-flavored intuition: a greedy interval-scheduling-style algorithm — repeatedly pick the best-scoring remaining candidate, eliminate everything that conflicts (overlaps too much) with it, and continue until nothing's left.

Detecting "person" for occupancy counting is close to the best-case scenario for fine-tuning (or even zero-shot use of a COCO-pretrained model directly) — "person" is already one of COCO's 80 classes, so the pretrained model has seen enormous numbers of people in varied poses/lighting before you show it a single image from your own setup.

What the repo's code actually shows

The detection service (SahYatri-DetectionAI/main.py) is a FastAPI app that loads a YOLO model via the ultralytics package and exposes a /detect endpoint:

from ultralytics import YOLO

model = YOLO('yolov5xu.pt')  # stock Ultralytics-hosted weights

def count_people(image: Image.Image) -> int:
    """Run YOLO inference and count people."""
    results = model(image)
    return sum(1 for box in results[0].boxes if box.cls == 0)  # COCO class 0 = person

@app.post("/detect")
async def detect_occupancy(image: UploadFile = File(...), camera_id: str = Query(...)):
    img = process_image(await image.read())
    person_count = count_people(img)
    send_to_apis(camera_id, person_count)  # forwards to the bus API from the last doc
    return JSONResponse({"camera_id": camera_id, "occupancy": person_count, "capacity": MAX_CAPACITY})

The Raspberry Pi's script (SahYatri-Hardware/capture.py) does not run YOLO locally — it captures a still frame every few seconds and POSTs it to this detection service over HTTP:

API_URL = "http://192.168.137.1:8000/detect"  # a LAN companion device, not on-device inference
CAPTURE_INTERVAL = 5  # seconds — periodic snapshots, not a continuous video feed

def capture_and_process_image():
    picam2.switch_mode_and_capture_file(still_config, image_path)
    with open(image_path, "rb") as img_file:
        response = requests.post(API_URL, files={"image": img_file}, params={"camera_id": CAMERA_ID})
        data = response.json()
        update_system_status(data["occupancy"], data["capacity"])  # updates an I2C LCD display

def update_system_status(occupancy, capacity):
    if occupancy >= capacity: system_status = "FULL!"
    elif occupancy >= capacity * 0.8: system_status = "NEAR FULL"  # the closest thing to a threshold tier in the code
    else: system_status = "OK"

The Pi additionally runs an MJPEG video stream endpoint with an on-screen status overlay, an I2C LCD readout, and IP-based location lookup — a genuinely solid embedded-systems piece of the project independent of the detection model question below.

⚠️ Reconcile before your interview — this matters

The resume framing given for this deep-dive ("fine-tuned YOLOv5n, deployed on the Pi at 15 FPS, adaptive thresholding, 90%+ accuracy") and what's actually in this repo don't line up on several specific, checkable details. Better to know this now than get an unexpected follow-up in the room:

⚠️ Model variant

The code loads yolov5xu.pt — the extra-large ("x") variant, the opposite end of the size spectrum from nano ("n"). YOLOv5n is ~1.9M parameters and built specifically for edge/mobile use; YOLOv5x is ~87M parameters and is the most accurate but slowest, heaviest variant in the family — a poor fit for a Raspberry Pi 4 specifically. If a nano model was actually fine-tuned and used somewhere, that code/weights file isn't in this repo, or a different version was deployed than what's committed here.

⚠️ Where inference actually runs

The Pi never loads a YOLO model — it captures a photo and POSTs it over HTTP to 192.168.137.1:8000, a separate device on the same local network (that IP pattern is a typical Windows Internet-Connection-Sharing gateway address, consistent with a laptop tethered to the Pi). Inference is running on that companion machine, not "on the Pi" in the sense of on-device edge inference.

⚠️ Frame rate

CAPTURE_INTERVAL = 5 means one still image is captured and sent for detection every 5 seconds — roughly 0.2 detections/sec, not 15 FPS. The video stream endpoint (/video_feed) does run continuously for the live dashboard view, but that's a raw camera feed with a text overlay, not continuous YOLO inference — the detection path and the video-streaming path are separate in this code.

⚠️ Fine-tuning and accuracy validation

There's no training/fine-tuning script, custom dataset, or evaluation code (confusion matrix, precision/recall, mAP) anywhere in the repo — main.py loads the stock pretrained COCO weights directly and filters to class 0 (person). If fine-tuning and a validation pass genuinely happened, it likely lived in a separate notebook/script (e.g. Colab) that wasn't committed to this repo — worth tracking that down and having the actual training run/metrics ready to describe if asked, rather than the claim resting on this codebase alone.

None of this means the underlying achievement is false — it likely means the committed repo reflects an earlier or partial snapshot of the system, and the fine-tuning/on-device/threshold work happened in a part of the project that isn't in what's public. The fix before an interview is simple: pin down exactly which claims you can back with an artifact (a weights file, a training notebook, a benchmark log) versus which ones need re-checking or softening.

What "adaptive thresholding" and "90%+ accuracy" would mean here — and how to validate them properly

Useful to have these concepts crisp regardless of exactly what's in the current repo, since they're reasonable, defensible design choices for this problem even if the current code shows a simpler static rule.

📌 What adaptive thresholding would concretely mean

The current code uses one fixed confidence threshold for "is this a person" regardless of conditions. A genuinely adaptive threshold would adjust that confidence cutoff based on context — e.g. lowering it in low-light frames where the model's confidence scores run systematically lower for real detections, or tuning it per-camera if different bus cameras have different angles/lighting. The static 80%/100% capacity bands seen in update_system_status are a threshold on the output count, not on detection confidence — a different (and much simpler) kind of "threshold" than what the phrase usually implies for a detection model.

🎯 Common follow-up — be ready with a real methodology

"How did you validate 90%+ accuracy?" → The defensible way to answer this, whether or not this exact validation was run: collect a held-out set of real bus images with manually counted ground-truth occupancy, run the model on each, and compare predicted vs. actual counts — reporting something like mean absolute count error or percentage of frames within ±1 of the true count (person-counting accuracy is usually measured this way, not via a classification-style accuracy percentage, since the task is a count, not a single label). If pushed on the specific number, the honest fallback is describing the methodology precisely rather than restating the headline figure — an interviewer respects "here's exactly how I'd measure that" far more than an unverifiable number.
