Node.js Fundamentals

Event Loop & libuv

Node.js runs your JS on a single thread, but I/O (file system, network, DNS, timers) is delegated to libuv, a C library that manages a thread pool and OS-level async APIs (epoll/kqueue/IOCP) under the hood. The event loop is what pulls completed work off those queues and runs your callbacks, one phase at a time.

PhaseRuns
timerssetTimeout / setInterval callbacks whose threshold has elapsed
pending callbacksSome system-level callbacks deferred from the previous loop
pollFetches new I/O events (this is where most callbacks — file reads, socket data — execute); blocks here if nothing else is queued
checksetImmediate() callbacks
close callbackssocket.on('close', ...) etc.

process.nextTick() and resolved Promise .then() callbacks (microtasks) are not a loop phase — they drain completely between every phase transition, which is why they always run before the next timer/I/O callback.

📌 Likely to be asked

"What's the output order of setTimeout(fn, 0), setImmediate(fn), and Promise.resolve().then(fn)?" → Microtask (Promise) always drains first, then it depends on context: inside an I/O callback, setImmediate reliably fires before setTimeout(0); at the top level, order between the two timers isn't guaranteed.

Non-blocking I/O & the Single-Threaded Model

"Single-threaded" refers only to your JS execution — one call stack, no shared-memory race conditions between your callbacks. Actual I/O work (disk, network, some crypto/zlib operations) runs off-thread via libuv's thread pool (default size 4) or native async OS calls, and the result comes back onto the main thread as a queued callback.

⚠️ Interview trap

Non-blocking I/O does not mean CPU-bound work is free. A synchronous while loop, heavy JSON parsing, or bcrypt.hashSync still blocks the single thread and stalls every other request being served — that's what worker threads / clustering / offloading to a queue are for, not Node's async I/O model.

Callbacks vs Promises vs async/await

// Callback — "error-first" convention, can nest into callback hell
fs.readFile("a.txt", (err, data) => {
  if (err) return handleErr(err)
  fs.readFile("b.txt", (err2, data2) => { /* nested... */ })
})

// Promise — chainable, still verbose for sequential branching
readFileAsync("a.txt")
  .then(data => readFileAsync("b.txt"))
  .catch(err => handleErr(err))

// async/await — same Promise machinery, synchronous-looking control flow
try {
  const data = await readFileAsync("a.txt")
  const data2 = await readFileAsync("b.txt")
} catch (err) { handleErr(err) }

async/await is syntactic sugar over Promises — it doesn't add new concurrency, it just makes sequential async code read top-to-bottom and lets you use try/catch for errors instead of .catch() chains.

⚠️ Interview trap

Awaiting independent async calls sequentially is a common perf bug: await a(); await b(); serializes two calls that could run in parallel. Use await Promise.all([a(), b()]) when they don't depend on each other.

Streams

Streams process data in chunks instead of loading a whole file/response into memory — essential for large files or long-lived connections. Four types: Readable (source, e.g. file read), Writable (sink, e.g. file write/HTTP response), Duplex (both, e.g. a TCP socket), Transform (duplex that modifies data in transit, e.g. gzip).

// Streaming a large file to an HTTP response without buffering it all in memory
app.get("/video", (req, res) => {
  fs.createReadStream("movie.mp4").pipe(res)
})
🎯 Common follow-up

"Why not just fs.readFile and send the whole buffer?" → Memory: a readFile loads the entire file into RAM before responding, so N concurrent large downloads means N full copies in memory; a stream only ever holds a small chunk at a time and applies backpressure automatically if the client is slow to consume.

Clustering

Since Node is single-threaded, one process can only use one CPU core. The cluster module forks multiple worker processes (typically one per core) that share the same server port via the OS, letting you scale across cores on one machine — each worker is a fully separate process with its own event loop and memory (no shared state).

const cluster = require("cluster")
const os = require("os")

if (cluster.isPrimary) {
  os.cpus().forEach(() => cluster.fork())
  cluster.on("exit", () => cluster.fork()) // respawn on crash
} else {
  require("./server") // each worker runs its own copy of the app
}
⚠️ Interview trap

Clustering breaks anything relying on in-memory shared state across requests — e.g. an in-process WebSocket room map or rate-limit counter — because each worker has its own memory. That's why real-time apps behind a cluster (or multiple server instances) need an external broker like Redis (the Socket.IO Redis adapter is the standard fix) to synchronize state across processes.

Express.js

Middleware

A middleware is a function (req, res, next) that runs in the order it's registered, and can inspect/mutate req/res, end the request, or call next() to pass control along. This is the entire mental model of Express — routing itself is just middleware scoped to a method+path.

app.use((req, res, next) => {
  console.log(`${req.method} ${req.path}`)
  next() // forgetting this hangs the request forever
})

app.use("/admin", requireAuth) // scoped to a path prefix
⚠️ Interview trap

Middleware order matters and is a classic gotcha: registering a route before express.json() means req.body is undefined in that route; registering an auth middleware after the route it's meant to protect means it never runs at all.

Routing

express.Router() creates a mini, mountable app — the standard way to split routes into files by resource instead of dumping everything in one server.js.

// routes/users.js
const router = express.Router()
router.get("/:id", getUser)
router.post("/", createUser)
module.exports = router

// server.js
app.use("/api/users", require("./routes/users")) // → GET /api/users/:id

Error Handling

Express recognizes an error-handling middleware purely by arity — it must declare exactly four parameters, (err, req, res, next) — and it must be registered last, after all routes.

// async route errors must be forwarded manually (pre-Express 5) or via a wrapper
app.get("/thing", async (req, res, next) => {
  try { res.json(await getThing()) }
  catch (err) { next(err) } // skips to the error handler below
})

app.use((err, req, res, next) => {
  console.error(err)
  res.status(err.status || 500).json({ error: err.message })
})
📌 Likely to be asked

"What happens if an async route handler throws and you don't catch it?" → In Express 4, an unhandled rejection inside an async handler does not reach your error middleware and can crash or hang the request — you must wrap in try/catch and call next(err), or use a helper like express-async-handler. Express 5 fixes this by auto-forwarding rejected promises.

Rooms & Namespaces

Namespaces (io.of("/chat")) split one Socket.IO server into isolated communication channels sharing the same underlying connection — good for separating concerns (e.g. /chat vs /game). Rooms (socket.join(roomId)) are arbitrary, cheap, dynamic groupings within a namespace — the standard way to scope broadcasts to "everyone in this game/channel."

socket.join(roomId)
io.to(roomId).emit("update", data)      // everyone in the room, including sender
socket.to(roomId).emit("update", data)  // everyone in the room, excluding sender

Reconnection Handling

The Socket.IO client auto-reconnects with exponential backoff by default, but reconnection only re-establishes the transport — it does not automatically restore server-side state like room membership or in-progress data. That has to be re-synced explicitly once the client reconnects (rejoin the room, request current state).

🎯 Common follow-up

"A user's WiFi drops for 3 seconds mid-session — what happens?" → Client auto-reconnects; on the server, the old socket fires disconnect and a brand-new socket ID connects. If your server-side state is keyed by socket ID (as opposed to a stable user/session ID), the reconnected client looks like a stranger and needs to re-join-room and re-sync state from the server — worth designing for explicitly rather than assuming seamless resume.

JWT Authentication

Token Structure

A JWT is three base64url-encoded segments joined by dots: header.payload.signature. The header names the algorithm; the payload carries claims (e.g. userId, role, exp); the signature is computed over the first two segments with a server-held secret (HMAC) or private key (RSA/ECDSA).

⚠️ Interview trap

The payload is base64-encoded, not encrypted — anyone can decode and read it (paste any JWT into jwt.io). Never put secrets or sensitive data in the payload. The signature only guarantees the token wasn't tampered with, not that its contents are private.

Access vs Refresh Tokens

Access TokenRefresh Token
LifetimeShort (minutes–hours)Long (days–weeks)
Sent withEvery API request (Authorization: Bearer)Only to the token-refresh endpoint
PurposeProve identity for a requestObtain a new access token without re-login
RevocationHard to revoke early (stateless) — rely on short expiryUsually stored server-side so it can be revoked (logout, compromise)

The split exists to balance two competing needs: short-lived access tokens limit the damage window if one leaks, while a long-lived refresh token avoids forcing the user to log in again every 15 minutes.

Storage Security

localStoragehttpOnly Cookie
Accessible to JSYes → vulnerable to XSS token theftNo → immune to XSS reading it
Sent automaticallyNo — you attach it manually to headersYes — browser sends it on every matching request
CSRF exposureNot applicable (not auto-sent)Needs CSRF protection (SameSite cookie attribute, CSRF token)
📌 Likely to be asked

"Where should you store a JWT on the client?" → There's no single correct answer, it's a trade-off: httpOnly cookies protect against XSS token theft but need CSRF mitigation (SameSite=Strict/Lax); localStorage avoids CSRF but is readable by any injected script. Most production setups lean httpOnly cookie + SameSite for that reason.

RBAC Implementation

Role-Based Access Control: encode a role (or list of permissions) in the token payload at login, then gate routes with a middleware that checks it after verifying the signature.

function requireRole(...allowed) {
  return (req, res, next) => {
    if (!allowed.includes(req.user.role)) {
      return res.status(403).json({ error: "Forbidden" })
    }
    next()
  }
}

router.delete("/:id", verifyToken, requireRole("admin"), deleteHandler)

Two-step gate: verifyToken answers "who are you," requireRole answers "are you allowed here" — keep them as separate middleware so authentication and authorization stay independently testable.

REST API Design

Statelessness

Every request must carry all the context needed to process it (auth token, params) — the server holds no per-client session in memory between requests. This is precisely why JWTs fit REST well (the token is the state) and why it's what lets you horizontally scale by just adding more identical server instances behind a load balancer, no sticky sessions required.

Idempotency

MethodIdempotent?Why
GETYesRead-only, no state change
PUTYesReplacing a resource with the same payload twice yields the same end state
DELETEYesDeleting an already-deleted resource still ends with it gone (though the 2nd call may 404)
PATCHDependsIdempotent if the patch sets absolute values; not if it's a relative op like "increment by 1"
POSTNoCalling it twice typically creates two resources
⚠️ Interview trap

Idempotent means "same result state no matter how many times you repeat it," not "returns the same response body every time." A DELETE called twice is still idempotent even though the first call might return 200 and the second 404 — the resource's final state (gone) is identical either way.

Deep-Dive 1: Chessify Chess-PvP Server

♟️ Chessify-WebApp — Chess-PvP/server.js
Node.js + Express + Socket.IO — room-based real-time multiplayer, live board sync

Socket room architecture

A single in-memory rooms object keyed by room ID holds each game's players, spectators, and current FEN. Joining a room runs an assignment strategy (first socket → white, second → black, everyone else → spectator) and immediately syncs the newcomer to the current board state — important for late joiners and page refreshes.

let rooms = {} // { roomId: { players: {white, black}, spectators: [], fen } }

socket.on("join-room", (roomId) => {
  socket.join(roomId)
  if (!rooms[roomId]) {
    rooms[roomId] = { players: { white: null, black: null }, spectators: [], fen: INITIAL_FEN }
  }
  const room = rooms[roomId]

  let role = "spectator"
  if (!room.players.white) { room.players.white = socket.id; role = "white" }
  else if (!room.players.black) { room.players.black = socket.id; role = "black" }
  else { room.spectators.push(socket.id) }

  socket.emit("role", role)
  socket.emit("sync-board", room.fen) // catch up newcomers/reconnects to current position
  io.to(roomId).emit("spectator-count", room.spectators.length)
  if (room.players.white && room.players.black) io.to(roomId).emit("opponent-joined")
})
💼 Resume tie-in

"I designed the PvP server around a room-based model where each game is an isolated in-memory object keyed by room ID — players get assigned white/black on a first-come basis and everyone after that becomes a spectator. On join, the server immediately pushes the current FEN via sync-board, so a spectator joining mid-game or a player refreshing their tab sees the live position instead of an empty board — that was important since the app supports live spectating."

Server-authoritative move validation

The client never trusts its own board — every move is re-validated server-side against the room's fen using chess.js, including whose turn it actually is, before being broadcast or accepted.

socket.on("move", ({ roomId, from, to, promotion }) => {
  const room = rooms[roomId]
  if (!room) return

  let senderColor = null
  if (room.players.white === socket.id) senderColor = 'w'
  else if (room.players.black === socket.id) senderColor = 'b'
  if (!senderColor) return // spectators can't move

  const game = new Chess(room.fen)
  if (game.turn() !== senderColor) return // reject out-of-turn moves

  const result = game.move({ from, to, promotion })
  if (!result) return // illegal move, silently dropped

  room.fen = game.fen()
  socket.to(roomId).emit("opponent-move", { from, to, promotion }) // everyone else
  socket.emit("move-confirmed", { fen: room.fen })              // sender
})
🎯 Common follow-up

"Illegal or out-of-turn moves just silently return — what does the client see?" Honest answer: nothing comes back, so the sender's UI doesn't get explicit feedback that their move was rejected — it just never confirms. A cleaner version would emit a move-rejected event with a reason so the client can show a toast instead of the move silently not happening; worth naming as a known gap if asked to critique the code.

🎯 Common follow-up

"How would you scale this beyond ~100 concurrent users / a handful of concurrent games?" The current design is a single process holding all room state in a plain JS object — that caps out at one server instance. To scale horizontally: (1) move room state into Redis so any server instance can serve any room, (2) use the socket.io-redis-adapter so io.to(roomId).emit() broadcasts across all instances instead of only the one holding that socket, (3) put a load balancer with sticky sessions (or the adapter handles this) in front. At 100 concurrent users on one process, the real risk isn't CPU — it's that a single process restart drops every in-progress game, since state is nowhere else.

Disconnect handling & room cleanup

socket.on("disconnect", () => {
  for (let roomId in rooms) {
    const room = rooms[roomId]
    let wasPlayer = false

    if (room.players.white === socket.id) { room.players.white = null; wasPlayer = true }
    if (room.players.black === socket.id) { room.players.black = null; wasPlayer = true }
    room.spectators = room.spectators.filter(id => id !== socket.id)

    if (wasPlayer) io.to(roomId).emit("opponent-disconnected")
    io.to(roomId).emit("spectator-count", room.spectators.length)

    if (!room.players.white && !room.players.black && room.spectators.length === 0) {
      delete rooms[roomId] // prevent unbounded memory growth from abandoned rooms
    }
  }
})
💼 Resume tie-in

"On disconnect, I sweep every room the socket could belong to, clear its seat, notify the opponent, and delete the room entirely once it's empty — that was a deliberate memory-leak guard, since without it every abandoned game link would sit in the rooms object forever."

⚠️ Flag in your own code

Iterating every room on every disconnect (for (let roomId in rooms)) is O(rooms) per disconnecting socket instead of O(1) — fine at small scale, but the fix an interviewer will want to hear is tracking which room a socket belongs to directly (e.g. a socketId → roomId map, or Socket.IO's own socket.rooms set) so disconnect cleanup is a direct lookup, not a full scan.

🎯 Common follow-up

"How do you handle a brief network drop vs a real quit?" Currently this code treats every disconnect the same — instant "opponent-disconnected." A more resilient version would delay that notification by a grace window (e.g. a few seconds) and only fire it if the same player hasn't reconnected with a session-identifying token in that time, since Socket.IO issues a new socket ID on every reconnect and a flaky connection would otherwise look identical to a rage-quit.

Express + MongoDB setup

const express = require("express")
const mongoose = require("mongoose")
const helmet = require("helmet")
const cors = require("cors")

const app = express()
app.use(cors())
app.use(helmet())          // sets security-related HTTP headers
app.use(express.json())

mongoose.connect(process.env.MONGO_URI, { dbName: "timetableDB" })
  .then(() => console.log("✅ MongoDB Connected"))
  .catch(err => console.error("Mongo Error:", err))

app.use("/api", require("./routes/public"))   // unauthenticated reads
app.use("/admin", require("./routes/admin")) // JWT-gated writes
app.get("/health", (req, res) => res.send("🟢 Server is healthy"))

Two-router split mirrors the REST resource split (public read API vs admin write API) mounted at different base paths — a simple, common pattern for keeping public and privileged surfaces visually separate in the codebase.

JWT login & protected route

// POST /admin/login
router.post("/login", (req, res) => {
  const { username, password } = req.body
  if (username === process.env.ADMIN_USERNAME && password === process.env.ADMIN_PASSWORD) {
    const token = jwt.sign({ username }, process.env.JWT_SECRET, { expiresIn: "1h" })
    return res.json({ token })
  }
  res.status(401).json({ error: "Invalid credentials" })
})

function auth(req, res, next) {
  const token = req.body.token || req.query.token
  if (!token) return res.status(401).json({ error: "No token provided" })
  try { jwt.verify(token, process.env.JWT_SECRET); next() }
  catch { res.status(403).json({ error: "Invalid token" }) }
}

// POST /admin/update — protected
router.post("/update", auth, async (req, res) => {
  await Timetable.findOneAndUpdate({}, { timetableData: req.body.data }, { upsert: true })
  res.json({ message: "Timetable updated successfully" })
})
💼 Resume tie-in

"Admin writes are gated behind a JWT issued on login and verified in an auth middleware ahead of the update route, while the public timetable-read endpoint has no auth at all — since the data behind it is meant to be publicly viewable inside the student app. That split (public read surface, authenticated write surface) is the RBAC boundary the whole API is built around."

⚠️ Flag in your own code — be ready to own this

Three real gaps here worth naming proactively rather than getting caught on:

  • Credentials compared in plaintext against env vars (username === process.env.ADMIN_USERNAME) — the README lists bcrypt as a dependency, but it's never actually used in this route; there's no hashing or per-user record, just a single hardcoded admin pair.
  • Token sent via request body/query string instead of the Authorization: Bearer header — query strings especially can end up logged by proxies/servers, which defeats part of the point of using a token over a raw password.
  • No refresh token — the access token is a flat 1-hour JWT with no rotation or revocation path; if it leaks, it's valid until it naturally expires with no way to kill it early.
🎯 Common follow-up

"Walk me through what you'd change to make this production-grade." Good answer shape: move to `Authorization: Bearer ` + a real `verifyToken`/`requireRole` middleware pair (matching the RBAC pattern above), store hashed admin credentials (or move to a proper users collection) and check with bcrypt.compare, add a short-lived access token + longer-lived refresh token stored server-side (or as an httpOnly cookie) so a compromised access token expires fast and can be revoked via the refresh record.

Public REST endpoint

// GET /api/timetable — no auth required
router.get("/timetable", async (req, res) => {
  const doc = await Timetable.findOne().select("timetableData -_id").lean()
  res.json(doc ? doc.timetableData : [])
})

.lean() skips hydrating a full Mongoose document (with its change-tracking and methods) and returns a plain JS object — a small but real perf win on a read-only endpoint that never needs to save the result back.

🎯 Common follow-up

"Why REST here instead of GraphQL, given the mobile app probably only needs part of this data?" Fair critique of the actual shape: the endpoint returns the entire timetable document (all batches) and lets the Flutter client filter client-side, which is over-fetching — a REST answer would be adding a query param like /api/timetable?batch=CS-2023; a GraphQL answer would let the client request exactly the fields/batch it needs. For an API this small (one resource, one client), REST's simplicity wins — GraphQL's payoff shows up with many resource types and multiple client shapes, which isn't the case here.

Deep-Dive 3: SahYatri BusApi

🚌 SahYatri-BusApi — Express + PostgreSQL
Ingests bus-occupancy events from edge cameras, serves live/summary data to the mobile app + dashboard
github.com/AmanVerma1067/SahYatri →

Connection pooling

const { Pool } = require("pg")

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  ssl: { rejectUnauthorized: false }
})

A connection pool reuses a small set of open TCP connections to Postgres instead of opening/closing one per request — directly relevant to the Node.js fundamentals above: opening a new DB connection is I/O-bound and would otherwise serialize behind connection-setup latency on every request under load.

💼 Resume tie-in

"The ingestion API sits behind a pooled Postgres connection (via pg.Pool) rather than opening a fresh connection per event — with camera events arriving continuously, pooling was what kept the API responsive instead of connection setup becoming the bottleneck under a steady stream of inserts."

REST endpoints & parameterized queries

// POST /api/occupancy — validated, parameterized insert
app.post("/api/occupancy", async (req, res) => {
  const { camera_id, occupancy, capacity } = req.body
  if (!camera_id || occupancy === undefined || capacity === undefined)
    return res.status(400).json({ error: "All fields are required" })
  if (occupancy > capacity)
    return res.status(400).json({ error: "Occupancy cannot exceed capacity" })

  const result = await pool.query(
    `INSERT INTO occupancy (camera_id, occupancy, capacity) VALUES ($1, $2, $3) RETURNING *;`,
    [camera_id, occupancy, capacity]
  )
  res.status(201).json(result.rows[0])
})

// GET /api/occupancy/summary — server-side aggregation, not client-side
app.get("/api/occupancy/summary", async (req, res) => {
  const result = await pool.query(`
    SELECT COUNT(*) total_records, AVG(occupancy) avg_occupancy,
           MAX(timestamp) latest_timestamp, COUNT(DISTINCT camera_id) unique_cameras
    FROM occupancy;`)
  res.json(result.rows[0])
})

// DELETE /api/admin/occupancy/:id — no auth middleware attached
app.delete("/api/admin/occupancy/:id", async (req, res) => {
  const result = await pool.query(`DELETE FROM occupancy WHERE id = $1 RETURNING *;`, [req.params.id])
  if (result.rows.length === 0) return res.status(404).json({ error: "Record not found" })
  res.json({ message: "Record deleted successfully", deleted: result.rows[0] })
})
💼 Resume tie-in

"All queries use $1/$2/$3 parameterized placeholders through pg rather than string-interpolated SQL, so the API is safe from SQL injection by construction. The summary endpoint does the aggregation (COUNT/AVG) in the database itself instead of pulling raw rows and reducing them in Node — cheaper for Postgres to compute than to ship thousands of rows over the wire for the API to crunch."

⚠️ Flag in your own code

DELETE /api/admin/occupancy/:id is under an /admin path by naming convention only — there's no auth middleware actually attached to it, so anyone who finds the URL can delete any record. This is the single most likely thing an interviewer zeroes in on if you walk them through this file: be upfront that it needs the same JWT + requireRole("admin") pattern shown in the RBAC section, gating a route by URL naming instead of middleware isn't real access control.

Scaling to 50,000+ events/day

50k events/day averages to roughly 1 insert every ~1.7 seconds — genuinely light load for Postgres and not something this API's current shape would struggle with at that rate. The interesting scaling conversation is what changes if traffic became bursty (many cameras reporting in the same second) or the read side grew.

🎯 Common follow-up

"How would you scale this beyond current load, or handle a burst of simultaneous camera reports?" Talking points, roughly in order of what you'd actually reach for first:

  • Indexing: the repo has no visible migration/index on camera_id or timestamp — every WHERE camera_id = $1 ORDER BY timestamp DESC query does a full scan without one; a composite index on (camera_id, timestamp DESC) is the first fix as row count grows.
  • Batching inserts: if many cameras report near-simultaneously, batching several rows into one INSERT ... VALUES (...), (...), (...) beats many single-row round trips.
  • Read/write separation: the dashboard's read traffic (`GET /api/occupancy`, `/summary`) is decoupled from camera write traffic — at real scale you'd put reads on a replica so ingestion writes never queue behind dashboard polling.
  • Pool sizing: pg.Pool defaults to 10 connections — under sustained concurrent load that ceiling (not raw event volume) is usually what you hit first, and it's a one-line config change to raise, paired with checking Postgres's own max_connections.
