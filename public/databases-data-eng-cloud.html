💡 Senior Insight

The real dividing line isn't SQL vs NoSQL — it's uniform vs heterogeneous data. Telemetry is perfectly uniform: bus ID, timestamp, count, lat, lng, forever. Schema flexibility buys nothing and schema enforcement stops a malformed reading entering the table. A product specification is the opposite: every customer has different fields, so a rigid schema means either a wide sparse table or a migration per customer. Same engineer, opposite choices, one principle.

🚨 Interview Trap

The 16 MB BSON ceiling and the unbounded array anti-pattern. Embedding a revision history inside a spec document feels natural — until a heavily-edited spec accumulates hundreds of revisions and the document approaches 16 MB. The write then fails, in production, on your most active customer, which is the worst possible discovery path.

It's also slow long before it fails: MongoDB rewrites the whole document on update, so a 5 MB document costs 5 MB of I/O to append one revision. And you can't page through an embedded array efficiently.

Fix: revisions go to a dedicated append-only spec_revisions collection keyed by specId, with the current version embedded for fast reads. Unbounded growth always means a separate collection — or the bucket pattern, grouping N entries per document, if you want a middle ground.

Normalization vs pragmatic denormalization

  • 1NF — one value per cell, no lists in a column.
  • 2NF — no column depends on only part of a composite key.
  • 3NF — no column depends on another non-key column (don't store city beside pincode).

When to break it deliberately: strict 3NF forces joins on every read. On a dashboard aggregating millions of telemetry rows, joining to routes on each one is measurable cost for a value that changes almost never. Copying route_name onto the row is a real optimization — you accept updating it in two places.

JSONB is the escape hatch that gets both: strict columns for the things you filter and join on, a JSONB column for genuinely variable attributes, and GIN indexing when you need to query inside it.

🛡️ SDE Defense

If asked "could Packspec have been Postgres?" — say yes, honestly, and show the design: strict columns for tenant_id, role, workflow state and timestamps; a JSONB column for the variable spec body; GIN index for field queries. That would have given stronger relational reporting. Mongo Atlas was the team's existing stack, which is a legitimate engineering reason on its own. Claiming a deliberate architectural bake-off on an inherited codebase is the kind of overclaim that collapses under one follow-up.

02 Transactions, concurrency & storage internals

MVCC — the idea both engines share

Multi-Version Concurrency Control: an update writes a new version rather than overwriting in place. Readers see the version that was current when their transaction started. The payoff is the line worth memorizing: readers never block writers, and writers never block readers.

 PostgreSQLMongoDB (WiredTiger)
Old versionsDead tuples in the table, cleaned by VACUUMKept in cache / lookaside
DurabilityWAL — write-ahead logJournal + oplog
Concurrency limitConnections (a process each)Transaction tickets (~128 read / 128 write)
Isolation defaultRead CommittedSnapshot (in transactions)
💡 Senior Insight

WAL is why a crash doesn't lose committed data. Postgres writes the intent to a sequential log and fsyncs that before touching data pages. Sequential writes are fast; random page writes are not. On restart it replays the log. This also explains a lot of Postgres behaviour downstream: WAL is what replication ships to standbys, what point-in-time recovery replays, and why a commit-heavy workload is bounded by fsync throughput — which is why batching inserts into fewer transactions is such a large win. Each commit is an fsync; 1,000 single-row commits is 1,000 fsyncs, one 1,000-row commit is one.

Isolation levels, and the anomaly each stops

LevelPreventsStill possible
Read CommittedDirty readsNon-repeatable reads, phantoms
Repeatable Read+ non-repeatable readsPhantoms (in the standard; Postgres blocks most)
SerializableEverything — behaves as if serialNothing, but transactions get aborted and must retry

Phantom read: you run the same WHERE twice in one transaction and the second returns extra rows another transaction inserted. Non-repeatable read is about a row changing; phantom is about the row set changing.

🚨 Interview Trap

Long-running transactions are a silent killer in Postgres. An idle-in-transaction session holds a snapshot, which means VACUUM cannot reclaim dead tuples newer than it — for the whole database. Tables bloat, indexes bloat, queries slow down, and the cause is one forgotten open transaction in a debug console. Related in Mongo: the default 60-second transaction limit and the ticket pool — long transactions exhaust tickets and new operations queue even though the server looks idle. Keep transactions short. Never wait on a network call inside one.

// If a client can send it, a client can send someone else's.

class TenantScopedRepo {
  constructor(model, tenantId) {
    if (!tenantId) throw new Error('tenantId required');   // fail loud at construction
    this.model = model; this.tenantId = tenantId;
  }
  find(f = {})        { return this.model.find({ ...f, tenantId: this.tenantId }); }
  findById(id)        { return this.model.findOne({ _id: id, tenantId: this.tenantId }); }
  update(id, patch)   { return this.model.updateOne({ _id: id, tenantId: this.tenantId }, patch); }
  aggregate(pipeline) { return this.model.aggregate([{ $match: { tenantId: this.tenantId } }, ...pipeline]); }
}                       // ^ tenant filter FIRST in the pipeline — both correct and index-friendly
Atomic multi-document transaction — cloning a spec without orphans 
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    const spec = await Spec.findOne({ _id: id, tenantId }, null, { session });
    if (!spec) throw new NotFoundError();

    const clone = await Spec.create([{ ...strip(spec), name: `${spec.name} (copy)`, tenantId }], { session });
    await Field.insertMany(fieldsFor(clone[0]),   { session });
    await Revision.create([initialRevision(clone[0])], { session });
    await AuditLog.create([{ action: 'clone', specId: clone[0]._id, tenantId }], { session });
  }, { readConcern: { level: 'snapshot' }, writeConcern: { w: 'majority' } });
} finally {
  await session.endSession();
}
// Without the session: a crash between insertMany and Revision.create leaves a
// spec with fields but no history — an orphan nobody notices until an audit.
🛡️ SDE Defense

writeConcern: majority is the clause to explain rather than recite: it means the write is acknowledged only once a majority of replica-set members have it, so a primary failover cannot roll your commit back. Combined with readConcern: snapshot, the transaction reads one consistent point-in-time view and either every document lands or none does.

And the constraint that shapes the design: transactions must be short. Everything slow — validation, external calls, file uploads — happens before withTransaction opens. The transaction contains writes only, because holding one open across a network call burns tickets and blocks other writers.

03 Indexing & query optimization

💡 Senior Insight

BRIN is the answer that separates you in a data-engineering interview. A B-tree over 50 million timestamps can run to gigabytes because it stores an entry per row. BRIN stores only min/max per block range — kilobytes — and works because telemetry arrives in time order, so the table is already physically sorted by the indexed column. A range scan just skips every block whose min/max can't contain the range.

The rule, and the condition that makes it fail: BRIN when insert order matches sort order. Backfill old data out of order and correlation breaks, blocks stop being selective, and BRIN quietly degrades toward a sequential scan.

Compound indexes: ESR and the prefix rule

ESR — order columns as Equality, then Sort, then Range. Equality narrows to a contiguous block, sort is then already satisfied, range scans within it.

🚨 Interview Trap

The leftmost prefix rule. An index on (bus_id, recorded_at) serves queries on bus_id and on bus_id + recorded_at — but not on recorded_at alone. You cannot skip a prefix column, because the index is sorted by the first column first. People add a compound index, watch one query stay slow, and can't see why.

Two more that cost real interviews: an index everything instinct (every index must be updated on every write — a direct tax on an ingest-heavy table), and a function on the column — WHERE DATE(recorded_at) = '2026-08-21' cannot use the index at all. Rewrite as a range: recorded_at >= '2026-08-21' AND recorded_at < '2026-08-22'.

Reading a query plan

EXPLAIN ANALYZE — what to look for 
EXPLAIN (ANALYZE, BUFFERS)
SELECT bus_id, avg(occupancy)
FROM telemetry
WHERE recorded_at >= now() - interval '7 days'
GROUP BY bus_id;

-- Read it BOTTOM-UP. The checklist:
--
-- 1. Seq Scan on a big table with a selective WHERE  → missing/unused index
-- 2. rows=1000 (estimated) vs actual rows=900000     → stale stats; run ANALYZE
-- 3. Nested Loop with a huge outer row count         → planner misjudged; often (2)
-- 4. "Filter: ... Rows Removed by Filter: 4000000"   → fetched then discarded; index it
-- 5. external merge Disk: 250MB                      → sort spilled; raise work_mem
-- 6. Buffers: read=  vs hit=                         → 'read' is disk, 'hit' is cache

-- MongoDB equivalent:
db.telemetry.find({ busId: 12 }).explain("executionStats")
-- COLLSCAN                         → no index used
-- IXSCAN → FETCH                   → index found docs, then fetched them
-- totalDocsExamined >> nReturned   → the index isn't selective enough
-- totalDocsExamined == nReturned   → ideal
-- IXSCAN with no FETCH             → covered query, best case

The single most useful signal in either engine: compare rows examined to rows returned. Close together is healthy; orders apart means you're scanning and discarding.

Connection pooling

Postgres forks a process per connection — roughly 5–10 MB each, plus scheduling cost. So connections are a scarce resource, not a free one.

  • Sizing — a common starting point is (cores × 2) + effective_spindles. Counter-intuitively, a smaller pool often has higher throughput: 20 connections on 4 cores just thrash.
  • Exhaustion looks like timeouts and latency spikes with an idle-looking database — everyone's queued at the pool.
  • PgBouncer in transaction mode multiplexes thousands of client connections onto a few server ones. Essential once you have many app instances, and mandatory for serverless, where each invocation would otherwise open its own connection.

Synchronous writes vs a queue

Start simple and honest: at SahYatri's real volume, direct writes were correct. The queue is what you reach for when a database slowdown starts causing data loss rather than just slowness.

📊 ML / Data Eng Defense

Batching is the highest-leverage change and it costs almost nothing. Every commit is an fsync; 1,000 single-row inserts is 1,000 fsyncs plus 1,000 round trips plus 1,000 index updates. Buffer for a couple of seconds and write one multi-row INSERT — or COPY for real volume, which skips per-row parsing entirely — and you routinely get an order of magnitude. Do this before reaching for Kafka or a different database engine; most "we need a time-series DB" conclusions are really "we're committing one row at a time."

Late data, retries and idempotency

A bus loses signal for two hours and uploads a backlog. Three things must hold:

  • Event time ≠ ingest time — store both. recorded_at is when the reading happened; ingested_at is when you received it. Aggregate on event time, or a reconnect skews your history.
  • Idempotency — a device that times out will retry, so the same reading can arrive twice. A unique constraint on (bus_id, recorded_at) with ON CONFLICT DO NOTHING makes duplicates harmless.
  • Watermarks — a rollup for hour H shouldn't be considered final until you're reasonably sure late data has landed. Either delay finalizing, or recompute affected buckets when late data arrives.
Idempotent batch upsert + partitioned schema + rollup 
-- partitioned parent
CREATE TABLE telemetry (
  bus_id       int         NOT NULL,
  recorded_at  timestamptz NOT NULL,
  ingested_at  timestamptz NOT NULL DEFAULT now(),
  occupancy    int         NOT NULL,
  lat          double precision,
  lng          double precision,
  PRIMARY KEY (bus_id, recorded_at)        -- also gives idempotency
) PARTITION BY RANGE (recorded_at);

CREATE TABLE telemetry_2026_08 PARTITION OF telemetry
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

CREATE INDEX ON telemetry_2026_08 USING BRIN (recorded_at);   -- tiny; data is time-ordered

-- idempotent batch insert: a retried burst can't double-count
INSERT INTO telemetry (bus_id, recorded_at, occupancy, lat, lng)
SELECT * FROM unnest($1::int[], $2::timestamptz[], $3::int[], $4::float[], $5::float[])
ON CONFLICT (bus_id, recorded_at) DO NOTHING;

-- hourly rollup: keep raw hot for a week, summaries forever
INSERT INTO telemetry_hourly (bus_id, hour, avg_occupancy, max_occupancy, samples)
SELECT bus_id, date_trunc('hour', recorded_at), avg(occupancy), max(occupancy), count(*)
FROM telemetry
WHERE recorded_at >= $1 AND recorded_at < $2
GROUP BY 1, 2
ON CONFLICT (bus_id, hour) DO UPDATE
  SET avg_occupancy = EXCLUDED.avg_occupancy,   -- recompute if late data arrived
      samples       = EXCLUDED.samples;
💡 Senior Insight

Partitioning pays three separate dividends and it's worth naming all three: query pruning (a last-7-days query skips every other partition without reading it), small hot indexes (writes only touch the current partition, so the index that must stay in cache is one month's worth, not five years'), and instant retention — dropping old data becomes DROP TABLE, which is metadata-only, instead of a DELETE that writes dead tuples and then makes VACUUM clean them up.

ETL vs ELT

ETL transforms before loading; ELT lands raw and transforms in the warehouse.

  • SahYatri is necessarily ETL, and that's a design commitment, not a preference: YOLOv5n reduces a frame to a count on the Pi, and the frame is discarded. You could not do ELT without transmitting video, which breaks the privacy guarantee.
  • ELT suits a warehouse where storage is cheap and you don't yet know the questions — land everything, transform later, re-transform when requirements change.

The trade in one line: ETL is cheaper to store and impossible to reinterpret; ELT keeps every option open and costs more.

🚨 Interview Trap

Docker layers are immutable, so a deleted secret is still in the image. COPY .env . && RUN use-it && RUN rm .env leaves the secret permanently readable in the earlier layer — anyone who pulls the image can extract it with docker history. Deleting a file in a later layer hides it from the filesystem, not from the image.

Real fixes: multi-stage (secrets used in build never enter the final stage), BuildKit --mount=type=secret (never written to any layer), or inject at runtime as environment variables. And a .dockerignore covering .env, .git, node_modules — .git alone often carries credentials in its history and bloats the build context.

Git LFS for model artifacts

Git stores a full copy of every version forever, and binary .pth files don't delta-compress. A 100 MB checkpoint committed ten times is a gigabyte in history that every clone downloads forever — and rewriting history to remove it is painful. LFS replaces the file with a pointer; .gitattributes holds the rules.

📊 ML / Data Eng Defense

The distinction worth stating: LFS gives versioning tied to code; object storage gives scale. With LFS, checking out the commit that produced a result also checks out the exact weights that produced it — reproducibility with zero manual bookkeeping, versus an S3 bucket where matching model_v3_final_FINAL.pth to a commit is something a human does and eventually gets wrong.

In CI it pays off concretely: GIT_LFS_SKIP_SMUDGE=1 lets lint and unit jobs clone in seconds without pulling weights, and only the inference test fetches them. Outgrow it past a few GB or a real team — LFS has bandwidth quotas and stores no model metadata — moving to S3 or a registry (MLflow, HF Hub) with a version pointer in Git.

CI/CD and API test automation

  • Cheap checks first — lint, then unit tests (PHPUnit/Jest/pytest), then build the container, then integration tests. Fail fast on the fast things.
  • Newman runs Postman collections headlessly, so the same collection you click locally becomes a merge gate.
  • Token injection — a first request logs in and stores the token into a collection variable via the Tests script; every later request uses {{authToken}}. Credentials come from environment files, never committed.
  • Ephemeral environment — docker compose up the API plus a throwaway database, run the suite against it, tear it down. Tests never touch shared state.
🛡️ SDE Defense

Multi-tenant isolation is exactly the property unit tests cannot verify. "Can tenant A read tenant B's spec?" is only answerable by a real request carrying A's real token against B's real resource ID, expecting 403. That's an integration test, and it's the highest-value one in the suite — it guards the failure with actual consequences. So the collection isn't just happy-path coverage; the useful cases are the negative ones: wrong tenant, insufficient role, expired token, tampered ID.

06 Interview defense bank

One-line reason → supporting mechanic → the trade-off you accepted.

Track A — SDE

A · Q1
1. Why shared-collection multi-tenancy instead of database-per-tenant?

Because the tenant count is high and each tenant is small — the exact profile shared-collection is built for. Database-per-tenant means every schema change is N migrations, every tenant needs its own connection pool, and cross-tenant analytics becomes a union across databases. Operational cost grows linearly with customers, which is backwards for a SaaS trying to add customers cheaply.

Shared collections with a tenantId discriminator give one migration, one pool, and indexes that lead with tenantId so queries stay selective.

The cost, stated plainly: isolation is now enforced by application code, so a single missing filter leaks data across customers. That's why it's structural — every query goes through a tenant-scoped repository that injects the filter, and the tenant ID is read only from the verified token, never from client input. Writing an unscoped query requires bypassing the repo, which is visible in review.

When I'd switch: a regulated enterprise tenant with a contractual data-residency or physical-isolation requirement. That's a compliance decision, not a performance one.

A · Q2
2. How did you design atomic transactions to prevent orphaned clone records?

The failure being prevented: cloning a spec writes several documents — the spec, its fields, an initial revision, an audit entry. A crash after two of four leaves a spec with fields but no history. Nothing errors; the data is just quietly wrong, and it surfaces during an audit weeks later.

The fix is a session-scoped transaction: every write carries { session }, with readConcern: snapshot so all reads see one consistent point in time and writeConcern: majority so a primary failover can't roll the commit back. Either all four documents land or none do.

The design constraint that falls out of this: transactions must be short. Validation, permission checks and any external calls happen before the transaction opens — it contains writes only. A transaction held open across a network call burns WiredTiger tickets and blocks other writers.

And the alternative I'd mention: if the clone could be modelled as a single document, no transaction would be needed at all — single-document writes are always atomic in MongoDB. Multi-document transactions are the fallback for when the model genuinely spans collections, not the default reach.

A · Q3
3. How do you enforce tenant isolation so a junior dev can't accidentally leak records?

By making the unsafe thing hard to write, not by asking people to remember. Any scheme that depends on every developer adding a tenantId filter to every query will eventually meet the endpoint that forgot — and that endpoint leaks.

Three layers: (1) tenant ID is extracted from the verified JWT in middleware and attached to the request — never accepted from body, query or header, because anything a client can send, a client can forge; (2) all data access goes through a TenantScopedRepo constructed with that ID, which injects the filter into every find, update and aggregation, and throws at construction if the ID is missing; (3) the raw model isn't exported from the data module, so a query without a tenant scope is not merely discouraged — it's inconvenient, and it shows up in review as someone reaching past the repository.

Then verify it — negative integration tests where tenant A's token requests tenant B's resource and must get 403. That's a class of bug only an end-to-end request can catch.

Trade-off: the repository layer adds indirection and makes genuine cross-tenant admin queries awkward. Correct — those should be explicit and rare.

A · Q4
4. Walk me through automating auth token injection and regression tests in CI.

Structure: the collection opens with a login request whose Tests script writes the returned JWT into a collection variable. Every subsequent request sends Authorization: Bearer {{authToken}}, so tokens are never hardcoded and expiry never breaks the run. Per-role tokens (admin, editor, viewer) are captured up front so permission cases can be tested without re-authenticating.

Data flow: a create request stores the new resource ID into a variable that later update and delete requests consume — the suite builds and tears down its own state, so runs are independent and re-runnable.

In CI: Newman runs the collection headlessly against an ephemeral docker compose stack with a throwaway database. Environment files supply base URLs and credentials, pulled from CI secrets rather than committed. A non-zero exit fails the merge.

What the suite is actually for: the valuable cases are the negative ones — wrong tenant, insufficient role, expired token, tampered ID. Happy paths are largely covered by unit tests; cross-tenant leakage is only detectable through a real authenticated request, which is exactly what this catches.

A · Q5
5. How do you structure a multi-stage Dockerfile to shrink images and protect secrets?

Two stages. The build stage carries compilers, dev headers and build-time credentials. The runtime stage starts from a slim base and copies only the built artifacts. Everything the build needed and the runtime doesn't — toolchains, caches, secrets — never exists in the shipped image. Smaller image, faster pulls, and a much smaller attack surface.

On secrets, the key mechanic: layers are immutable, so RUN rm .env in a later layer removes the file from the filesystem but not from the image — it's still extractable via docker history. Multi-stage solves this structurally, because the layer containing the secret is discarded rather than hidden. For build-time secrets specifically, BuildKit's --mount=type=secret exposes the value during one RUN without writing it to any layer. Runtime secrets are injected as environment variables or from a secret manager — never baked in.

Also: order layers so dependencies install before source is copied, or every code change reinstalls the world. Run as a non-root user. And keep a .dockerignore covering .git, .env and node_modules — .git frequently carries credentials in its history and bloats the build context.

Track B — ML / AI / Data Engineering

B · Q1
1. Why PostgreSQL for transit telemetry over MongoDB or InfluxDB?

Because every question I ask this data is an aggregate over a time range, and that's what SQL is for. "Average occupancy per hour on route 12 last week" is one query with a window function. In a document store I'd be writing aggregation pipelines or doing it in application code.

The data is also perfectly uniform — bus ID, timestamp, occupancy, lat, lng — so schema flexibility buys nothing, while schema enforcement stops a malformed reading from entering the table at all.

Postgres then gives me the whole time-series toolkit natively: range partitioning so a week's query skips every other partition, BRIN indexes that are tiny because time-ordered inserts leave the table physically sorted, ON CONFLICT for idempotent retries, and DROP TABLE retention instead of a slow DELETE.

Why not Influx: it's genuinely better at extreme write volume, but it's a second technology to operate and learn, with a different query language, for a workload Postgres handles comfortably. Trade-off: raw write throughput is lower, which I address by batching. At 100× scale I'd move to TimescaleDB first — same SQL, purpose-built storage, no rewrite.

B · Q2
2. How do you optimize a table ingesting millions of telemetry rows per day?

Four levers, roughly in order of payoff.

1. Batch the writes. Every commit is an fsync, so one-row-per-insert is the dominant cost. Buffer and use multi-row inserts or COPY. Usually an order of magnitude on its own, and it's a code change, not an architecture change.

2. Partition by time. PARTITION BY RANGE (recorded_at), one partition per month. Three separate wins: queries prune to relevant partitions; writes only touch the current partition so the hot index stays small enough to sit in cache; retention becomes an instant DROP TABLE instead of a DELETE that leaves dead tuples for VACUUM.

3. BRIN on the timestamp. A B-tree over 50M timestamps is gigabytes; BRIN stores min/max per block range and is kilobytes. It works only because inserts arrive in time order, so the table is already physically sorted — that correlation is the precondition, and backfilling out of order breaks it. Keep a B-tree on (bus_id, recorded_at) for per-bus lookups, since that one needs real selectivity.

4. Downsample. Nobody queries per-second data from six months ago. A scheduled job rolls raw readings into hourly averages; raw stays hot for a week, summaries persist. Dashboards then read a table that's orders of magnitude smaller.

And index restraint — every index is updated on every insert, so on an ingest-heavy table each one is a throughput tax. Add them from measured query plans, not speculation.

B · Q3
3. A bus loses connectivity for 2 hours, then uploads 2,400 payloads at once. What happens?

Three separate problems, and naming them separately is the answer.

Correctness — event time vs ingest time. Those 2,400 readings all arrive now but happened over the last two hours. If the schema only records arrival time, the history shows an empty two hours followed by an impossible spike. So recorded_at is set on the device and ingested_at on the server, and every aggregate uses event time.

Duplicates — idempotency. A device that times out mid-upload will retry, so readings can arrive twice. A unique constraint on (bus_id, recorded_at) with ON CONFLICT DO NOTHING makes retries harmless — which in turn means the device can retry aggressively without coordination.

Load — the burst itself. The device uploads in chunks (say 200 readings per request) rather than one enormous body, and the server inserts each chunk as one batched statement. If many buses reconnect simultaneously after an area-wide outage, that's a thundering herd, so devices add jitter to their retry timing and the ingest endpoint returns 202 after buffering rather than holding the connection through the write.

Downstream: any hourly rollup covering that window is now stale, so late data marks affected buckets for recomputation — which is why the rollup is written as an idempotent upsert rather than a plain insert.

B · Q4
4. Why Git LFS for .pth weights rather than plain Git or object storage?

Plain Git is disqualified immediately. Git keeps a full copy of every version forever, and binary checkpoints don't delta-compress, so a 100 MB file committed ten times is a gigabyte that every clone downloads forever. Worse, it's not undoable without rewriting history for everyone.

LFS over object storage because it ties weights to code. Checking out the commit that produced a result also checks out the exact weights that produced it — reproducibility with no manual bookkeeping. With a bare S3 bucket, mapping model_v3_final_FINAL.pth to the commit that trained it is something a human tracks in a spreadsheet and eventually gets wrong.

Practical CI benefit: GIT_LFS_SKIP_SMUDGE=1 lets lint and unit jobs clone in seconds without pulling weights; only the inference test fetches them.

When I'd outgrow it: LFS has bandwidth quotas and stores no metadata — no metrics, no training config, no lineage. Past a few GB or a real team, S3 or a model registry (MLflow, HF Hub) holding the artifact with only a version pointer in Git. For a project with a handful of checkpoints, LFS is the right rung on that ladder, and knowing when you'd step off it is the rest of the answer.

B · Q5
5. Index scan vs collection scan — what do you look for in EXPLAIN ANALYZE?

The difference: a sequential/collection scan reads every row and discards non-matches — O(n), and fine when you genuinely want most of the table. An index scan walks a sorted structure to jump straight to matching rows — roughly O(log n). Note the planner sometimes chooses a seq scan correctly: if a query returns 60% of the table, random index lookups plus heap fetches are slower than reading it sequentially.

What I check, in order:

  • Estimated vs actual rows. rows=1000 planned against actual rows=900000 means stale statistics — the planner chose badly on bad information. ANALYZE the table first; it fixes more "slow query" tickets than adding an index does.
  • Rows Removed by Filter. A large number means the database fetched rows only to throw them away — that filter belongs in an index.
  • Seq Scan on a large table with a selective WHERE — missing index, or an unusable one (function applied to the column, or a skipped leftmost prefix).
  • Sort spilling to disk (external merge Disk: 250MB) — raise work_mem or index for the sort order.
  • Buffers — read is disk, hit is cache. High reads on a repeated query means the working set doesn't fit in cache.

In MongoDB: COLLSCAN means no index used; IXSCAN → FETCH means the index found documents and then fetched them. The number that matters is totalDocsExamined versus nReturned — equal is ideal, orders apart means the index isn't selective. An IXSCAN with no FETCH is a covered query, where the index alone answered it. Best case in either engine.
