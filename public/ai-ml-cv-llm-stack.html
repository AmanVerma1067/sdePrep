01 ML & Deep Learning Foundations

Loss Functions

A loss function is just the definition of "wrong." Pick the one whose shape matches your output.

LossOutput layerUse whenPenalizes
MSELinearRegression (calories, price)Squared distance — outliers hurt a lot
Binary CESigmoidYes/no, or multi-labelConfident wrong answers, harshly
Categorical CESoftmaxOne class out of N (food classifier)Low probability on the true class
Focal lossSigmoidHeavy class imbalance (detection)Down-weights easy examples
🚨 Interview Trap

"Why not MSE for classification?" Two reasons, and they want both: (1) MSE with a sigmoid gives you a non-convex surface with flat regions, so gradients vanish exactly when the model is confidently wrong. (2) Cross-entropy's gradient through softmax simplifies to (prediction − target) — clean, proportional to the error, no saturation term. CE learns faster because the math is nicer, not because it's "for classification."

Gradient Descent & Optimizers

VariantUpdate afterTrade-off
Batch GDWhole datasetStable, accurate direction — impossibly slow, huge memory
SGDOne sampleFast, noisy; noise can escape shallow local minima
Mini-batch32–256 samplesThe real-world default — GPU-friendly, decent gradient estimate
  • Momentum — keep a running average of past gradients. Rolls through small bumps and ravines instead of zig-zagging across them.
  • Adam — momentum plus a per-parameter learning rate scaled by recent gradient magnitude. Rare features get bigger steps.
  • AdamW — the fix that matters. Plain Adam folds L2 into the gradient, where the adaptive scaling then partially cancels it. AdamW applies weight decay separately, so regularization actually regularizes. Use AdamW when fine-tuning.
💡 CP Intuition

Backprop is memoized DP on a DAG. The computational graph is your DAG, each node's gradient is a subproblem, and the chain rule is the transition. Forward pass = fill the table with activations. Backward pass = one reverse topological sweep reusing every stored value. Without memoization you'd recompute shared subpaths exponentially — that's literally the naive-recursion-vs-DP gap you already know. loss.backward() is a DP solve.

Bias–Variance

Regularization

  • L1 (Lasso) — adds λ·Σ|w|. Constant gradient pushes weights to exactly zero → sparsity, built-in feature selection.
  • L2 (Ridge / weight decay) — adds λ·Σw². Gradient shrinks with the weight, so weights get small but never zero. Spreads influence across correlated features.
  • Dropout — randomly zero a fraction p of activations each training step. The network can't rely on any single neuron, so it learns redundant paths.
  • Early stopping — stop when val loss turns upward. Free, and often the strongest regularizer you have.
  • Augmentation — for food images: random crop, horizontal flip, color jitter. A photo of a plate is still that food rotated 10° or slightly warmer in tone.
🚨 Interview Trap

Inverted dropout. "What does dropout do at inference?" Nothing — it's off. The follow-up is the real question: why doesn't turning it off change the activation scale? Because PyTorch scales surviving activations up by 1/(1−p) during training, so expected output already matches inference. That's inverted dropout. If you forget model.eval(), dropout stays on and your predictions become random — the single most common PyTorch inference bug.

CNNs & ResNet

  • Kernel — a small learned filter slid across the image. Early layers find edges; deep layers find "this looks like a plate of rice."
  • Padding — 'same' keeps output size equal to input (pad the border); 'valid' means no padding, so output shrinks.
  • Stride — step size. Stride 2 roughly halves spatial dimensions.
  • Pooling — downsample by taking the max/average over a window. Cheap size reduction and small-shift tolerance.

Output size, the formula they ask you to derive on a whiteboard:

out = floor((in + 2·padding − kernel) / stride) + 1

ResNet's skip connection: instead of learning H(x) directly, a block learns the residual F(x) and outputs F(x) + x.

y = F(x, {W}) + x
💡 Senior Insight

Why skip connections fix vanishing gradients, stated precisely: differentiating F(x) + x gives F'(x) + 1. That +1 is a gradient highway — even if F'(x) collapses toward zero, the gradient still reaches earlier layers at full strength instead of being multiplied down through 50 layers. It also makes identity easy to learn: if a block isn't useful, drive F(x) → 0 and it passes input through unchanged. Depth stops being a risk.

PyTorch: ResNet-50 transfer head (Nutri-Vision pattern) 
import torch.nn as nn, torchvision.models as models

model = models.resnet50(weights=models.ResNet50_Weights.IMAGENET1K_V2)

# 1. freeze the pretrained feature extractor
for p in model.parameters():
    p.requires_grad = False

# 2. replace the 1000-class ImageNet head with our food head
model.fc = nn.Sequential(
    nn.Dropout(p=0.5),                    # new head overfits fastest — regularize it
    nn.Linear(model.fc.in_features, NUM_FOOD_CLASSES)
)

# 3. only the new head gets gradients
optimizer = torch.optim.AdamW(model.fc.parameters(), lr=1e-3, weight_decay=1e-2)

# 4. later: unfreeze layer4 at a much lower LR
for p in model.layer4.parameters():
    p.requires_grad = True
optimizer = torch.optim.AdamW([
    {"params": model.layer4.parameters(), "lr": 1e-5},
    {"params": model.fc.parameters(),     "lr": 1e-4},
], weight_decay=1e-2)
🚨 Interview Trap

"Why must you use ImageNet's normalization stats — mean=[0.485,0.456,0.406], std=[0.229,0.224,0.225]?" Because the frozen filters were trained on inputs in that exact distribution. Feed them differently-scaled pixels and every early activation shifts, so the features you're relying on are subtly wrong. Silent accuracy loss with no error message. Match the preprocessing to the weights, always.

📊 ML Track Defense

Why Dropout(0.5) specifically on the head? Because the head is where overfitting concentrates. The backbone is frozen and already generalizes — it saw a million ImageNet images. The new Linear layer is the only thing learning, from a comparatively tiny food dataset, so it's the part that will memorize. 0.5 is the standard aggressive setting for a fully-connected layer; convolutional layers use far less (0.1–0.2) because weight sharing already regularizes them. If you'd trained the whole network, 0.5 throughout would have underfit.

02 NLP, Custom NER & Entity Resolution

The classical pipeline

  • Tokenization — split text into units. Harder than it looks: "1/2 cup", "chicken-tikka", "200g".
  • Lemmatization — reduce to dictionary form ("eggs" → "egg"). Unlike stemming, the result is a real word — which matters when you're querying a food database by name.
  • Stop-words — drop "the", "a", "and". Fine for retrieval, dangerous for NER, where surrounding words are the signal.

💡 CP Intuition

spaCy's hash embeddings are a Bloom filter trick you already understand from hashing problems: instead of a vocabulary-sized lookup table, hash each word into a small fixed table with a few hash functions. Memory is constant regardless of vocabulary size, and there's no out-of-vocabulary cliff — a food word it never saw still gets a vector. You accept rare collisions in exchange for a tiny, unbounded-vocabulary model. Classic space-vs-precision trade.

Training a custom FOOD entity

Annotations are character offsets, not tokens:

BILOU is the internal tagging scheme spaCy converts those offsets into — Begin, Inside, Last, Outside, Unit. It's how a multi-word entity like "grilled chicken breast" stays one entity instead of three.

Precision, Recall, F1 — say it in product terms

P = TP/(TP+FP) · R = TP/(TP+FN) · F1 = 2PR/(P+R)
  • Precision — of the things I tagged as food, how many really were? Low precision = junk entities reaching the USDA lookup.
  • Recall — of the real foods present, how many did I catch? Low recall = a missing item and an undercounted meal.
  • F1 — harmonic mean. Harmonic, not arithmetic, because it refuses to reward a lopsided model: predict everything as food and recall hits 1.0 while F1 stays low.
📊 ML Track Defense

Which one do you optimize? Have an opinion, and tie it to the product. For a food logger I'd favour recall at the NER stage — a missed item silently undercounts calories, while a false positive gets filtered downstream when the USDA fuzzy match returns a low confidence score. That's the real defense: my pipeline has a second filter, so I can afford to be greedy at stage one.

Also mention the split: entities were annotated then split roughly [70/15/15] train/val/test, split by sentence, not by entity, so the same meal string can't appear on both sides and inflate the score.

UNIT = r"(g|gram|kg|ml|l|cup|tbsp|tsp|slice|piece|bowl|medium|large|small)"
QTY  = re.compile(rf"(\d+(?:\.\d+)?|\d+/\d+)\s*{UNIT}s?\b", re.I)

def parse_quantity(text):

    if not m:
        return None                    # fail loudly, don't guess

🚨 Interview Trap

"Why not one LLM call for the whole sentence?" Don't say "it's slower." Say: a nutrition app must never invent a number. An LLM will happily return a confident, wrong gram value with no signal that it guessed. My regex returns None when it doesn't recognize a format — a visible failure the UI can handle — and every macro number comes from USDA FoodData Central, not from a model. Learn the fuzzy part, hard-code the exact part.

The honest framing of why string similarity was the right call: the USDA search endpoint already returns a candidate shortlist. So resolution isn't "search 300k foods" — it's "rank 10 candidates." YOLO internals

The image is divided into a grid. Each cell predicts boxes as (x, y, w, h, objectness) plus class probabilities. Anchor boxes are prior shapes — the network predicts an offset from an anchor rather than absolute coordinates, which is a far easier regression target.

IoU — overlap between two boxes:

IoU = area(A ∩ B) / area(A ∪ B)

NMS — the cleanup pass. Sort candidate boxes by confidence; take the top one; delete every remaining box whose IoU with it exceeds a threshold (typically 0.45); repeat.

🚨 Interview Trap

These are two different thresholds and interviewers love watching people conflate them. Confidence threshold decides whether a box exists at all. IoU/NMS threshold decides whether two surviving boxes are duplicates of the same object. Turning down confidence gives you more detections; turning down NMS IoU gives you fewer duplicates but risks deleting two genuinely overlapping passengers standing close together. In a crowded bus, NMS is what makes you undercount.

📊 ML Track Defense

Why mAP and not accuracy? Detection has no fixed set of predictions to be "accurate" about — the model outputs a variable number of boxes with confidences. So you sweep the confidence threshold, build a precision-recall curve per class, take the area under it (Average Precision), and average across classes → mAP. mAP@0.5 counts a detection correct at IoU ≥ 0.5; mAP@0.5:0.95 averages across stricter IoU cutoffs and is the harder, more honest number.

For passenger counting specifically, mAP is the model metric but not the product metric — I'd report count error (predicted vs actual headcount), because a box in slightly the wrong place doesn't matter if the count is right.

Making it work on a Raspberry Pi 4

A Pi 4 has an ARM Cortex-A72 CPU and no discrete GPU. Every millisecond is bought deliberately:

  • Resize aggressively — inference at 320×320 instead of 640×640 is roughly a 4× reduction in compute. Biggest single win.
  • Skip frames — passenger counts don't change 30 times a second. Process every Nth frame.
  • Adaptive confidence thresholding — a bus goes from tunnel dark to noon glare in seconds. A fixed threshold that works at noon silently drops passengers in a tunnel. Sampling frame brightness and shifting the threshold keeps recall stable across lighting.
  • Watch thermals — a Pi under sustained load throttles, and FPS quietly degrades over a long route. Hence the cooling fan in the enclosure. Mention this; it signals you've actually deployed hardware.

Quantization & export — know it as the next lever

PrecisionSizeSpeed on CPUAccuracy cost
FP321×BaselineNone
FP160.5×Helps on GPU, little on ARM CPUNegligible
INT80.25×Large — integer ops are ARM's strengthSmall, needs calibration data

ONNX Runtime is the portable, framework-agnostic route; NCNN is hand-tuned for ARM and usually faster still on a Pi. Be straight about what you did versus what you'd do next: the deployed pipeline hit 15 FPS through resolution and frame-skipping, and INT8 export is the obvious next step if the target moved higher.

💡 Senior Insight

Why INT8 barely hurts accuracy: trained weights cluster in a narrow range around zero, so 256 well-placed levels represent them nearly as well as 4 billion. The trick is calibration — run a few hundred representative images through, record the actual min/max activation range per layer, and map that range to INT8 rather than a guessed one. Skip calibration and you clip outliers, and accuracy falls off a cliff.

🛡️ SDE Defense

The architectural claim worth leading with: the frame never leaves the vehicle. The Pi turns a frame into an integer and discards the image. That's privacy enforced by architecture, not by policy — there is no video to leak, subpoena, or misconfigure a bucket for. It also removes a per-bus continuous video upload from the cost model and keeps the system counting through dead zones. Three wins from one placement decision.

04 Generative AI, Prompt Chaining & RAG

Self-attention, without the math anxiety

Every token emits three vectors: a Query ("what am I looking for?"), a Key ("what do I offer?"), and a Value ("here's my content"). Dot every query against every key to get relevance scores, softmax them into weights, and take a weighted sum of values.

Attention(Q,K,V) = softmax(QKᵀ / √d_k) · V
  • Why √d_k? Without it, dot products grow with dimension, softmax saturates, gradients vanish. It's a scaling fix, not a theoretical flourish.
  • Multi-head — run several attentions in parallel so different heads can track different relationships (syntax, coreference, topic) at once.
  • Positional encodings — attention is order-blind by construction, so position must be injected explicitly. Otherwise "chicken with rice" and "rice with chicken" are identical inputs.
💡 CP Intuition

Attention is a soft hash-map lookup. A dictionary returns the value for the one key that matches exactly. Attention returns a blend of all values, weighted by how well each key matches — differentiable, so it can be learned. And the cost is the thing to remember: every token attends to every token, so it's O(n²) in sequence length. That single fact explains context-window limits, why long prompts get expensive fast, and why chunking exists.

LoRA freezes the base model and trains two thin matrices whose product is added to a weight matrix — training a fraction of a percent of parameters, and adapters swap in and out without touching the base. QLoRA adds a 4-bit quantized base so it fits on one consumer GPU.

🚨 Interview Trap

"Fine-tune it so it stops hallucinating." Fine-tuning teaches behaviour and format, not facts. Training on your documents makes the model sound like them; it does not make it recall them reliably, and it will still invent confidently. Facts belong in the context window — that's RAG. Say this cleanly and you're ahead of most candidates in the room.

🛡️ SDE Defense

The reliability story, which is the actually impressive part. Gemini is a third-party API subject to rate limits, timeouts and regional blocks — so it's treated as an unreliable dependency, not a function call:

  • 6-second timeout — a hard ceiling, because a hung request is worse than a degraded answer.
  • 2 retries, exponential backoff (1s → 2s) — absorbs transient failures without hammering a rate-limited endpoint.
  • Deterministic fallbacks — resume parsing degrades to a regex parser, question generation to pre-written role scripts, coding tasks to a curated challenge bank.
  • Constrained output — the branch decision must be one of four tokens. Anything else is rejected, so a hallucination can't become a state transition.

Net effect: an outage degrades the interview's adaptiveness; it never ends the session.

RAG pipeline

Ingest → chunk → embed → index → retrieve → generate. Chunking is where most RAG systems are quietly won or lost.

StrategyHowTrade-off
Fixed-sizeEvery N charactersSimple; cuts sentences in half
Recursive characterSplit on ¶ → sentence → word until it fitsRespects structure — the sane default
SemanticSplit where embedding similarity dropsBest boundaries, costs an embedding pass
Document-awareSplit on headings/sectionsExcellent for structured PDFs
📊 ML Track Defense

Chunk size and overlap, with the reasoning attached. For multi-page PDFs I used recursive character splitting at roughly [1000] characters with [150–200] overlap. The logic, which matters more than the number:

  • Too small → a chunk retrieves without the context that makes it meaningful ("it must be renewed annually" — what must?).
  • Too large → the embedding averages several topics, so the vector points nowhere specific and retrieval precision collapses. You also burn context window on irrelevant text.
  • Overlap exists so a fact spanning a boundary survives in at least one chunk intact. ~15% is the usual sweet spot; more is just duplicated storage.

Then say how you'd verify it: build a small set of question–answer pairs from the documents and measure retrieval hit-rate at different chunk sizes. Tuning by measurement beats tuning by vibes, and interviewers notice the difference.

Similarity & index types

  • Cosine similarity — angle only, ignores magnitude. The default for text, since document length shouldn't affect topical similarity. (On normalized vectors, cosine and dot product are identical.)
  • Flat — brute-force compare against everything. Exact, fine up to ~100k vectors.
  • HNSW — a navigable small-world graph; fast and accurate, higher memory. The common production choice.
  • IVFFlat — cluster vectors, search only the nearest few clusters. Lower memory, needs training and a tuned probe count.
💡 CP Intuition

HNSW is skip lists in high dimensions. A skip list layers sparse express lanes over a linked list so you cover distance fast and drop down for precision; HNSW layers sparse long-range graph edges over dense local ones and does exactly the same descent. Same logarithmic-navigation idea you'd use for range queries — which is why approximate nearest neighbour is a search-structure problem, not an ML problem.

Multi-agent orchestration (LangChain + CrewAI)

Splitting one large task into specialized agents with a shared state:

AgentJobWhy separate
ParserExtract structure from the PDFDeterministic, cacheable, runs once
RetrievalFetch relevant chunks per sub-questionOnly this agent needs the vector store
ValidatorCheck claims against retrieved sourcesA separate pass catches what generation missed

The real reason to split: each agent gets a small, focused context window instead of one prompt trying to hold the whole document, the question, and the instructions at once.

🚨 Interview Trap

"So agents are better?" No — agents multiply your failure modes: loops, drift, compounding errors from step one, and cost that's hard to predict. State your default plainly: single-pass RAG unless I can name the specific step single-pass cannot do. Multi-hop questions and cross-document comparison are real cases. "Summarize this contract" is not.

RAGAS — how to evaluate the thing

  • Context relevance — did retrieval fetch the right chunks? (Retriever's fault if low.)
  • Faithfulness — is the answer actually supported by those chunks? (Low = hallucination.)
  • Answer relevance — does it address the question asked?

These three isolate where the pipeline broke. Good context but low faithfulness = a generation problem. Low context relevance = a chunking or embedding problem. That diagnostic split is the whole point of the framework.

05 Search AI & Deterministic Game Engines

Minimax

Two-player zero-sum with perfect information. You maximise, the opponent minimises, recursively down to a depth limit, then a heuristic scores the leaf.

Minimax with alpha-beta pruning 
def minimax(board, depth, alpha, beta, maximizing):
    if depth == 0 or board.is_game_over():
        return evaluate(board)

    if maximizing:
        best = -INF
        for move in ordered_moves(board):          # ordering drives the pruning
            board.push(move)
            best = max(best, minimax(board, depth-1, alpha, beta, False))
            board.pop()
            alpha = max(alpha, best)
            if beta <= alpha:
                break                              # β cutoff — opponent avoids this line
        return best
    else:
        best = INF
        for move in ordered_moves(board):
            board.push(move)
            best = min(best, minimax(board, depth-1, alpha, beta, True))
            board.pop()
            beta = min(beta, best)
            if beta <= alpha:
                break                              # α cutoff
        return best

What α and β mean: α is the best score the maximiser has already guaranteed somewhere; β is the best the minimiser has guaranteed. When β ≤ α, this branch is one the opponent will simply never allow — so exploring it further cannot change the final answer.

O(b^d) → O(b^(d/2)) with perfect move ordering
🚨 Interview Trap

"Does pruning change the move it picks?" No. Alpha-beta is provably identical to plain minimax at the same depth — it only skips work that could not affect the result. What does vary is speed, and it varies enormously: best-move-first ordering approaches the b^(d/2) bound, worst-first prunes essentially nothing. That's why move ordering (captures first, then checks) is where the real engineering goes.

Follow-up: "why depth 3?" It's a latency budget, not a quality target — depth 3 is where a pure-Python search still responds fast enough to feel instant. Strong play comes from Stockfish; the Python search exists as a fallback when the binary won't start.

💡 CP Intuition

Alpha-beta is branch-and-bound, the same pruning you use in backtracking problems like N-Queens or subset-sum: maintain a bound, and abandon any branch that provably cannot beat it. Chess just makes the bound two-sided because two opposed players are optimizing. If you've written a pruned DFS, you've written alpha-beta.

Evaluation function

A leaf isn't a finished game, so you score it with a heuristic — two parts:

  • Material — pawn 1, knight/bishop 3, rook 5, queen 9.
  • Piece-Square Tables — a per-piece 64-value grid encoding where a piece is good. A knight on the rim is weak; a central knight is strong. A pawn's value rises as it advances.
score = Σ(material) + Σ(PST[piece][square])
📊 ML Track Defense

Why hand-crafted heuristics rather than a learned evaluator? Because chess rules are fully known and enumerable, so search gives you correctness that learning would only approximate — and a PST is inspectable, so a wrong move is debuggable. Learned evaluation (AlphaZero-style) wins only at scale: enormous self-play compute, and you trade explainability for strength. Use search when you have a computable model of the world; use learned models when you only have examples. Chess is the former; food images are the latter. Being able to say why the same person chose differently on two projects is the answer they're actually testing.

Integrating Stockfish

  • UCI — Universal Chess Interface. You spawn the binary as a subprocess and talk plain text over stdin/stdout: position fen ..., go depth 10, read back bestmove e2e4.
  • ELO limiting — UCI_LimitStrength + UCI_Elo 1800 caps strength so the bot is beatable. Full-strength Stockfish is an unplayable opponent, not a feature.
  • Polyglot opening book — a .bin of position hashes mapped to known-good moves. Instant, human-like openings with zero search; the engine only starts thinking once you leave the book.
🛡️ SDE Defense

The three-tier degradation is the design worth naming: opening book → Stockfish → in-process minimax. Each tier is faster-but-dumber than the one before, and every tier is local, so an AI move never depends on a third-party network call. The failure mode of a missing Stockfish binary is a weaker opponent, not a broken game. That's the same instinct as RecrutAI's fallback chain, applied to a different dependency.

Track A — SDE (integration & performance)

A · Q1
1. How do you serve PyTorch and spaCy models behind FastAPI without blocking the event loop?

A model forward pass is CPU-bound and synchronous — put it directly in an async def and it stalls every other request on that worker.

The fix is small and specific: declare the inference route as a plain def, not async def. FastAPI automatically runs sync route handlers in a threadpool, so the loop stays free. For anything heavier, run_in_executor with a bounded process pool, or move inference behind its own service.

Also: load the model once at startup, not per request — a ResNet-50 load is seconds and hundreds of MB. And cap concurrency deliberately, because N parallel inferences means N copies of activation memory.

Trade-off: threadpool workers are finite, so under load requests queue rather than fail. That's the correct failure mode — a bounded queue beats an OOM.

A · Q2
2. Why decouple the Flask AI service from the Node.js Socket.IO server in Chessify?

Because the two jobs have opposite concurrency shapes. Multiplayer is hundreds of mostly-idle sockets — pure I/O, ideal for an event loop. A Stockfish or minimax search pins a core for hundreds of milliseconds — pure CPU.

In one Node process, a single bot move would freeze every live game on the server, because there's one thread executing JavaScript. Split, an engine slowdown makes bot moves slower and nothing else. They also deploy and restart independently.

Trade-off: a network hop and a second service to operate. Worth it, because the alternative is a global stall triggered by one user's move.

A · Q3
3. How do deterministic fallbacks keep a Gemini outage from crashing a live screening?

By treating the LLM as an unreliable dependency with a hard latency ceiling. Every call is wrapped: 6-second timeout, 2 retries with exponential backoff (1s then 2s), and on final failure the system degrades rather than throws.

Each stage has a deterministic substitute — resume parsing falls back to a regex parser, question generation to pre-written role scripts, coding tasks to a curated challenge bank. Responses are also shape-validated before use, so a malformed reply triggers the fallback instead of propagating a bad object.

Trade-off: fallback interviews are scripted, not adaptive. That's a deliberate choice — a candidate mid-interview needs a working session far more than an optimal one.

A · Q4
4. How do you version model weights and handle large binaries in CI?

Plain Git is disqualified immediately: it stores a full copy of every version forever, so a 100 MB .pth committed ten times is a gigabyte every clone must download, with no useful diffing on binary data.

Git LFS replaces the file with a small pointer and stores the bytes separately (.gitattributes holds the tracking rules). The payoff is atomic code-to-weights pairing — checking out the commit that produced a result also checks out the exact weights that produced it. In CI, that means runners can skip LFS fetch entirely for lint and unit jobs and pull weights only for the inference test.

When I'd outgrow it: LFS has bandwidth quotas and stores no metadata. Past a few GB or a real team, S3 or a model registry (MLflow, HF Hub) with a version pointer in Git.

A · Q5
5. Latency, bandwidth and privacy trade-offs of edge vs cloud inference?

Latency: edge is bounded and local — no network variance. Cloud round-trip is unpredictable on a moving vehicle and unbounded when connectivity drops.

Bandwidth: edge sends an integer per reading; cloud sends continuous video per bus. The cost gap widens linearly with fleet size, so cloud gets worse exactly as the product succeeds.

Privacy: the decisive one. On-device, the frame becomes a count and is discarded — there is no passenger video to leak or subpoena. Privacy by architecture, not policy.

What I gave up: model capacity (YOLOv5n's ~1.9M params vs a full-size model's ~87M) and easy updates — new weights must be pushed to every device rather than deployed once. For "how full is this bus," approximate is fine, so it's a good trade. For something requiring high precision, it wouldn't be.

B · Q1
1. Walk me through training your custom spaCy NER model.

Annotation: meal strings labelled with character-offset spans for a single custom FOOD entity — spaCy converts those offsets to BILOU tags internally, which is what keeps "grilled chicken breast" one entity rather than three.

Splits: roughly [70/15/15] train/val/test, split by sentence so the same meal string can't land on both sides. Validation drove early stopping; test was touched once at the end.

Training: blank English pipeline (not a pretrained NER model, to avoid inheriting irrelevant entity types), compounding batch sizes, dropout ~0.35 to stop it memorizing the small dataset.

Metrics: report your real P/R/F1 — and more importantly, which one you optimized. I favoured recall: a missed food silently undercounts calories, while a false positive gets filtered when the USDA fuzzy match scores it low. Having a second filter downstream is what lets stage one be greedy.

B · Q2
2. Why ResNet-50? Which layers were frozen, what LR schedule, why Dropout 0.5?

ResNet-50 because residual connections make a 50-layer network trainable (the +x gives gradients a path back), ImageNet pretraining already encodes texture and shape features that transfer directly to food, and it's the accuracy/size sweet spot — ResNet-18 underfits fine-grained food distinctions, ResNet-152 is heavier for marginal gain.

Freezing: started with the full backbone frozen, training only the new head — fastest path to a baseline and the right call on a small dataset. Then optionally unfroze layer4 (the most task-specific block) at a much lower LR.

LR: normal (~1e-3) for the randomly-initialised head; roughly 10–100× lower for any unfrozen backbone layer. Those pretrained weights are already good — large gradients would destroy them. That's the whole idea behind discriminative learning rates.

Dropout 0.5: the head is where overfitting concentrates — it's the only part learning, from a small dataset. 0.5 is standard for fully-connected layers; conv layers use far less because weight sharing already regularizes them.

B · Q3
3. IoU vs NMS in YOLOv5, and how did adaptive thresholding fix false negatives?

IoU is a measurement — intersection over union of two boxes, a number from 0 to 1. NMS is an algorithm that uses it: sort boxes by confidence, keep the highest, discard every remaining box with IoU above ~0.45 against it, repeat. IoU is the ruler; NMS is the cleanup.

The two thresholds are different things — confidence decides if a box exists, NMS IoU decides if two boxes are the same object. Conflating them is the classic slip.

Adaptive thresholding: a bus goes from tunnel-dark to noon-glare within seconds. A fixed confidence threshold tuned for bright light produces low-confidence detections in the dark that get filtered out — passengers vanish, and it fails silently. Sampling frame brightness and lowering the threshold in poor light keeps recall stable. The trade is more false positives in the dark, which is the right direction: overcounting by one is a better failure than reporting an empty bus that's full.

B · Q4
4. How do you evaluate and reduce hallucinations in RAG? What chunk size and overlap?

Evaluate by splitting the blame. RAGAS-style: context relevance (did retrieval fetch the right chunks?), faithfulness (is the answer supported by them?), answer relevance (does it address the question?). Good context but low faithfulness is a generation problem; low context relevance is a chunking or embedding problem. Without that split you're guessing which half to fix.

Reduce by: requiring citations back to chunk IDs, instructing the model to answer "not in the provided documents" rather than infer, constraining output to a schema, and adding a validator pass that re-checks claims against sources.

Chunking: recursive character splitting at ~[1000] chars with [150–200] overlap. Too small and a chunk loses the context that makes it meaningful; too large and the embedding averages multiple topics, so the vector points nowhere specific and retrieval precision drops. Overlap ensures a fact spanning a boundary survives intact in at least one chunk. I'd verify the choice by building question–answer pairs from the documents and measuring retrieval hit-rate across chunk sizes rather than guessing.

B · Q5
5. How does α-β pruning cut branches, and how does your evaluation function score position?

Pruning: α = the best value the maximiser has already secured; β = the best the minimiser has secured. Explore a branch, and the moment β ≤ α you stop — the opponent already has a better option elsewhere and will never permit this line, so its remaining moves cannot change the root decision. It's branch-and-bound with two bounds because two opposed players are optimizing.

Effect: with good move ordering, O(b^d) → roughly O(b^(d/2)) — same answer, roughly double the reachable depth for the same time budget. With bad ordering you prune almost nothing, which is exactly why captures and checks are searched first.

Evaluation: material (pawn 1 … queen 9) plus piece-square tables — a 64-value grid per piece type encoding where that piece is strong. Central knights score above rim knights; advanced pawns score above home-rank pawns. Sum both from the side to move's perspective. It's hand-tuned and inspectable, which means a bad move is debuggable — you can point at the term that caused it.

B · Q6
6. How do you process real-time sensor streams to detect driving anomalies (Drive-Sure)?

The signal: accelerometer and gyroscope readings at high frequency. Harsh braking is sustained negative longitudinal acceleration; harsh cornering is lateral acceleration past a threshold; rapid acceleration is the positive mirror.

The pipeline: (1) smooth the raw stream — a moving average or low-pass filter, because a single spike is road noise, not a braking event; (2) detect over a sliding window, since an event is a sustained pattern over ~1–2 seconds, not one sample; (3) emit discrete events rather than raw readings, so what leaves the device is "harsh brake, severity 0.8, at timestamp T" — small, meaningful, and cheap to store; (4) aggregate events into a rolling risk score, normalized per distance travelled so a long trip isn't penalized for having more events.

Storage: append-only time-series, partitioned by time, with raw kept hot briefly and events kept long-term.

The hard part, and say so: thresholds are vehicle- and mount-dependent, and a phone lying loose on a seat generates spikes that look identical to braking. Calibration — establishing a per-device baseline orientation before scoring — is what separates a demo from a product.
