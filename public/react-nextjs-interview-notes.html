React Fundamentals

JSX

JSX is syntactic sugar over React.createElement(type, props, ...children). It's not HTML — it's an expression that compiles to plain JS function calls, which is why you can drop {expressions} anywhere and why a component must return a single root (or a Fragment).

Compiles to
const el = <h1 className="title">Hi {name}</h1>

// becomes
const el = React.createElement("h1", { className: "title" }, "Hi ", name)
📌 Likely to be asked

"Why can't a component return two sibling elements without a wrapper?" → Because JSX compiles to one createElement call; a Fragment (<>...</>) is the free wrapper that doesn't add a DOM node.

Components · Props vs State

A component is a function that takes props (input, owned by the parent, read-only) and returns JSX. State is data owned and mutated by the component itself, and changing it triggers a re-render.

PropsState
Owned byParent, passed downThe component itself
Mutable?No — read-only inside the childYes, via setter (never mutate directly)
Triggers re-render?When parent re-renders with new valuesWhen the setter is called with a new value
AnalogyFunction argumentsLocal variables with a re-render side effect
⚠️ Interview trap

"Can a child modify its own props?" No — but it can call a callback passed down as a prop (e.g. onChange) so the parent updates its state and passes new props down. This is the core of unidirectional data flow.

Hooks

All hooks follow the Rules of Hooks: call only at the top level (never in loops/conditions/nested functions) and only from React function components or other hooks. This is because React tracks hooks by call order across renders, not by name.

useState
const [count, setCount] = useState(0)
// functional update avoids stale closures when new value depends on old
setCount(prev => prev + 1)
useEffect
useEffect(() => {
  const id = setInterval(() => setTick(t => t + 1), 1000)
  return () => clearInterval(id) // cleanup — runs before next effect + on unmount
}, [dep]) // [] = mount only · omitted = every render · [dep] = when dep changes
useContext
const theme = useContext(ThemeContext) // subscribes to nearest Provider above
useMemo vs useCallback
const sorted = useMemo(() => expensiveSort(list), [list]) // memoizes a VALUE
const handleClick = useCallback(() => doThing(id), [id])  // memoizes a FUNCTION reference
⚠️ Interview trap

useMemo/useCallback are not free — they cost a comparison + cache slot every render. Only reach for them when (a) the computation is genuinely expensive, or (b) you need referential stability to avoid breaking React.memo on a child or re-triggering a useEffect dependency.

Custom Hooks

A custom hook is just a function starting with use that calls other hooks internally — it's a way to extract and share stateful logic (not state itself; each caller gets its own independent state).

function useMediaQuery(query) {
  const [matches, setMatches] = useState(false)
  useEffect(() => {
    const mql = window.matchMedia(query)
    const onChange = () => setMatches(mql.matches)
    onChange()
    mql.addEventListener("change", onChange)
    return () => mql.removeEventListener("change", onChange)
  }, [query])
  return matches
}
📌 Likely to be asked

"Do two components using the same custom hook share state?" No — every call to the hook creates its own isolated state via its own useState call. Only the logic is shared, not the data.

Virtual DOM & Reconciliation, Keys

React keeps a lightweight JS object tree (the virtual DOM). On state change it builds a new tree, diffs it against the previous one (reconciliation), and patches only the real DOM nodes that changed — because real DOM writes are expensive, JS object diffing is cheap.

Diffing heuristics: different element types → tear down and rebuild the whole subtree; same type → keep the DOM node and update only changed attributes; lists → matched by key, not by position.

⚠️ Interview trap

Using array index as key works fine for static lists but breaks badly when items are reordered/inserted/removed — React matches by key, so it will reuse the wrong DOM node's local state (e.g. an input's typed value ends up on the wrong row). Always use a stable, unique ID.

Lifting State Up

When two sibling components need to share/sync data, move the state to their nearest common parent and pass it down as props (plus a callback to mutate it). It's the vanilla-React answer to "how do siblings communicate" before reaching for Context or a state library.

🎯 Common follow-up

"What if the components are far apart in the tree?" → Lifting state all the way up causes prop drilling; that's the segue into Context API or a state library.

⚠️ Interview trap

Context is not a performance optimization or a state manager — it's a dependency-injection mechanism. Every component consuming a context re-renders on any change to that context's value, which is why high-frequency state (e.g. live board position, mouse coordinates) in Context can get expensive without splitting contexts or memoizing consumers.

Next.js Fundamentals

SSR vs SSG vs ISR vs CSR

When HTML is builtData freshnessGood for
CSRIn the browser, after JS loadsAlways fresh (client fetch)Dashboards, highly interactive/authenticated pages
SSRPer request, on the serverAlways freshSEO-sensitive pages with per-user/per-request data
SSGAt build timeFixed until next buildMarketing pages, docs, blogs
ISRAt build time, then regenerated in the background on a timer/on-demandEventually fresh (stale-while-revalidate)Product pages, content that changes but not every request
📌 Likely to be asked

"How does ISR actually work?" → The first request after the revalidate window serves the (now stale) cached page while Next.js regenerates it in the background; the next request gets the fresh version. No request ever blocks on regeneration.

App Router vs Pages Router

⚠️ Interview trap

"Server Components" ≠ SSR. SSR is about when HTML is rendered (per request vs build time); Server Components are about where a component's code ever runs (only on the server — its JS bundle is never shipped to the client at all). You can have SSR with only Client Components (Pages Router did this for years).

Routing

Both routers are file-system based: a folder/file path maps directly to a URL. Dynamic segments use brackets.

app/ ├── page.tsx → / ├── about/page.tsx → /about ├── blog/[slug]/page.tsx → /blog/:slug (params.slug) └── game/[gameId]/page.tsx→ /game/:gameId (params.gameId)

Other conventions: [...slug] catch-all, [[...slug]] optional catch-all, (group) route groups that don't affect the URL.

API Routes

Backend endpoints colocated with your frontend code — no separate server needed for simple use cases.

App Router — app/api/hello/route.ts
export async function GET(request: Request) {
  return Response.json({ message: "hi" })
}
export async function POST(request: Request) {
  const body = await request.json()
  return Response.json({ received: body })
}

In the Pages Router these are a single default-exported handler keyed off req.method instead of separate named exports (see the repo deep-dive below — this project actually uses the older style inside an App Router app).

Middleware

Code in middleware.ts at the project root that runs before a request completes, at the edge — used for auth gating, redirects, A/B routing, header rewriting. It runs on every matched request and can't touch the DOM or do heavy computation (it's a lightweight Edge runtime, not Node).

export function middleware(request: NextRequest) {
  const token = request.cookies.get("session")
  if (!token) return NextResponse.redirect(new URL("/login", request.url))
  return NextResponse.next()
}
export const config = { matcher: ["/dashboard/:path*"] }

Data Fetching Patterns

  • Server Components: just await fetch() directly in an async component — no useEffect/loading state needed for initial data.
  • Caching: fetch(url, { cache: 'force-cache' }) (default, SSG-like) vs { cache: 'no-store' } (SSR-like) vs { next: { revalidate: 60 } } (ISR-like).
  • Client Components: still use useEffect + fetch, or a library like SWR/React Query for caching, revalidation, and request dedup.
  • Parallel vs waterfall: kick off independent fetch() calls without awaiting each one sequentially, then Promise.all — a classic perf follow-up question.

Image & Font Optimization

next/image auto-generates responsive srcsets, lazy-loads offscreen images, serves modern formats (WebP/AVIF), and prevents layout shift by reserving space via required width/height (or fill).

next/font self-hosts Google/local fonts at build time (no runtime request to Google), inlines font-display config, and avoids the render-blocking external font request entirely — directly improves CLS/LCP.

One-liner for interviews: Next.js is to React what a full framework is to a library — React answers "how do I build UI," Next.js answers "how do I ship a full app around that UI."

useEffect vs useLayoutEffect

useEffectuseLayoutEffect
TimingAsynchronously, after the browser paintsSynchronously, after DOM mutations but before the browser paints
Blocks paint?NoYes
Use whenAlmost always — data fetching, subscriptions, loggingYou must measure/mutate the DOM before the user sees a flicker (e.g. reading layout to reposition a tooltip)
📌 Likely to be asked

"What breaks if you use useEffect for a DOM measurement that repositions an element?" → A visible flash: the browser paints the wrong position first, then your effect fires and snaps it — useLayoutEffect avoids that flash by running before paint.

memo vs useMemo vs useCallback

React.memouseMemouseCallback
What it wrapsA componentA computed valueA function
PreventsRe-render of the component if props are shallow-equalRe-computation of an expensive value if deps unchangedRe-creation of a function reference if deps unchanged
Typical pairingWraps a child that receives a callbackFeeds a value into JSX or another hook's depsFeeds a stable function into a memo'd child's props or an effect's deps
⚠️ Interview trap

React.memo on a component is wasted if you pass it an inline arrow function or object literal as a prop — a new reference is created every parent render, so the shallow-equality check always fails. That's exactly why useCallback/useMemo exist: to stabilize what you hand to a memoized child.

Architecture at a glance

Frontend/ # Next.js app ├── app/ │ ├── page.tsx # mode select │ └── game/[gameId]/page.tsx # dynamic PvP room route ├── components/ │ ├── chess-game.tsx # root layout component │ ├── game-context.tsx → Context provider: ALL game state + socket wiring │ ├── chessboard.tsx → parses FEN, renders 64 squares │ └── chess-piece.tsx → draggable piece ├── lib/pvpSocket.ts → socket.io-client singleton └── pages/api/chess.ts → Pages Router API route (proxies AI move requests) Chess-PvP/server.js # Node + Socket.IO: room-based move validation

One GameProvider context holds the entire game (board, timers, chat, PvP roles) and exposes it via useGame() to every component in the tree — a textbook "Context as a mini state manager" setup.

Live board state & socket sync components/game-context.tsx

The provider tracks both AI-mode and PvP-mode state in the same context, and wires up Socket.IO listeners inside a useEffect gated on gameType === "pvp" — a clean example of conditionally running effects based on a mode flag, with cleanup on unmount via the socket connection lifecycle.

const [game, setGame] = useState(new Chess())
const [fen, setFen] = useState(game.fen())
const [history, setHistory] = useState<Move[]>([])
// ...12+ more useState calls for timers, selection, chat, PvP roles, etc.

// PvP socket setup
useEffect(() => {
  if (gameType !== "pvp" || !gameId) return

  pvpSocket.connect()
  pvpSocket.emit("join-room", gameId)

  pvpSocket.on("role", (role: string) => {
    if (role === "white") { setAssignedColor("w"); setBoardFlipped(false) }
    else if (role === "black") { setAssignedColor("b"); setBoardFlipped(true) }
    else setAssignedColor("spectator")
  })

  pvpSocket.on("sync-board", (fenStr: string) => {
    setGame(new Chess(fenStr))
    setFen(fenStr)
  })
  // ...more listeners: opponent-joined, opponent-move, move-confirmed, chat, spectator-count
}, [gameType, gameId])
💼 Resume tie-in

"I built a GameProvider around React Context to centralize board state, timers, and PvP socket state behind a single useGame() hook, so components like the board and move history never touch Socket.IO directly — they just read reactive state. On join, the client emits join-room and the server replies with a role and a sync-board FEN so late joiners and spectators get the current position instead of an empty board."

🎯 Common follow-up

"Why 15+ separate useState calls instead of one useReducer?" Honest answer: it grew incrementally and most of the state is genuinely independent (a timer tick doesn't need to know about chat messages). The real tradeoff to name in an interview: separate useStates mean more re-render triggers scattered across the file and no single place to see all valid state transitions; a reducer would centralize the PvP event → state-transition logic (role assigned, board synced, move confirmed) into one switch statement, which is easier to reason about and test in isolation.

Socket event handling components/game-context.tsx

The opponent-move handler is a good example of a functional state update used specifically to avoid a stale closure over game — the socket callback was registered once inside the effect, so it can't rely on the game variable from that render being current by the time the event fires later.

pvpSocket.on("opponent-move", ({ from, to, promotion }) => {
  setGame((prev) => {
    const newGame = new Chess(prev.fen())   // fresh instance from latest state
    const move = newGame.move({ from, to, promotion })
    if (move) {
      setFen(newGame.fen())
      setHistory((h) => [...h, move])
      setCurrentMove((c) => c + 1)
      setLastMove({ from, to })
    }
    return newGame
  })
})
💼 Resume tie-in

"Because the socket listener is registered inside a useEffect that only runs once per game session, I used the functional form of setGame(prev => ...) everywhere a handler needed the current board — that sidesteps the stale-closure bug where the listener would otherwise keep referencing whatever game was at mount time."

⚠️ Flag in your own code

chess.js's Chess instance is mutable — calling .move() mutates it in place. That's exactly why the code always does new Chess(prev.fen()) instead of calling .move() on the existing instance: React compares state by reference, so mutating game directly and calling setGame(game) would be a no-op — same reference, no re-render. Be ready to explain this if asked "why re-instantiate the whole Chess object on every move instead of mutating it?"

Board rendering & re-renders components/chessboard.tsx

On every fen change, an effect re-parses the FEN string into an 8×8 array, and the component then rebuilds all 64 <Square> / <ChessPiece> elements from scratch — none of the child components are wrapped in React.memo.

useEffect(() => {
  const fenBoard = fen.split(" ")[0]
  const rows = fenBoard.split("/")
  const newBoard = rows.map(parseRow) // full 2D array rebuilt every fen change
  setBoard(newBoard)
}, [fen])

// renderBoard() then maps over all 64 squares unconditionally —
// no memoization on <Square> or <ChessPiece>
🎯 Common follow-up

"How would you optimize re-renders here?" Solid answer path:

  • Wrap Square and ChessPiece in React.memo so only the ~2 squares involved in a move actually re-render, instead of all 64.
  • That requires each square's props (isLastMove, isLegalMove, etc.) to be primitives or stable references — currently fine since they're booleans/strings, so memo's shallow comparison would actually work here.
  • The parsed board array itself could be derived with useMemo(() => parseFen(fen), [fen]) instead of useState + useEffect — it's a pure derivation from fen, not real state, so this removes an unnecessary render pass (state update → re-render → commit).
⚠️ Flag in your own code

This is a strong "why did you structure it this way" target: deriving board via useState+useEffect instead of useMemo is a common real-world anti-pattern — it's state that mirrors other state, which means an extra render cycle every single move. Good to proactively acknowledge if asked to walk through the component.

Optimistic vs authoritative moves makeMove() branching logic

const makeMove = (from, to, promotion?) => {
  if (gameType === "pvp") {
    // no local board mutation — just ask the server
    pvpSocket.emit("move", { roomId: gameId, from, to, promotion })
    return true
  }
  // AI mode: apply the move locally immediately
  const newGame = new Chess(game.fen())
  const move = newGame.move({ from, to, promotion })
  if (move) { setGame(newGame); setFen(newGame.fen()); /* ... */ }
}
💼 Resume tie-in

"In PvP mode the client never applies a move locally — it emits move to the server and waits for move-confirmed or opponent-move before the board updates. The Node server re-validates every move with chess.js, so the client is never the source of truth — this closes off client-side move spoofing, which matters in a real-time PvP game with spectators watching a shared state."

🎯 Common follow-up

"Why not apply the move optimistically on the client, then reconcile if the server rejects it?" Because chess moves are validated deterministically and near-instantly server-side over a low-latency socket, the UX cost of the round-trip is small, and it fully removes an entire class of desync bugs (rolling back an illegal move that already rendered). Trade-off worth naming: for a slower or higher-latency backend, this non-optimistic approach would feel laggy, and you'd want optimistic UI + reconciliation instead.

App Router + Pages API route, side by side

The app uses the App Router (app/page.tsx, app/game/[gameId]/page.tsx) for pages, but the AI-move proxy endpoint is a legacy Pages Router handler at pages/api/chess.ts — Next.js supports both conventions coexisting in one project.

// pages/api/chess.ts — Pages Router style, works alongside app/
export default async function handler(req: NextApiRequest, res: NextApiResponse) {
  const { fen, depth } = req.body
  const apiRes = await fetch("https://chess-api.com/v1", {
    method: "POST",
    headers: { "Authorization": `Bearer ${process.env.CHESS_API_KEY}` },
    body: JSON.stringify({ fen, depth, maxThinkingTime: 100 }),
  })
  res.status(apiRes.status).json(await apiRes.json())
}
🎯 Common follow-up

"Why is there a pages/api route in an App Router project — was that intentional?" Be upfront: it's most likely leftover from scaffolding/an earlier migration rather than a deliberate choice, since App Router's own app/api/chess/route.ts Route Handler convention does the same job. It's a fine opportunity to show you know the two aren't meant to coexist as a long-term pattern — you'd migrate it to a Route Handler for consistency, and it also matters for env vars: this route keeps CHESS_API_KEY server-side either way, but consolidating on one router convention avoids confusion about which caching/runtime rules apply to which API surface.
