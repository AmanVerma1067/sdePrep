Databases — Practical Choice

PostgreSQL vs MySQL vs MongoDB — when to choose which

You've genuinely used all three across different projects, so the strongest interview answer isn't "Postgres is better" — it's "here's the shape of data and access pattern that made me pick each one," backed by your own projects below.

MongoDB wouldn't make anything easier here and would lose the query-planner-optimized aggregation Postgres already gives for free.

Node.js + PostgreSQL (Neon) — bus occupancy events from edge cameras
github.com/AmanVerma1067/SahYatri →

Why PostgreSQL for time-series sensor data

-- Effective shape of the occupancy table, from the insert/query code
occupancy (id, camera_id, occupancy, capacity, timestamp)

-- The query that justifies the choice: server-side aggregation,
-- not pulling rows into Node to reduce them
SELECT COUNT(*) total_records, AVG(occupancy) avg_occupancy,
       MAX(timestamp) latest_timestamp, COUNT(DISTINCT camera_id) unique_cameras
FROM occupancy;

Every event has the exact same shape — a camera ID, a reading, a capacity, a timestamp. There's no nested structure, no per-event variability, and the entire point of the data is answering aggregate questions across time (average occupancy, latest reading, per-camera trends). That's precisely the workload relational engines are built to optimize: an indexed GROUP BY/AVG/COUNT query plan, computed inside the database rather than shipping raw rows to the application to reduce by hand.

💼 Resume tie-in

"I chose PostgreSQL for SahYatri because the sensor data is uniform and fixed-shape, and the product's value is almost entirely in aggregate queries over time — average occupancy, latest reading per camera, trend summaries. Postgres computes those server-side with an optimized query plan; doing the equivalent in MongoDB would mean either an aggregation pipeline reimplementing SQL's GROUP BY semantics, or pulling raw documents into the app and reducing them there — more code, no real benefit, for data that was never going to have a variable shape."

🎯 Common follow-up

"MySQL can do the same aggregate queries — why Postgres over MySQL specifically here?" → Fair challenge to be ready for: for a table this simple, MySQL genuinely would work about as well. The honest reasons to name are ecosystem ones rather than a hard technical requirement — Postgres's JSONB gives room to add semi-structured event metadata later without a schema migration, and hosted-Postgres options like Neon (used here) offer a serverless/branching workflow that fit a fast-moving side project well. Worth being honest that this wasn't a workload MySQL would have struggled with.

📚 StudySync backend (timetable-api)
Express + MongoDB (Mongoose) — academic timetable data behind the StudySync Flutter app
github.com/AmanVerma1067/StudySync →

Why MongoDB for flexible scheduling data

// Actual Mongoose schema — timetableData is an array containing ONE Map,
// keyed by numeric batch ID, each value a nested per-day session structure
const timetableSchema = new mongoose.Schema({
  timetableData: {
    type: [{
      type: Map,
      of: new mongoose.Schema({
        batch: { type: String, required: true },
        Monday: [sessionSchema],   // variable-length array of sessions
        Tuesday: [sessionSchema],  // per day — could be 0, could be 6
        // ...Wednesday–Saturday
      })
    }],
    required: true
  }
})

The number of batches, the number of sessions per day, and even which days have sessions at all — all genuinely vary per timetable and per term. Modeling that relationally means either a sparse wall of nullable columns, or normalizing into batches → days → sessions tables with joins just to reconstruct one timetable view. MongoDB lets the whole nested, variable-shape structure be read and written as one document — which matches exactly how the app actually consumes it (fetch one timetable, render it whole).

💼 Resume tie-in

"StudySync's timetable data is inherently variable-shape — different batches, different numbers of sessions per day, sessions that don't exist on some days at all. I used MongoDB with a nested document (a Map of batches, each holding per-day arrays of sessions) so the whole timetable reads and writes as one document instead of being reconstructed from a join across normalized tables on every request. Given the read pattern is always 'give me this whole timetable,' not 'give me one session,' the document model matched the access pattern directly."

⚠️ Interview trap — be ready to own this

If asked to defend the schema itself: the validator enforcing arr.length === 1 with numeric-string Map keys is a workaround for a design that's arguably one level too clever — a flatter array of {batch, day, sessions} documents (one document per batch, or even per batch-day) would avoid needing a custom Mongoose validator to keep the outer array pinned to exactly one element. Good to acknowledge this proactively rather than defend the current shape as optimal — it works, but "what would you change" has a real answer here.

🎯 Common follow-up

"Given MongoDB has no schema enforcement by default, what stops garbage data from getting written?" → Mongoose itself — the app doesn't touch the raw mongodb driver for writes, it goes through a Mongoose schema with required fields and a custom validator function, so structural validation happens at the application/ODM layer even though the database itself would happily accept anything.

DigiFlute internship — MongoDB Atlas for multi-tenant SaaS

No public repo, but a good third data point when asked "why MongoDB again here, if you also used Postgres."

The internship product's core object (a packaging specification) has the same "variable nested structure, always read/written whole" profile as StudySync's timetables, just at higher stakes — dynamically configurable groups and fields per client. Atlas specifically (managed MongoDB) removed the operational overhead of running a replica set yourself, which mattered more there than in a solo side project.

📌 Likely to be asked

"You used MongoDB in two projects and Postgres in one — do you have a real opinion, or did you just use whatever was around?" → Point back to the pattern across both: MongoDB where the data's shape genuinely varies and is always consumed as a whole document (timetables, specifications); Postgres where the data is uniform and the value is in aggregate queries across many rows (sensor readings). That's a consistent, defensible rule — not "whichever was trendy."

Docker

Awareness level

Images vs Containers, Dockerfile basics

An image is a read-only, layered snapshot of a filesystem + runtime (your app code, dependencies, OS libraries) — a blueprint. A container is a running instance of that image, with its own writable layer on top. One image → many containers, the same way one class → many objects.

# Minimal Dockerfile for a Node/Express API
FROM node:20-alpine        # base image — layer 1
WORKDIR /app
COPY package*.json ./
RUN npm ci --production    # dependencies — cached as their own layer
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

Layer order matters for build speed: COPY package*.json before COPY . . means Docker's build cache reuses the (slow) npm ci layer whenever only application code changed, not just dependencies.

Awareness level

Why containerize

  • "Works on my machine" elimination — the container packages the exact runtime + dependency versions, so dev/staging/prod run identical environments.
  • Isolation — each container has its own filesystem/process namespace, so one app's dependencies can't clash with another's on the same host.
  • Reproducible deploys — deploying is "run this exact image" instead of "run this setup script and hope."
  • Horizontal scaling — spinning up N identical containers behind a load balancer is the basic unit most cloud orchestration (ECS, Kubernetes, Azure Container Apps) is built around.
📌 Likely to be asked

"Container vs VM?" → A VM virtualizes hardware and runs a full guest OS per instance (heavy, minutes to boot); a container shares the host's OS kernel and only isolates the process/filesystem layer (light, starts in ~seconds). That's the whole reason containers are cheap enough to spin up per-service or per-request-burst.

CI/CD

Awareness level

Pipeline stages & what problem it solves

CI (Continuous Integration): every push/PR automatically triggers build + test, catching breakage before it merges — instead of finding out something's broken after three other people built on top of it. CD (Continuous Delivery/Deployment): a passing build automatically flows to staging (Delivery, human approves the final prod push) or straight to production (Deployment, fully automatic).

StageWhat runs
Lint / static analysisFast, cheap checks first — fail early before spending time on a full build
BuildCompile / install dependencies / build the Docker image
TestUnit + integration tests (this is where a Postman/Newman collection run often plugs in — see below)
Deploy to stagingPush the build to a non-prod environment for final checks
Deploy to productionAutomatic (CD) or manual-approval-gated (Delivery)
📌 Likely to be asked

"What problem does CI/CD actually solve, in one sentence?" → It moves the cost of finding a bug from "a human notices it in production" to "an automated pipeline catches it in minutes, before merge" — the earlier a problem is caught in that chain, the cheaper it is to fix.

🎯 Common follow-up

"When would you use a managed database service (RDS/Atlas) instead of running Postgres/Mongo in your own container?" → Almost always, past a hobby-project scale — managed services handle automated backups, failover, patching, and point-in-time recovery, which is meaningfully harder to get right yourself than it looks. Self-hosting makes sense mainly when cost at scale or very specific configuration control outweighs that ops burden.

For solo/small-team projects (your own repos), the practical version of GitHub Flow is what you're actually doing: branch per feature, PR (even to yourself) as a checkpoint, merge to main.

Rebase vs merge

# merge — preserves both histories, creates a merge commit
git checkout main
git merge feature-branch

# rebase — replays your commits on top of main's latest tip,
# producing a linear history with no merge commit
git checkout feature-branch
git rebase main
MergeRebase
History shapePreserves exact chronological/branch structureLinear — looks like the work happened sequentially on top of main
Safety on shared branchesSafe alwaysNever rebase a branch others have already pulled — it rewrites commit hashes and breaks their history
Use whenMerging a finished feature branch into mainCleaning up your own local commits before opening a PR
⚠️ Interview trap

"Rebase rewrites history" is the golden rule to state explicitly: rebasing a branch changes every commit's hash after the rebase point. If someone else already based work on your pre-rebase commits, force-pushing the rebased branch orphans their work. Rule of thumb stated cleanly: rebase before you push/share, merge (or rebase only your own unshared commits) after.

Resolving conflicts

# after a merge/rebase reports a conflict, Git marks the file:
<<<<<<< HEAD
your version of this line
=======
their version of this line
>>>>>>> feature-branch

# after manually editing to the correct final content:
git add resolved-file.js
git rebase --continue   # or: git commit, if this was a merge

The actual skill being tested here isn't Git commands, it's judgment: understanding why both sides changed the same lines (usually two people touched the same function for different reasons) before picking a resolution, rather than blindly taking "ours" or "theirs."

Postman

API testing workflow & environments

An environment is a named set of variables (base_url, auth_token, tenant_id) swapped as a group — the same collection runs unmodified against local, staging, or production just by switching which environment is active.

// Pre-request script — runs before the request fires
const token = pm.environment.get("auth_token")
pm.request.headers.add({ key: "Authorization", value: `Bearer ${token}` })

// Test script — runs after the response comes back
pm.test("Status is 200", () => pm.response.to.have.status(200))
pm.test("Response has an id", () => {
  const json = pm.response.json()
  pm.expect(json).to.have.property("id")
})

// Chaining requests: save a value from this response for the NEXT request
pm.environment.set("created_spec_id", pm.response.json().id)

That last pattern — capturing a value from one response into an environment variable for a later request — is how you test multi-step flows (login → create → update → delete) as one ordered collection run instead of manually copy-pasting IDs between requests.

What "200+ Postman test cases" actually implies

A number like that isn't meaningful as a headline stat on its own — what makes it a credible, defensible claim in an interview is being able to explain what those cases were actually covering, so you're not caught flat if someone asks "200 tests for what, exactly."

  • Breadth across endpoints: with 60+ production API routes on the DigiFlute product (multi-tenant SaaS, per-role RBAC), even 2–3 cases per endpoint (happy path + one error path + one auth-boundary check) crosses 150+ before covering any edge cases.
  • RBAC boundary coverage: the same endpoint tested multiple times under different roles (Creator/Verifier/Approver/Admin) to confirm access is actually enforced, not just that the happy path works.
  • Negative/edge cases: malformed payloads, missing required fields, expired/invalid tokens, cross-tenant access attempts — these multiply case count fast and are usually where real bugs hide, not the happy path.
  • Environment reuse: the same collection run against dev/staging with different environment variables, rather than 200 cases meaning 200 hand-written one-off scripts.
💼 Resume tie-in

"The 200+ test cases weren't 200 happy-path checks — they covered the endpoint surface across multiple roles and both success and failure paths, which is what actually catches the bugs that matter in a multi-tenant system: an endpoint working correctly for the right role but failing to reject the wrong one. Chaining requests via environment variables (e.g. capturing a created resource's ID to use in the next request) let me test full multi-step flows — like a specification moving through Creator → Verifier → Approver — as one ordered run instead of testing each endpoint in isolation."

🎯 Common follow-up

"Why Postman collections instead of a proper automated test suite (Jest, PHPUnit)?" → Fair distinction to draw clearly: Postman collections are strong for black-box API contract testing — verifying the HTTP surface behaves correctly regardless of implementation — and they run via Newman in a CI pipeline just like a unit test suite would. What they don't replace is unit-level testing of internal logic (a function's edge cases in isolation) — the honest answer is these serve different layers, and a mature setup would have both, not one instead of the other.
