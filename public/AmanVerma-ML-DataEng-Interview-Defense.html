Likely follow-ups

QHow did you model the documents? Embed or reference?
Say: "Mixed, based on how each thing is read. A specification's revisions and its field values are embedded, because they are always fetched with the spec and never queried on their own. Products, components and users are separate collections referenced by ID, because they are shared across many specs and duplicating them would mean updating in twenty places. The rule I used was embed what is read together and owned by one parent, reference what is shared."
This is the single most important answer in the section for a data role. Learn it properly, because "embed versus reference" is the MongoDB schema question and a vague answer here reads as though someone else did the modelling.
QWhat did you index and why?
Say: "Company ID first, on every collection, because it is in the filter of literally every query. Then compound indexes where the list views sort, so company plus status plus updated-at for the spec list, since that is the exact shape of the main screen. The rule is that the index prefix should match how the query filters and sorts, or it does not get used."
QDid you ever look at a query plan?
Say: If you did, say what explain() showed you, ideally a collection scan you turned into an index scan. If you did not, say so: "Not systematically. I indexed on the access patterns rather than in response to measured slow queries, because at our data volume nothing was slow enough to force it." Honest and defensible. Inventing a profiling story is not.
QEmbedding revisions inside the spec document. What breaks eventually?
Say: "The 16MB document limit. A spec edited hundreds of times with the full field set stored each time would eventually hit it, and every read gets heavier along the way even when you only wanted the current version. The fix is a separate revisions collection with the current version denormalised onto the parent."
Knowing the 16MB limit and the unbounded-array antipattern is a strong signal for a data role.

QWhy does auditability matter here?
Say: "A packaging specification is a document a client signs off on, so if it changes after approval somebody needs to see who changed it and when. Overwriting in place destroys that. Every edit writes a new revision and deletes are flags rather than removals, so the history survives."

QSoft deletes make querying harder. How did you avoid the obvious bug?

Say this first

Plain-English version

"You type 'two slices of bread and an apple' and it works out that there are two foods, how much of each, and what that is nutritionally. A model I trained finds the food names, a set of rules pulls out the quantities and units, and then each food gets looked up in the USDA database and scaled to the portion."

What the code actually shows

models/food_ner/meta.json is committed and real. It is a blank English pipeline with a single component, ner, and exactly one label, FOOD. No word vectors.

nlp/spacy_model.py loads it from disk and returns None if the directory is missing. nlp/hybrid_extractor.py then combines model output with rule_based_extraction and uses difflib.SequenceMatcher for fuzzy matching.

Structure is clean: rules.py, spacy_model.py, preprocessing.py, hybrid_extractor.py. That separation reads well.

Likely follow-ups

QHow much data did you annotate, and what F1 did you get?
Go and get these numbers before the interview. This is the first question any ML interviewer asks about a trained model and there is no good improvisation. You need the number of annotated sentences, the train and test split, and precision, recall and F1 on the FOOD entity.
If the numbers do not exist, run the evaluation. It is an afternoon. Walking into an ML interview with "I trained a NER model" and no metric is the single most common way candidates lose these rounds.
QWhy train from a blank pipeline instead of fine-tuning en_core_web_sm?
Say: "FOOD is not a category the pretrained models have, and I only needed that one entity type, so a blank pipeline with a single label kept it small and fast. The trade-off is no pretrained word vectors, so the model has less to generalise from and needs more examples to reach the same place. With a bigger corpus I would start from a transformer base instead."
This is exactly right and it shows you understood what you were giving up. Say the vectors part, since meta.json shows zero vectors and an interviewer reading it will notice.
QWhy hybrid? Why not let the model extract quantities too?
Say: "Because quantities are a regular language and food names are not. 'Two', '2', 'a couple of', 'half a cup' is a small closed set you can enumerate, and rules get it right every time with no training data. Food names are open vocabulary, new ones appear constantly, and that is where a model earns its keep. Using the right tool for each half meant I needed far less annotation."
Strong answer. Knowing when not to use ML is something interviewers explicitly look for.
QWhat happens if the NER model fails to load?
Say: "The loader returns None and the extractor falls back to the rule-based path alone. Recall drops, since rules only catch foods in the known list, but the service keeps returning results instead of erroring. That is deliberate, and the same pattern shows up in the other systems I have built."
This is a real code path, not a story. Very good answer.
QHow do you match an extracted string to a USDA entry? "Chicken" matches hundreds of rows.
Say: "Fuzzy string similarity with difflib, and the similarity ratio becomes the confidence score I return alongside the match, so downstream can see how sure the lookup was. It is the honest weak point of the pipeline. 'Chicken' really does match dozens of USDA entries with different nutrition, and picking the highest string similarity is not the same as picking the right food. Embedding the food names and matching on vector similarity would be the upgrade, and better still would be surfacing the top three and letting the user pick."
Naming this yourself is much better than having it found. String matching against a food database is a known hard problem.
QWhat is portion scaling?
Say: "USDA gives nutrition per 100g, so everything has to be converted. Grams are direct. Units like cups and slices need a per-food conversion, since a cup of rice and a cup of spinach are wildly different weights, so those come from a lookup table. Where I have no conversion I fall back to a default serving size and lower the confidence."
Verified in Model_Image/main.py
"Fine-tuned a ResNet-50 food classifier in PyTorch via transfer learning, versioning checkpoints with Git LFS, and served both models behind a FastAPI inference API returning a unified JSON schema with per-item macros and deterministic fallbacks on upstream failure."
What the code actually shows

build_model() calls models.resnet50(weights=ResNet50_Weights.IMAGENET1K_V1), then replaces the final layer with nn.Sequential(nn.Dropout(p=0.5), nn.Linear(in_features, num_classes)). Textbook transfer learning, confirmed.

Likely follow-ups

QWhat did you freeze, and what did you actually train?
Say what you did. The standard two-phase answer: freeze the backbone and train only the new classifier head first, then unfreeze the last block or two and continue at a much lower learning rate. If you only trained the head, say only that. Whichever it was, know it, because "fine-tuned" without knowing which layers moved is the tell that someone ran a script they did not read.
QHow many classes, what dataset, what accuracy?
Get all three before the interview. The class count is in class_mapping.json. The run is called exp_combined_small, which suggests a combined dataset, so know which datasets and how many images. And you need validation accuracy, top-1 at minimum. There is a best_model.pth, which means something was being selected on, so the number exists somewhere.
QWhy dropout 0.5 on the head?
Say: "Regularisation. The backbone has ImageNet features and the head is the only thing learning my classes on a fairly small dataset, so it overfits easily. Dropout on the head was the cheapest thing that helped. Augmentation on the training set was the other lever."
QWhy ResNet-50 and not something newer and lighter?
Say: "It is a well-understood baseline with reliable pretrained weights, and I wanted the variable to be my data, not my architecture. EfficientNet or a ViT would likely do better on accuracy per parameter, and if this were going on a phone I would want something mobile-shaped instead. For establishing whether the idea worked at all, ResNet-50 was the boring correct choice."
"Boring correct choice, deliberately" is a good look. Reaching for the newest architecture without a reason is not.
QWhy Git LFS?
Say: "Model checkpoints are large binaries and Git stores a full copy of every version, so committing them normally bloats the repo permanently and clones get painful. LFS keeps a pointer in Git and the blob elsewhere. It is the minimum viable version control for model artifacts. A proper setup would use a model registry with metrics attached to each version."

The Food_Logging README documents LogMeal, a commercial food recognition API, as the image path in the unified service. Your resume says you trained a food classifier. Both are true. An interviewer who reads one and then the other will think one of them is not.

Say this before they ask

The unified API also integrates LogMeal, because a commercial model covers far more classes and does multi-item segmentation on a plate, which mine does not. QSo why train your own at all if the API is better?
Say: "Cost and control. Every LogMeal call is a paid request and a network dependency, and for a fixed set of common foods a small local model handles it for free with lower latency. This is a genuinely good ML systems answer. Model cascades by cost and confidence are a real production pattern.

Say: "The class mapping carries nutrition per class so image predictions resolve without a second network call, which was fine for a fixed class list. Spotting your own two-sources-of-truth problem is exactly the instinct a data role wants.

Likely follow-ups

QName the five dimensions.

QHow is technical depth actually scored?
Say it straight: "Keyword and vocabulary density against the expected domain terms for the role, plus structural checks on the answer. Cost, drift and auditability. Three good reasons, and the auditability one is the strongest for a hiring product.

Say: "Latency and cost. A live interview means multiple calls per turn and a candidate sitting there waiting, so a slow model makes the product unusable regardless of quality. Numbers match the README exactly

What the code actually shows

Likely follow-ups

QWhy six seconds? Why two retries?
Say: "Worst case a candidate waits six seconds, then one, then six, then two, then six. That is roughly twenty-one seconds before the fallback fires, which is already at the edge of what someone will sit through in a live interview. More retries makes the worst case worse for the person waiting, and the failures I actually saw were rate limits, which a third retry a second later does not fix anyway."
Do the arithmetic out loud. Being able to state your own worst-case latency is a small thing that reads as though you designed it rather than copied it.
QWhat does the candidate experience when the fallback fires?
Say: "They get a question from the pre-written script for their role instead of a generated one, so the interview continues and they never see an error. The honest cost is that the adaptive part stops for that turn, since a scripted question does not respond to what they just said. It degrades to a fixed interview rather than to nothing."
QYour README says the fallbacks guarantee 100% platform uptime. Do you believe that?
Say: "No, and I would not write that line again. Fallbacks mean a Gemini outage does not take the interview down, which is a real property worth having. Uptime depends on my own service, the host and the network too, and no fallback protects against those. It should say the system degrades gracefully when the model provider fails."
Someone will read that README. Getting there first turns an overclaim into evidence that you have calibrated since writing it.
QTimeout plus retry on a non-idempotent call. Any risk?
Say: "A timeout does not mean the call did not happen, it means I stopped waiting. Since these are generation calls with no side effects beyond cost, a duplicate is wasted money rather than corrupted state. If the call wrote something I would need an idempotency key so the retry is recognised as the same request."
Excellent answer if they go there. Most candidates have never thought about it.

The hard questions

RecrutAI is an AI system that judges people. Any serious ML or data interviewer will push on validity, fairness and state. These are the ones that actually decide the round.

QHow do you know the scores are any good?
Say: "I do not, in a measured sense, and that is the biggest gap in the project. There is no labelled set of interviews with human scores to compare against, so I cannot tell you agreement with a real interviewer. Validating it properly means collecting a few hundred transcripts scored by humans and measuring correlation, then checking test-retest consistency by running the same transcript through twice and seeing whether the score moves."
This is the answer that wins or loses the ML round. The instinct they are testing is whether you know that a model producing output is not the same as a model being right. Naming the exact validation you would run turns a gap into evidence of judgement.
QAn AI screening candidates. What about bias?
Say: "It is a real risk and I did not test for it. Keyword density scoring will favour candidates who use the vocabulary the model expects, which correlates with a particular kind of background, and the communication dimension measures fluency, which disadvantages non-native speakers on something that is not the skill being hired for. Testing it means the same answer content phrased different ways and checking whether the score moves when it should not. In production I would want it as a signal for a human reviewer, never an automatic reject."
Never say "the AI is objective." It is the wrong answer and it is the one they are listening for.
QWhere does session state live?
Say: "In a global in-memory map keyed by session ID, and users sit in a JSON file hashed with scrypt, with tokens held in memory on a fourteen-day TTL. It is the right amount of infrastructure for a demo and completely wrong for production. A restart loses every interview in progress, and you cannot run a second instance because the two would not share sessions. Postgres for users and sessions, Redis for the live state."
Say it before they find it. The README states it plainly, so pretending otherwise is not an option.
QWhy scrypt and not bcrypt?
Say: "It is in Node's standard crypto module, so no dependency, and it is memory-hard, which makes GPU-parallel cracking more expensive than with bcrypt. Either is a defensible choice. What matters is that it is not a bare hash and not something homegrown."
QYour proctoring deducts 8 points for a high-severity event. Where did 8 come from?
Say: "I picked it. There is no empirical basis for eight versus five and I would not pretend otherwise. What I can defend is the structure, which is that integrity penalties are subtracted from the base score rather than blended into it, so a recruiter can see the two separately and disagree with the penalty without losing the assessment. The weights should be configurable, and they are not."
"I picked it, here is what I can defend instead" is a much better answer than inventing a justification.
QTab-switching detection. Does that not punish honest behaviour?
Say: "Yes, sometimes. A notification steals focus and that looks identical to looking something up. It is why the dashboard shows the events and the timeline rather than just a number, so a human can look at three focus losses in the last minute of a hard question and decide for themselves. Treating it as evidence rather than a verdict is the only defensible way to use it."

The question you must not fumble

"How do you know your model is good?" It comes in some form in every ML interview. The answer always involves a baseline, a held-out set, and a metric chosen to match what going wrong actually costs. If the answer starts with an accuracy number and stops there, that is a fail.

A DE role means a SQL screen, usually written and usually harder than people expect. Your resume lists SQL, PostgreSQL, MySQL, ETL and schema design, so all of it is fair game.

LLM and RAG questions

You have LangChain, Hugging Face, RAG pipelines, prompt chaining and the Gemini API on the skills line, plus two LLM projects. This is the most fashionable part of your resume and it will get the most attention.

QExplain RAG to someone non-technical.
Say: "The model does not know your documents, so before asking it anything you search your own documents for the passages most likely to contain the answer and paste those into the question. The model answers from what you gave it rather than from memory, which is what stops it making things up and lets you point at where the answer came from."
QYour RAG gives a wrong answer. How do you debug it?
Say: "Separate retrieval from generation first, because they fail differently. Look at what chunks came back. If the right passage was never retrieved, the problem is chunking or embeddings or the query, and no amount of prompt work fixes it. If the right passage was retrieved and the answer is still wrong, then it is the prompt or the model. Most RAG failures I have seen are retrieval failures that people try to fix with prompting."
This is a genuinely strong answer and it is the one people who have actually built RAG give.
QHow do you chunk?
Say what you did, with the size and overlap, and why. The reasoning that matters: chunks too small lose the context that makes a passage meaningful, too large and the embedding averages over several topics so it matches nothing well. Overlap stops an answer that straddles a boundary from being lost. Splitting on structure, paragraphs and sections, beats splitting on character count.
QHow do you get structured output from an LLM reliably?
Say: "Ask for a fixed schema, validate what comes back, and have something to do when it does not parse. In RecrutAI that is exactly the fallback layer, since the branching decision has to be one of a fixed set of actions, and if the response is not one of those the system takes the default rather than crashing. Constrained decoding or a JSON mode helps, but you still validate."
QHow do you evaluate an LLM feature at all?
Say: "Build a small set of inputs with known good outputs and run it every time the prompt changes, because otherwise you are tuning by vibes and every fix silently breaks something else. For anything where correctness is fuzzy you need either human ratings on a sample or a model judging against a rubric, and the judge needs checking against humans before you trust it."
