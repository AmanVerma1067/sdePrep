01 Browser & frontend runtime

The Critical Rendering Path

What the browser does between receiving HTML and showing pixels:

HTML ──parse──► DOM ┐ ├──► Render Tree ──► Layout ──► Paint ──► Composite CSS ──parse──► CSSOM ┘ (visible only) (where) (what) (layers→screen) Layout = compute size and position of every box (expensive) Paint = fill in pixels: colours, text, shadows (medium) Composite = stack the painted layers on the GPU (cheap)

The render tree contains only what's visible. An element with display:none never enters it. visibility:hidden does enter it — it takes up space, so it must be laid out.

Reflow vs repaint

You change…TriggersCost
width, height, margin, padding, font-sizeReflow → repaint → compositeHighest — may re-layout the whole page
color, background, box-shadow, visibilityRepaint → compositeMedium
transform, opacityComposite onlyLowest — GPU, no layout, no paint
🚨 First-Principles Trap

Layout thrashing. Reading a layout property (offsetTop, offsetWidth, getBoundingClientRect) forces the browser to flush pending changes and compute layout right now, because it must give you an accurate answer. So a loop that writes a style then reads a position triggers a full reflow on every iteration:

for (el of els) { el.style.width = x + 'px'; console.log(el.offsetWidth); } — 100 elements, 100 forced layouts.

Fix: batch reads, then batch writes. Read all the values first, then apply all the changes. One layout instead of a hundred.

Related: this is exactly why CSS animations should use transform and opacity rather than left and width. Animating left reflows every frame and drops below 60fps; animating transform is a GPU composite and stays smooth.

async vs defer

<script> HTML parse ──[STOP]── download ── execute ──[RESUME]── (blocks everything — worst case) <script async> HTML parse ──────────────────────────────────────── download ─── execute (parse PAUSES here) → runs as soon as it lands. ORDER NOT GUARANTEED. <script defer> HTML parse ────────────────────────────► DOM ready download execute (in order) → after parsing, IN DOCUMENT ORDER. The safe default.

Rule of thumb: defer for anything that touches the DOM or depends on another script. async only for independent scripts that don't care about order or the DOM — analytics being the classic example.

The DOM and event flow

An event travels in three phases: capturing (window down to the target), target, then bubbling (target back up to window). Listeners default to the bubbling phase; pass true as the third argument to catch it on the way down.

window │ ▲ capture ▼ │ bubble document │ ▲ ▼ │ <ul> ← ONE listener here handles all <li> clicks │ ▲ ▼ │ <li> ← target
🛡️ SDE Core

Event delegation is why bubbling matters practically. Instead of attaching 1,000 listeners to 1,000 list items — 1,000 objects in memory, all needing cleanup — attach one to the parent and read event.target to find which child was clicked.

Two wins beyond memory: it automatically works for items added later (a newly inserted row needs no listener), and there's one thing to remove on teardown instead of a thousand. This is exactly what React does internally — it attaches a small number of listeners at the root rather than one per element.

Know the difference between stopPropagation() (halts the journey up the tree) and preventDefault() (allows propagation but cancels the browser's default action, like following a link).

The browser event loop

┌─────────────┐ offload ┌──────────────┐ │ Call Stack │ ──────────► │ Web APIs │ timers, fetch, DOM events │ (one thread)│ └──────┬───────┘ └──────▲──────┘ │ done │ ▼ │ ┌─────────────────────────┐ │ │ Macrotask queue │ setTimeout, I/O, events │ ├─────────────────────────┤ └──────────────┤ Microtask queue │ Promise.then, queueMicrotask event loop: └─────────────────────────┘ 1. run stack to empty 2. DRAIN ALL microtasks ← every single one 3. take ONE macrotask 4. repeat (render between steps)
🚨 First-Principles Trap

Microtasks drain completely; macrotasks are taken one at a time. That asymmetry is the whole answer to ordering puzzles — and it means a promise that schedules another promise, recursively, starves the queue. The page freezes and no timer ever fires, because step 2 never finishes.

The classic ordering question: console.log('A'); setTimeout(()=>log('D'),0); Promise.resolve().then(()=>log('C')); console.log('B'); → A, B, C, D. Sync code first, then all microtasks, then macrotasks. And setTimeout(fn, 0) does not mean "now" — it means "after the stack empties and all microtasks are done."

Memory and garbage collection

Mark-and-sweep: start from the roots (globals, the current call stack), mark everything reachable, delete everything unmarked. So an object is freed when it's unreachable, not when it's "unused."

Common leaks, all the same shape — something still holds a reference:

  • An event listener never removed keeps its closure, and everything the closure captured, alive.
  • A setInterval never cleared keeps running and keeps its callback reachable.
  • A detached DOM node still referenced by a variable — removed from the page, still in memory.
  • A cache or array that only ever grows.

Cookie flags that matter: HttpOnly (JavaScript can't read it — blocks XSS token theft), Secure (HTTPS only), SameSite — Strict never sends cross-site, Lax sends on top-level navigation only, None always sends and requires Secure.

🚨 First-Principles Trap

"Where do I store the auth token?" has no safe answer — you're choosing which attack to defend.

localStorage is readable by any JavaScript on your page, so one XSS — including from a compromised npm dependency — steals the token. An HttpOnly cookie is unreadable by JS, but it's sent automatically on every request to your domain, which is precisely what makes CSRF possible.

The usual production answer: HttpOnly; Secure; SameSite=Strict cookies, since SameSite defeats most CSRF, plus a CSRF token for anything sensitive. Bearer headers for mobile clients that have no cookie jar. State the trade-off rather than picking one and calling it "secure."

Same-Origin Policy and CORS

An origin is protocol + domain + port. All three must match. https://a.com and http://a.com are different origins; so are a.com and api.a.com; so are ports 80 and 3000.

The Same-Origin Policy stops page A reading a response from origin B. CORS is the server's way of granting an exception — a set of response headers saying "this origin is allowed."

SIMPLE REQUEST (GET/POST, basic headers) browser ──── GET /data ────► server ◄─── Access-Control-Allow-Origin: https://app.com PREFLIGHT (PUT/DELETE, custom headers, JSON content-type) browser ──── OPTIONS /data ────► "may I send a PUT with Authorization?" Access-Control-Request-Method: PUT ◄─── Access-Control-Allow-Origin: https://app.com Access-Control-Allow-Methods: PUT, DELETE Access-Control-Allow-Headers: Authorization Access-Control-Max-Age: 86400 ← cache it, skip future preflights browser ──── PUT /data ────► only now does the real request go
🚨 First-Principles Trap

CORS is enforced by the browser, not the server — and it is not a security feature for your API. The request usually reaches your server and executes; the browser just refuses to hand the response to JavaScript. A curl request, a mobile app or a script ignores CORS entirely. So CORS protects users from malicious pages, not your API from attackers. Your API still needs real authentication.

And Access-Control-Allow-Origin: * cannot be combined with Allow-Credentials: true — browsers reject it, because "any site may send authenticated requests and read the results" would be catastrophic. With credentials you must name the exact origin.

💡 Mental Model

TCP is registered post; UDP is shouting across a room. The choice is: is a late packet still useful?

In a video call, a frame that arrives 400 ms late is worthless — you'd rather have a brief glitch than a call that runs progressively behind. UDP drops it and moves on. In a file download, every byte matters no matter how late, so TCP retransmits. Reliability isn't universally good — it costs latency, and sometimes latency is what you're buying.

TLS in one paragraph

Asymmetric crypto (slow, but no shared secret needed) is used once to verify the server's certificate and agree a session key. Everything after that uses symmetric crypto (fast) with that key. Asymmetric to establish trust, symmetric to move data — that sentence is the whole answer, and it explains why HTTPS isn't meaningfully slower once connected.

🚨 First-Principles Trap

"HTTP/2 fixed head-of-line blocking" is only half right, and the other half is the good answer. HTTP/2 fixed it at the application layer — ten requests share one connection instead of queueing. But they still share one TCP stream, and TCP guarantees in-order delivery. So one lost packet stalls every multiplexed request until it's retransmitted, even requests whose data already arrived.

HTTP/3 moves to QUIC over UDP precisely to escape this: streams are independent at the transport layer, so a lost packet stalls only its own stream. That's why HTTP/3 uses UDP — not because UDP is faster, but because TCP's ordering guarantee was the bottleneck.

REST's six constraints

  1. Client-server — separate concerns, evolve independently.
  2. Stateless — every request carries everything needed. No server-side session memory.
  3. Cacheable — responses say whether they can be cached.
  4. Layered — a client can't tell if it's talking to the server or a proxy/CDN.
  5. Uniform interface — resources, standard verbs, self-describing messages.
  6. Code-on-demand (optional) — the server may send executable code.

Statelessness is the one that carries the weight, because it's what makes horizontal scaling possible: any server can handle any request, so you add servers behind a load balancer without sticky sessions.

Sessions vs JWTs

STATEFUL SESSION STATELESS JWT cookie: sid=abc123 header.payload.signature │ │ ▼ ▼ server looks up abc123 server verifies the signature in a session store using a key it already has │ │ ✅ revoke instantly (delete it) ✅ no lookup, scales freely ❌ needs shared storage ❌ valid until it expires — across all servers you cannot "log out"
🛡️ SDE Core

The trade is revocation versus lookup. Sessions can be killed instantly but require shared state every request. JWTs need no lookup but stay valid until exp, so logout is a client-side illusion.

The standard resolution: short access token (~15 min) + long refresh token stored server-side. The short life bounds the damage from theft, and the refresh token — because it is tracked — can be revoked. You've reintroduced state, but only on one endpoint instead of all of them, which is the actual insight. If someone asks "how do you log a JWT user out?", "you can't, so here's how the design works around it" is the answer.

Also: a JWT is signed, not encrypted. Anyone can decode the payload. Signing proves it wasn't altered; it hides nothing. Never put secrets in claims.

XSS vs CSRF

 XSSCSRF
AttackAttacker's JS runs on your pageAttacker's page makes the browser send a request to your site
NeedsUnescaped user input rendered as HTMLThe victim already logged in + cookies sent automatically
Can read the responseYes — full controlNo — only fires the request
DefenceEscape output, Content-Security-Policy, HttpOnlySameSite cookies, CSRF tokens, check Origin

Types of XSS: stored (the payload is saved in your database and served to everyone), reflected (bounced back from a URL parameter), DOM-based (never touches the server — client JS writes untrusted data into the page).

🚨 First-Principles Trap

XSS defeats every CSRF defence. If an attacker can run JavaScript on your origin, they can read your CSRF token and send perfectly valid requests. So the defences aren't equal partners — fix XSS first, because CSRF protection assumes your page isn't already compromised.

And the subtle one: CSRF works precisely because the browser is being helpful. Cookies are attached automatically to any request to your domain, including one triggered by a form on evil.com. The attacker never sees the response — they just need the side effect (transfer money, change email) to happen. That's why SameSite is such an effective fix: it stops the automatic attachment.

03 Database fundamentals

Storage models

 Row-oriented (OLTP)Column-oriented (OLAP)Document / KV
Stores togetherAll fields of one rowAll values of one columnA whole nested object
Fast at"Give me this one record""Average this column over 50M rows""Give me this document"
CompressionPoor — mixed typesExcellent — same type togetherVaries
ExamplePostgreSQL, MySQLClickHouse, Redshift, ParquetMongoDB, Redis, DynamoDB
💡 Mental Model

Storage layout is a bet about which direction you'll read. Rows bet you want whole records; columns bet you want one field across many records.

Disks read in blocks, so an average over one column in a row store drags every other column into memory too — 20 fields read to use one. A column store reads only that column's blocks, and because every value is the same type, it compresses far better. Same data, opposite physical layout, roughly 100× difference on analytical queries.

ACID and what enforces each letter

PropertyMeansEnforced by
AtomicityAll or nothingWrite-ahead log + undo — replay or roll back on crash

IsolationConcurrent transactions don't corrupt each otherLocking or MVCC
DurabilityCommitted means survives a power cutfsync the log to disk before acknowledging

Write-Ahead Logging in one line: write down what you're about to do, and flush that note to disk, before doing it. On restart, replay the log. Sequential log writes are fast; random page writes are slow — so WAL gives durability without paying random-write cost on every commit.

Isolation levels

LevelDirty readNon-repeatable readPhantom read
Read UncommittedPossiblePossiblePossible
Read CommittedPreventedPossiblePossible
Repeatable ReadPreventedPreventedPossible*
SerializablePreventedPreventedPrevented

* In the SQL standard. PostgreSQL's MVCC snapshot blocks most phantoms at Repeatable Read.

  • Dirty read — you see a change another transaction hasn't committed, and it might roll back.
  • Non-repeatable read — you read a row twice in one transaction and the value changed.
  • Phantom read — you run the same WHERE twice and get extra rows. Not a row changing; the row set changing.
🚨 First-Principles Trap

Serializable isn't free, and it isn't "just safer." Higher isolation means either more locking (more waiting, more deadlocks) or optimistic checks that abort transactions. At Serializable, Postgres may kill your transaction with a serialization failure — so your application must be prepared to retry. Choosing Serializable without retry logic turns a correctness feature into random 500s under load.

Most systems run Read Committed and handle specific races explicitly with SELECT FOR UPDATE or a conditional UPDATE ... WHERE. That's targeted, cheap, and predictable.

Index structures

StructureLookupRangesWritesUsed by
B+ TreeO(log N)✅ ExcellentModeratePostgres, MySQL, most SQL
HashO(1)❌ NoneFastIn-memory maps, some KV stores
LSM TreeSlower reads✅Very fastCassandra, RocksDB, LevelDB

Why B+ Tree and not a binary tree: disks read in blocks, so you want each node to hold hundreds of keys and fill exactly one block. A tree with fanout 500 reaches a billion rows in about four levels — four disk reads — where a binary tree would need thirty. Also, in a B+ Tree all real data lives in the leaves, which are linked together, so a range scan is "seek once, then walk sideways."

💡 Mental Model

LSM trees trade read speed for write speed, on purpose. Writes go to an in-memory table and an append-only log — never a random disk seek — then get flushed to immutable sorted files, which are periodically merged in the background.

The cost: a read may have to check several files. The benefit: writes are sequential, which is the single fastest thing a disk does. That's why write-heavy systems (time-series, event logs, message stores) use LSM, while read-heavy transactional systems use B-Trees. The data structure encodes the workload assumption.

Normalization

  • 1NF — one value per cell, no lists stuffed into a column, rows are unique.
  • 2NF — 1NF, and no column depends on only part of a composite key.
  • 3NF — 2NF, and no column depends on another non-key column. (Don't store city next to pincode.)

What normalization actually prevents is anomalies, and naming them is better than reciting the forms: an update anomaly (a value stored in five places, you change four), an insert anomaly (you can't record a department until someone works there), a delete anomaly (removing the last employee erases the department).

Denormalize deliberately when reads dominate and the duplicated value rarely changes. You're buying read speed with the obligation to update in two places — a fine trade, as long as it's a decision rather than an accident.

04 AI / ML fundamentals

The lifecycle

problem → data → features → train → evaluate → deploy → monitor ▲ │ └──────────── retrain ◄──────────────────┘ supervised : labelled data (spam / not spam) unsupervised : no labels, find structure (customer clusters) self-supervised: labels from the data itself (predict the next word) reinforcement : learn from reward signals (game playing, robotics)

Preprocessing

  • Imputation — fill missing values (mean, median, or a "missing" category). Note that missingness itself is often a signal worth keeping as a flag.
  • One-hot encoding — for categories with no order (red/green/blue). One column each.
  • Ordinal encoding — for categories with real order (small/medium/large → 1/2/3).
  • Standardization (z-score) — (x − mean) / std. Mean 0, std 1. The default; handles outliers better.
  • Min-max normalization — squash to [0,1]. Good when you need a bounded range; badly distorted by outliers.
📊 ML Track — why scaling matters at all

Gradient descent takes steps proportional to feature magnitude. If age ranges 0–100 and income ranges 0–1,000,000, the loss surface is a long narrow valley — a learning rate small enough not to explode on income is far too small for age, so training crawls or diverges. Scaling makes it round, so one learning rate suits everything.

Distance-based methods (kNN, k-means, SVM) need it even more urgently: without scaling, income is the distance and every other feature is noise. Tree models don't care, because they split on thresholds rather than distances — worth saying, since it shows you know why rather than "always scale."

🚨 First-Principles Trap

Data leakage via the scaler. Fit the scaler on the whole dataset before splitting and the training set now contains information about the test set's mean and standard deviation. Your test score comes out optimistic, and you find out in production.

Correct order: split first, fit the scaler on train only, then transform train and test with that same fitted scaler. Same rule for imputation values and feature selection. And for time-series data, split by time, never randomly — a random split lets the model train on the future and predict the past, which is a leak so total the model can look near-perfect.

📊 ML Track — MSE vs MAE, said well

An error of 10 costs MSE 100 but costs MAE 10. So MSE will happily make ten predictions slightly worse to fix one large error, which is right when big misses are genuinely disproportionately bad — and wrong when your data has noisy outliers you'd rather ignore. Statistically, minimizing MSE fits the mean; minimizing MAE fits the median. That's the crisp version of "MAE is robust."

And for classification, cross-entropy beats MSE because its gradient through softmax simplifies to (prediction − target) — proportional to the error, no saturation. MSE with a sigmoid gives near-zero gradients exactly when the model is confidently wrong, which is the worst possible time to stop learning.

Gradient descent

VariantUpdate afterTrade-off
BatchWhole datasetStable direction, impossibly slow
SGDOne sampleFast and noisy; noise helps escape shallow minima
Mini-batch32–256 samplesThe real default — GPU-friendly, good estimate
  • Learning rate — too high overshoots and diverges; too low crawls or gets stuck. Schedules (decay, warmup, cosine) start fast and finish carefully.
  • Momentum — a running average of past gradients, so you roll through small bumps instead of zig-zagging.
  • Vanishing gradients — in deep networks, gradients multiply through layers and shrink toward zero, so early layers stop learning. Fixed by ReLU, normalization, and residual connections.
  • Exploding gradients — the opposite; fixed by gradient clipping.

Bias, variance and regularization

Total Error = Bias² + Variance + Irreducible Error
Train errorVal errorDiagnosisFix
HighHighUnderfitting (high bias)Bigger model, better features, train longer
LowHighOverfitting (high variance)More data, augmentation, dropout, L2, early stop
LowLowGoodShip it

Irreducible error is noise in the data itself — no model removes it, and chasing it is how you overfit. Worth naming, because it's the reason 100% accuracy is a red flag rather than a triumph.

  • L1 (Lasso) — constant gradient pushes weights to exactly zero → sparsity, automatic feature selection.
  • L2 (Ridge) — gradient shrinks with the weight, so weights get small but never zero → spreads influence across correlated features.
  • Dropout — randomly zero some activations each training step, so the network can't depend on any single neuron.
  • Early stopping — stop when validation loss turns up. Free, and often the strongest regularizer available.

Splits and cross-validation

Train fits the weights. Validation tunes hyperparameters and decides when to stop. Test is touched once, at the end. If you tune against the test set, it has quietly become a validation set and you no longer have an honest estimate.

k-fold cross-validation splits into k parts, trains k times using each part as validation once, and averages. Better use of limited data and a more reliable estimate — at k× the training cost.

Evaluation metrics

PREDICTED positive negative A positive │ TP │ FN │ ← missed it C ├─────────┼─────────┤ T negative │ FP │ TN │ U false alarm Accuracy = (TP + TN) / everything Precision = TP / (TP + FP) "when I said yes, was I right?" Recall = TP / (TP + FN) "of all the real ones, how many did I catch?" F1 = 2PR / (P + R) harmonic mean
🚨 First-Principles Trap

The 99% accuracy trap. If 1 in 100 transactions is fraud, a model that predicts "not fraud" every single time scores 99% accuracy — and catches zero fraud. Accuracy is dominated by the majority class, so under imbalance it measures the class distribution rather than the model.

Precision and recall fix it by ignoring true negatives entirely. Both are computed only from the things you predicted positive and the things that actually were positive — so the vast harmless majority stops inflating the number. Whenever classes are imbalanced, quote precision, recall and F1, and say why accuracy would mislead.

📊 ML Track — which one do you optimize?

There's no universal answer; it depends on which mistake costs more.

  • Recall matters most when missing a positive is dangerous — cancer screening, fraud detection, safety alerts. A false alarm costs a second test; a miss costs a life.
  • Precision matters most when a false alarm is expensive — a spam filter that bins a real job offer is worse than one that lets some spam through.
  • F1 when both matter and you want one number. It's the harmonic mean specifically because it refuses to reward a lopsided model: predict everything positive and recall hits 1.0 while F1 stays low.

ROC-AUC plots true-positive rate against false-positive rate across every threshold, so it measures ranking quality independent of where you set the cutoff. AUC 0.5 is random, 1.0 is perfect. Caveat worth adding: under extreme imbalance, precision-recall AUC is more informative than ROC-AUC, because ROC's false-positive rate is diluted by a huge true-negative count.

NLP and vision first principles

NLP — turning text into numbers:

  • Bag of Words — count each word. Order is lost.
  • TF-IDF — count × rarity, so common words stop dominating. Order still lost.
  • Embeddings — dense learned vectors where similar meanings sit close together. This is the leap: BoW and TF-IDF treat "car" and "automobile" as unrelated columns; embeddings place them nearby.

Vision — an image is a matrix of pixel values (height × width × 3 colour channels). A convolution slides a small learned filter across it, so the same feature detector works anywhere in the image — that's weight sharing, and it's why CNNs need far fewer parameters than a fully-connected network. The receptive field is how much of the original image one deep neuron can "see": stack layers and it grows, so early layers detect edges while deep layers recognise objects.

TLS certificate check, key exchange (1–2 round trips) asymmetric to agree a key, symmetric thereafter 5. HTTP GET /path + Host, Cookie, Accept headers 6. SERVER load balancer → app → DB/cache → response 7. RESPONSE status, headers (Content-Type, Cache-Control), body 8. RENDER HTML→DOM, CSS→CSSOM, render tree, layout → paint → composite 9. SUBRESOURCES images, JS, CSS fetched in parallel; JS may block parsing unless async/defer

Details that impress if you get to them: the browser checks its own cache before DNS at all; TCP's handshake is one round trip before any data moves, which is why connection reuse matters so much; and HTTP/3 collapses the TCP and TLS handshakes into one via QUIC.

Q2
TCP vs UDP — how do you choose?
💡 30-second opener

"TCP guarantees your data arrives complete and in order, and pays for that with a handshake, acknowledgements and retransmissions. UDP just fires packets and hopes. The question I'd ask is: is a late packet still useful? For a file download, absolutely — every byte matters, so TCP. For a video call, a frame that's 400 milliseconds late is worthless, and waiting for it makes the whole call lag, so UDP."

If they push: TCP's 3-way handshake is SYN → SYN-ACK → ACK, plus congestion control that slows down when the network is busy — good for fairness, bad for latency-sensitive traffic. UDP has none of that, so applications built on it implement whatever reliability they actually need, which is exactly what QUIC does: reliability and ordering per stream, over UDP, so one lost packet doesn't stall unrelated streams.

The line that lands: "reliability isn't free and it isn't always desirable — you're trading latency for it."

Q3
Authentication vs authorization, and sessions vs JWTs?
💡 30-second opener

"Authentication is 'who are you' — proving identity. Authorization is 'what are you allowed to do' — checking permissions. You always authenticate first. In HTTP terms that's the difference between 401 and 403: 401 means I don't know who you are, 403 means I know exactly who you are and you still can't do this."

On sessions vs JWTs: "A session stores state on the server and hands the client an ID; a JWT puts the claims in the token itself and signs them. The trade is revocation versus lookup. Sessions let you log someone out instantly by deleting the record, but every request needs a shared store. JWTs need no lookup so they scale freely — but a signed token stays valid until it expires, so you can't truly log someone out."

The resolution: "Short access tokens, around 15 minutes, plus a long refresh token stored server-side. The short life bounds the damage from theft, and the refresh token is tracked so it can be revoked. You've reintroduced state, but only on one endpoint instead of all of them."

Add if there's room: a JWT is signed, not encrypted — anyone can decode the payload, so never put secrets in it.

Q4
What are ACID properties, and what enforces them?
💡 30-second opener

"Four guarantees a transaction gives you. Atomicity — all of it happens or none of it does, enforced by a write-ahead log the database can replay or roll back. Consistency — constraints and invariants are never violated. Isolation — concurrent transactions don't corrupt each other, enforced by locking or MVCC. Durability — once I say committed, it survives a power cut, because the log was flushed to disk before I answered."

The example that makes it concrete: "A bank transfer is two updates — debit one account, credit another. Atomicity is what stops a crash between them from destroying money."

If they go deeper on isolation: name the anomalies rather than the levels. Dirty read = seeing uncommitted data. Non-repeatable read = the same row's value changes mid-transaction. Phantom read = the same query returns extra rows. Then: "each isolation level removes one more of these, and costs more concurrency to do it. Serializable can abort your transaction, so the application has to retry — that's why most systems run Read Committed and handle specific races explicitly."

Q5
How is machine learning different from traditional programming?
💡 30-second opener

"It's the same three pieces rearranged. Traditional programming: I write the rules, feed in data, and get answers out. Machine learning: I feed in data and the answers, and it produces the rules. So the rules become the output rather than the input."

TRADITIONAL data + rules ──► answers MACHINE LEARNING data + answers ──► rules (a model)

Then the "so what": "That's why ML is for problems where the rules exist but nobody can write them down. I can't write rules that identify a photo of biryani, but I can supply ten thousand labelled photos. Conversely, if the rules are writable — parsing '150g', validating an email — writing them is faster, exact, debuggable and free. A model that's 97% right on something a regex gets 100% right is a worse product."

The trade-off to name: "You give up determinism and explainability. Traditional code fails loudly with a stack trace pointing at the line. A model fails quietly with a confident wrong answer, and there's no line to point at."

Q6
Why is accuracy misleading, and how do precision and recall fix it?
💡 30-second opener

"Because accuracy is dominated by whichever class is bigger. If 1 in 100 transactions is fraud, a model that always says 'not fraud' scores 99% accuracy and catches nothing. It's measuring the class distribution, not the model. Precision and recall fix that by ignoring true negatives entirely — so the harmless majority stops inflating the score."

Define them in plain words: "Precision is: when I said yes, how often was I right? Recall is: of all the real cases, how many did I catch?"

Then the two scenarios, which is what they're waiting for:

  • "Cancer screening is recall-first. A false alarm costs a follow-up test. A miss costs a life. I'd accept far more false positives to miss fewer real cases."
  • "Spam filtering is precision-first. Some spam reaching the inbox is annoying. A real job offer sent to the spam folder is a disaster. I'd let spam through rather than risk that."

Close with the tension: "They trade off against each other — you move a threshold and gain one at the other's expense. F1 is the harmonic mean when you need one number, and it's harmonic specifically so a lopsided model can't game it. Under heavy imbalance I'd also look at precision-recall AUC rather than ROC-AUC, because ROC's false-positive rate gets diluted by the enormous true-negative count."
