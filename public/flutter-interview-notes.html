Flutter Fundamentals

Widget Tree

In Flutter, everything is a widget — layout, styling, even padding and alignment are widgets that wrap other widgets. The UI is a tree of these, rebuilt (not literally recreated on the OS canvas, but recomputed as a lightweight description) whenever state changes. Flutter actually maintains three parallel trees: the Widget tree (your immutable configuration, cheap to rebuild), the Element tree (the mutable, persistent structure that manages widget lifecycle and links to the render tree), and the RenderObject tree (does actual layout/painting). This separation is why "rebuild" doesn't mean "repaint everything" — Flutter diffs the new widget tree against the existing element tree and only touches the render objects that actually changed.

📌 Likely to be asked

"Why three trees instead of one?" → Widgets are cheap, throwaway, immutable descriptions rebuilt constantly; Elements and RenderObjects are the expensive, stateful, persistent parts that shouldn't be recreated every frame. Separating "what should this look like" (widget) from "the actual mutable object doing the work" (element/render object) is what makes Flutter's declarative rebuild-on-every-change model fast.

  State<Counter> createState() => _CounterState();

class _CounterState extends State<Counter> {
  int count = 0;
  void _increment() => setState(() => count++); // triggers a rebuild of THIS subtree only
  @override
  Widget build(BuildContext context) => Text('$count');
}

Widget Lifecycle

MethodWhen
initState()Once, when the State object is first created — the place to kick off initial data loads, subscriptions, controllers
build()Every time the widget needs to render — called far more often than the others, must stay fast and side-effect-free
didUpdateWidget()When the parent rebuilds this widget with new configuration (same State object reused) — compare old vs new widget params here
dispose()Once, when the widget is permanently removed — cancel subscriptions/controllers/timers here or leak memory
⚠️ Interview trap

Calling setState() after a widget is disposed (e.g. an async network call completing after the user navigated away) throws in debug mode and is a real production bug — always guard with a mounted check: if (mounted) setState(() => ...) before touching state after an await.

⚠️ Flag before you get asked this directly

Both StudySync and SahYatri's mobile app use plain StatefulWidget + setState() only — neither provider, riverpod, flutter_bloc, nor any other state package appears in either app's pubspec.yaml. If asked "which state management approach did you use," the honest answer for these two projects specifically is setState, which is a perfectly reasonable choice given both apps are single-screen-dominant (one main timetable/occupancy view) — but be ready to explain why that was sufficient here rather than implying a library was used that wasn't.

🎯 Common follow-up

"At what point would setState stop being sufficient for one of these apps?" → Once state needs to be shared across widgets that aren't in a direct parent-child relationship (e.g. a global connectivity/sync-status indicator visible in multiple screens), or once the same async loading/caching logic needs to be triggered from more than one place — at that point duplicating setState calls across widgets gets error-prone, and lifting that logic into a Provider/Riverpod-managed service becomes the right move.

Cross-Platform Architecture

How Flutter compiles to native

Flutter apps are written in Dart and don't run through a JS bridge or WebView the way some cross-platform frameworks do. In release builds, Dart is AOT (Ahead-Of-Time) compiled to native ARM/x64 machine code — the app ships as real native machine instructions, not interpreted at runtime. During development, Dart uses JIT (Just-In-Time) compilation instead, which is what enables hot reload — the running app's Dart code can be patched and re-executed without a full rebuild.

Flutter doesn't use each platform's native UI widgets at all — it draws every pixel itself using its own rendering engine (historically Skia, transitioning to Impeller on newer versions), directly onto a canvas the OS gives it. That's why a Flutter app looks pixel-identical on iOS and Android — it's not translating to native UIButton/native Android widgets, it's painting its own.

📌 Likely to be asked

"How does Flutter talk to native platform APIs (camera, GPS, Bluetooth) if it doesn't use native UI widgets?" → Platform Channels — an async message-passing bridge between Dart code and platform-specific Kotlin/Java (Android) or Swift/Objective-C (iOS) code, used specifically for capability access, not UI rendering. Packages like shared_preferences, http, and picamera2-style hardware access all sit on top of platform channels under the hood.

Dart basics relevant to interviews

  • Null safety: types are non-nullable by default (String name can never be null); nullable types are explicit (String? name), enforced at compile time — eliminates most null-pointer-style crashes before runtime.
  • Future and async/await: Dart's async model mirrors JS Promises conceptually — a Future<T> represents a value that will exist later, await pauses execution of the current async function until it resolves, without blocking the whole isolate.
  • Isolates: Dart's concurrency unit — each isolate has its own memory and event loop, no shared mutable state, communicating via message passing (similar spirit to Node's cluster workers, not OS threads with shared memory).
  • Everything is an expression-friendly, class-based OOP language with strong typing, closer to Java/Kotlin/TypeScript in syntax than to Python — comfortable ground coming from a CP/algorithms background.

Offline-First App Patterns

Local Caching Strategies

OptionShapeFits
SharedPreferencesSimple key-value store, values are primitives/stringsSmall data — settings, tokens, a single cached JSON blob (as in StudySync, below)
sqflite / DriftReal SQLite database with tables/queriesStructured, queryable local data — many records, relationships, filtering
Hive / IsarNoSQL local object store, typically faster than SQLite for simple object storageLarger structured datasets without needing SQL query capability

The general pattern regardless of storage choice: fetch from network → on success, write to local storage → render from the freshly fetched data; on failure, read whatever's already in local storage and render that instead. The "offline-first" framing means the local cache is treated as a legitimate data source, not just a fallback bolted on as an afterthought.

Sync-on-Reconnect Architecture (conceptual)

A fuller sync-on-reconnect system typically has three pieces: (1) a connectivity listener (e.g. Flutter's connectivity_plus package) that fires when the device transitions from offline to online, (2) a pending-write queue that buffers local changes made while offline so they can be replayed once connectivity returns, and (3) a reconciliation step that merges server state with local state once the replay completes.

📌 Likely to be asked

"What's the difference between 'sync on reconnect' and just 'retry on next request'?" → Retry-on-next-request is passive — the app only re-syncs the next time the user happens to trigger a network call (opening a screen, pulling to refresh). True sync-on-reconnect is active — a connectivity listener detects the transition back online and triggers a sync immediately, without waiting for the user to do anything. The difference matters most for apps with pending offline writes that need to reach the server promptly.

Conflict Resolution Basics

Conflicts only arise when writes can happen on both the client and elsewhere (another device, the server) to the same data while disconnected. Common strategies, roughly in order of complexity:

  • Last-write-wins (LWW): each record carries a timestamp; whichever write has the latest timestamp overwrites the other. Simple, but silently discards the losing write.
  • Field-level merge: instead of one write overwriting a whole record, merge at the field level — if device A changed the title and device B changed the description, keep both changes instead of one clobbering the other.
  • Version vectors / CRDTs: data structures specifically designed so concurrent edits can be merged deterministically without conflicts by construction — used in systems like collaborative editors; genuinely complex to implement correctly, usually reached for only when LWW's data loss is unacceptable.
🎯 Common follow-up

"How would you decide which strategy to use?" → Start from what happens if you're wrong: if losing a conflicting write is low-stakes (e.g. a "last viewed" timestamp), LWW is fine. If losing data is unacceptable (e.g. two people editing the same document offline), you need field-level merging or to surface the conflict to a human to resolve rather than resolving it silently.

The actual cache-then-network flow

Future<void> loadTimetable() async {
  setState(() => isLoading = true);
  try {
    final response = await http.get(
      Uri.parse('https://timetable-api-9xsz.onrender.com/api/timetable'),
      headers: {'x-api-key': 'tt_api_key', 'Content-Type': 'application/json'},
    );

    if (response.statusCode == 200) {
      final data = json.decode(response.body) as List<dynamic>;
      await cacheTimetable(response.body);  // write-through: cache the raw response
      applyTimetable(data);                     // render from the fresh data
      // shows a "Timetable updated successfully!" snackbar
    } else {
      await loadCachedTimetable();               // non-200 → fall back to cache
      // shows a "Using cached timetable" snackbar
    }
  } catch (_) {
    await loadCachedTimetable();                 // network exception → fall back to cache
    // shows a "Failed to connect. Using cached data" snackbar
  }
  setState(() => isLoading = false);
}

Future<void> cacheTimetable(String jsonData) async {
  final prefs = await SharedPreferences.getInstance();
  await prefs.setString('cached_timetable', jsonData); // raw JSON string, written whole
}

Future<void> loadCachedTimetable() async {
  final prefs = await SharedPreferences.getInstance();
  final cachedData = prefs.getString('cached_timetable');
  if (cachedData != null) applyTimetable(List<dynamic>.from(json.decode(cachedData)));
}

loadTimetable() is called from two triggers: initState() on app launch, and the LiquidPullToRefresh widget's onRefresh callback — a manual pull gesture re-runs the exact same fetch-cache-fallback flow.

💼 Resume tie-in

"The app treats the local cache as a first-class data source, not just a crash fallback — every successful network fetch writes through to SharedPreferences immediately, and any failure (bad status code or a thrown exception, covering both 'server responded with an error' and 'no network at all') falls back to whatever's cached, with an explicit snackbar telling the user which state they're in. That mattered specifically because the app is used by students checking their timetable throughout the day, often on unreliable campus WiFi — showing stale-but-present data beats showing a blank error screen."

⚠️ Dead code, and the "1.5 second" claim — reconcile before your interview

⚠️ Unused parallel implementation

The repo contains a second, separate caching implementation — lib/services/api_service.dart, lib/utils/local_storage.dart, and lib/models/timetable_model.dart (a typed TimetableEntry model with a LocalStorage class) — that timetable_screen.dart never actually calls. The live screen has its own inline cacheTimetable/loadCachedTimetable methods working directly with raw JSON strings, duplicating what the typed LocalStorage class already does. Worth knowing which files are load-bearing before a walkthrough — if asked to explain the caching architecture, describe the actual live path in timetable_screen.dart, not the unused typed-model version, or be upfront that the typed version was an earlier iteration that got superseded but not cleaned up.

⚠️ "Restores full sync within 1.5s of reconnect" — what this claim can and can't mean given the actual code

There's no connectivity listener anywhere in this code — no connectivity_plus or equivalent package, nothing watching for the device transitioning from offline to online. Sync happens on two triggers only: app launch (initState) and a manual pull-to-refresh gesture. So "restores sync within 1.5s of reconnect" cannot mean "the instant the network comes back, sync happens automatically" in this codebase — that behavior isn't implemented. What the 1.5s figure can honestly describe: the time from a sync being triggered (app reopened, or user pulls to refresh) to the cache being updated and the UI re-rendered with fresh data — which is plausible and measurable, since it's one HTTP GET against a small hosted API returning a small JSON payload, followed by a SharedPreferences string write and a setState call. That's a real, defensible number for "how fast does a triggered sync complete" — just be precise that it's not describing automatic background reconnect detection.

The honest framing for an interview: "sync is trigger-based, not connectivity-event-based — it runs on app foreground and on pull-to-refresh, and completes quickly (~1.5s) because it's a single lightweight request against a small payload with a simple write-through cache." That's a true, specific, defensible claim; "the app detects reconnection and syncs automatically" is not, for this codebase as written.

Conflicting writes & partial-sync failure

🎯 "How do you handle conflicting writes made offline by two devices?"

Honest answer for this specific app: it doesn't need to, because it isn't bidirectional. Data flows one way — server → client cache — the app never writes timetable data back up to the API, so there's no scenario where two devices' local edits could collide. If asked to design the bidirectional case anyway (worth having ready, since it's a natural extension question): I'd timestamp each local write, and on reconnect, compare the local write's timestamp against the server's last-modified timestamp for that record — last-write-wins for low-stakes fields, with a merge or user-prompted resolution for anything where silently discarding a change would be a real problem (see Conflict Resolution Basics above).

🎯 "What happens if sync fails partway through?"

There isn't really a "partway" state to worry about here, and that's worth stating as a deliberate strength of the simple design rather than a gap: the cache write is a single SharedPreferences.setString() call with the complete response body, executed only after the HTTP request has already fully succeeded (status 200) and the full body is in hand. There's no multi-step write sequence that could be interrupted midway — either the whole fetch succeeds and the whole cache gets overwritten in one atomic call, or it doesn't and the previous cache is untouched. The trade-off: this simplicity works because the payload is small and the write is a single key. A more complex sync (e.g. writing many individual records) would need to actually reason about partial-failure/rollback, which this pattern sidesteps rather than solves.

class ApiService {
  static const String apiUrl = "https://bus-api-ihcu.onrender.com/api/occupancy";

  static Future<List<BusOccupancy>> fetchOccupancyData() async {
    final response = await http.get(Uri.parse(apiUrl));
    if (response.statusCode == 200) {
      List<dynamic> data = jsonDecode(response.body);
      return data.map((json) => BusOccupancy.fromJson(json)).toList();
    } else {
      throw Exception("Failed to load data");  // no fallback — propagates straight up
    }
  }
}

shared_preferences is listed in this app's pubspec.yaml, but grep across the screens shows it's never actually used — no cache write, no cache read, no offline fallback path. A failed request throws and, unless the calling screen wraps it, surfaces as an error state with no cached data to fall back on.

⚠️ Be precise about which app has which architecture

If asked generally "tell me about your offline-first Flutter work," this app is not an example of it — StudySync is. It's a good thing to know cold rather than accidentally conflate the two apps' architectures under interview pressure; SahYatri's mobile app is a straightforward online-only client for the bus-occupancy API, and that's a perfectly fine, honest thing to say about it.
